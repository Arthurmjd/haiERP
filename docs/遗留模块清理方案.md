# 遗留模块清理方案

> 目标：移除 `myFactoryAI` 底座中与海岚 ERP 无关的存量代码（1044 + 87 个 Java 文件 + 210 个 XML，约 16.2 万行），
> 在**不改变任何现有业务行为**的前提下，降低构建/启动开销、缩小攻击面、消除新人误读源码的风险。
>
> 分析基线：`master` @ `9a40421`。所有数字与结论均来自实测命令，非估算。

---

## 0. 一页结论

| 项 | 结论 |
| --- | --- |
| 能否安全切除 | **能**。保留侧对遗留包**零引用**，遗留包内**零横切关注点** |
| 清理对象 | 1131 个 Java + 210 个 XML，共 **162,411 行** |
| 保留对象 | `net/factoryopen/myfactoryai/erp/**` 41 个文件（自研业务）+ `ruoyi-*` 底座 + `myfactoryai-ai` + `myfactoryai-system` |
| 最大风险 | **XML 与实体类必须同批删除**。`<resultMap type="OrdSo">` 走短别名解析（`typeAliasesPackage: net.factoryopen.**.domain`），只删 Java 不删 XML → 启动即失败 |
| 推荐路径 | **一次性物理删除（方案 A）**，用 `git rm` 保证可回滚；方案 B 仅作为过渡 |
| 实际收益 | 编译时间、IDE 索引、启动时 MyBatis 解析开销、攻击面；**jar 体积几乎不变**（221MB 主要是第三方依赖） |
| 工作量 | 约 30 分钟改动 + 一轮全量回归 |

## 2. 依赖实测：为什么这次切除是安全的

四条正向证据 + 三条反证检查，全部为实测输出。

### 2.1 正向证据

| # | 检查项 | 命令 | 结果 |
| --- | --- | --- | --- |
| E1 | 保留侧是否 import 遗留包 | `grep -rn "import net.factoryopen.core\|net.factoryopen.myfactoryai.manufacturing" myfactoryai-admin myfactoryai-ai myfactoryai-system ruoyi-* --include=*.java` | **0 条** |
| E2 | 是否用全限定名/配置引用（绕过 import） | `grep -rn "factoryopen\.core" --include=*.java --include=*.xml --include=*.yml`（排除遗留目录自身） | 仅 1 条：`MyFactoryAIApplication` 的 `scanBasePackages` |
| E3 | 遗留包内是否有横切关注点 | `grep -rln "@Aspect\|@ControllerAdvice\|Filter\|WebMvcConfigurer\|@PostConstruct\|CommandLineRunner\|@Scheduled" core/ manufacturing/` | **0 个文件** |

## 3. 方案对比

| | 方案 A：物理删除 | 方案 B：仅排除扫描 | 方案 C：拆独立模块 |
| --- | --- | --- | --- |
| 做法 | `git rm` 掉 D1–D3，改 `scanBasePackages` | 保留源码，加 `@ComponentScan(excludeFilters=…)` | 新建 `myfactoryai-legacy` 模块，`<optional>true</optional>` |
| Java 类不再装配 | ✅ | ✅ | ✅ |
| 210 个 XML 不再解析 | ✅ | ❌ **仍然解析** | ✅ |
| 仓库体积 / clone 速度 | ✅ 显著改善 | ❌ 不变 | ❌ 不变 |
| IDE 索引 / 新人误读 | ✅ 消失 | ❌ 仍存在 | ⚠️ 仍在仓库 |
| 改动量 | 中（删除 + 1 行） | 小（1 处注解） | 大（3 个 pom + 目录迁移） |
| 回滚成本 | 低（`git revert`） | 极低 | 中 |
| 风险 | 中（不可逆删除，靠 git 兜底） | 低 | 中 |
| **推荐** | **★ 正式方案** | 过渡 / 演示前急救 | 不推荐 |

**为什么推荐 A 而不是 B**：
方案 B 只阻止 Bean 装配，但 `mapperLocations: classpath*:mapper/**/*Mapper.xml` 仍会在启动时解析那 210 个 XML
（`SqlSessionFactoryBean` 在 `buildSqlSessionFactory()` 里逐个 parse）。也就是说 B 只拿到约一半的启动收益，
却额外引入一条需要长期维护的正则排除规则。既然 E1–E3 已证明零耦合，直接删更干净。

**为什么不用 C**：拆模块的唯一好处是"随时能装回来"。但 git history + tag 已经能做到这件事，C 的额外成本不值。

### Phase 1 · 先验证，不动代码（可选但推荐）

用**一次单独提交**证明"排除后确实没有隐藏耦合"，把风险与删除动作解耦。

1. 修改 `backend/myfactoryai-admin/src/main/java/net/factoryopen/myfactoryai/MyFactoryAIApplication.java`：

```java
// 改前
@SpringBootApplication(exclude = {DataSourceAutoConfiguration.class},
        scanBasePackages = {"net.factoryopen.myfactoryai","net.factoryopen.core","com.ruoyi","org.jeecg.modules.jmreport"})

// 改后：去掉 net.factoryopen.core，并把 manufacturing 子包排除
@SpringBootApplication(exclude = {DataSourceAutoConfiguration.class})
@ComponentScan(
        basePackages = {"net.factoryopen.myfactoryai", "com.ruoyi", "org.jeecg.modules.jmreport"},
        excludeFilters = @ComponentScan.Filter(
                type = FilterType.REGEX,
                pattern = "net\\.factoryopen\\.myfactoryai\\.manufacturing\\..*"))
```

> `@SpringBootApplication` 本身没有 `excludeFilters` 属性，所以必须去掉它的 `scanBasePackages`，
> 改用独立的 `@ComponentScan`，否则排除规则不生效。

2. 验证：

```bash

mvn -q -DskipTests package
```

3. 冒烟：启动后端，用 8 个演示账号各登录一次，跑一遍「登录 → 订单列表 → 订单详情 → 确认 → 建工单」。
   **全部通过则证明无隐藏耦合，可进入 Phase 2。**
   若出现 `NoSuchBeanDefinitionException`，说明漏掉了某条隐式依赖，回到 §2 重查并把该 bean 加入保留清单。

4. 提交：`chore: exclude legacy manufacturing packages from component scan`

### Phase 2 · 物理删除（核心动作）

> ⚠️ **Java 与 XML 必须同一次提交删除。**
> 原因：`mapper/ord/OrdSoMapper.xml` 里写的是 `<resultMap type="OrdSo">`，短别名由
> `typeAliasesPackage: net.factoryopen.**.domain` 解析。若先删 `OrdSo.java` 而留下 XML，
> `SqlSessionFactoryBean` 在启动时就会抛 `Could not resolve type alias 'OrdSo'` —— **应用起不来**。

```bash
cd /d/haiErp/haiERP

# D1 + D2：遗留 Java（1044 + 87 个文件）
git rm -r backend/myfactoryai-manufacturing/src/main/java/net/factoryopen/core
git rm -r backend/myfactoryai-manufacturing/src/main/java/net/factoryopen/myfactoryai/manufacturing

# D3：遗留 MyBatis XML（210 个文件）—— 必须与 D1/D2 同一提交
git rm -r backend/myfactoryai-manufacturing/src/main/resources/mapper

# D4（可选）：无用的测试控制器
git rm backend/myfactoryai-admin/src/main/java/net/factoryopen/myfactoryai/web/controller/tool/TestController.java
```

删除后 `myfactoryai-manufacturing` 模块只剩：

```
myfactoryai-manufacturing/src/main/
├── java/net/factoryopen/myfactoryai/erp/     ← 41 个文件，全是自研业务
│   ├── domain/   (12)
│   ├── mapper/   (14)
│   └── service/  (12)
└── resources/                                 ← 已空，可保留空目录或一并删除
```

**注意**：`mapperLocations` 通配符在匹配不到任何文件时不会报错，无需改配置。
`typeAliasesPackage` 用的是通配符 `net.factoryopen.**.domain`，同样安全。

### Phase 4 · 清理重量级无用依赖（独立 PR，可选）

删除遗留代码后，部分依赖随之失去用途，但**必须逐个验证**，不能一把梭：

| 依赖 | 位置 | 判断依据 | 风险 |
| --- | --- | --- | --- |
| `mssql-jdbc` 12.6.1 | `myfactoryai-admin/pom.xml` | 项目只用 MySQL；遗留代码里也未见 SQL Server 用法 | 低，可直接删 |
| `jimureport-spring-boot3-starter` | `myfactoryai-admin/pom.xml` | 启动类 `scanBasePackages` 仍含 `org.jeecg.modules.jmreport`，且 `SecurityConfig` 放行了 `/jmreport/**` | **中**：需先确认没用报表功能，并一并清理扫描包与放行规则 |

> 比删 16 万行业务代码对 jar 的影响大得多。**如果目标是瘦身，先做这一步。**

## 6. 风险表

| 风险 | 概率 | 影响 | 对策 |
| --- | --- | --- | --- |
| XML 与实体类分批删除 → 启动失败 | **高（若操作不慎）** | 应用起不来 | **强制同一次提交**；提交前跑 V1 + V6 |
| 前端某处有未发现的遗留接口调用 | 低 | 单个页面 404 | 全量 `grep` 已确认只用 `/erp` `/ai`；V9 + 手工点一遍导航兜底 |
| 某遗留类被 admin 以全限定名引用（非 import） | 极低 | 编译失败 | E2 已扫全限定名，仅启动类 1 处 |
| 遗留代码里有 `@Scheduled` 定时任务被删除 | 极低 | 无人察觉的功能丢失 | E3 已确认 0 个；且 `myfactoryai.scheduled: false` 本就关闭 |
| `git rm` 后误用 `git checkout -- .` 恢复出半套文件 | 低 | 编译失败 | 用 `git reset --hard before-legacy-cleanup` 整体回滚，不要手工挑选 |
| 团队其他分支仍在改遗留代码 | 中 | merge 冲突 / 代码复活 | 合并前在群里通知；PR 合并后立即 `git push` tag，其他人 rebase |

### 回滚（三种粒度）

```bash
# 1) 还没提交：撤销全部删除
git checkout -- .

# 2) 已提交，想整体回到清理前
git reset --hard before-legacy-cleanup

# 3) 已合并进 master，想撤销
git revert <commit_sha>          # 单个提交
git revert --no-commit a1b2c3d^..a1b2c3d   # 一段区间
```

因为 D1–D3 用的是 `git rm`（进版本库的操作），**文件内容始终在 git object 里**，不存在真正丢失的可能。

## 7. 不建议做的事

| ✗ 不要 | 原因 |
| --- | --- |
| 用资源管理器 / `rm -rf` 直接删目录 | 绕过 git 索引，回滚只能靠 reflog，且 D1–D3 与 XML 的批次关系无法保证 |
| 只删 Java 不删 XML | 见 §4 Phase 2，`Could not resolve type alias` 直接启动失败 |
| 顺手把 `myfactoryai-manufacturing` 整个模块删掉 | `myfactoryai-admin` 依赖它，自研 `erp` 包在里面 |
| 和「模块改名」「删第三方依赖」混在一个 PR | review 噪音大，出问题无法定位是哪一步引入的 |
| 删完 `sql/myfactoryai-free.sql` 就当清理完成 | 该文件已在 `.gitignore`，与本次任务无关 |
| 在 `application.yml` 里把 `mapperLocations` 改成空 | 没必要，通配符匹配 0 个文件是合法状态 |

### 命令踩坑备忘

- `ls a.java b.java` 在多参数下**只要有一个不存在就返回非 0**，用它做存在性判断会全量误报。
  校验接口存在请用 `find -name "X.java" | wc -l`。
- 未加 `clean` 直接 `package` 会把 `target/classes` 里的旧 `.class` 一并打进去。删除代码后**必须 `mvn clean`**。
