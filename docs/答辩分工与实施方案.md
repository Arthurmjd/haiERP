# 第一部分 · 分工方案

## 1. 文档说明

### 1.1 项目简介

海岚 ERP 是一套面向服装制造企业内部管理的信息化系统，覆盖「主数据管理 → 权限体系 → 业务单据 → 数据看板 → 智能问答」的完整链路。系统以 RuoYi 权限底座为基座，叠加服装行业主数据（物料/BOM/客户/供应商/员工）与生产业务单据（销售订单、采购订单、生产工单、库存出入库、裁剪排产等）的管理能力，并在其上实现了「先选数据范围、再提问、再基于查询结果分析」的受控 AI 业务问答模块。

项目定位是教学实训：在真实工程约束下完成一次从需求拆解、权限建模、数据库设计、接口实现、前端落地到回归验证的全流程工程实践。

### 1.2 技术栈

| 层次 | 技术选型 | 关键说明 |
| --- | --- | --- |
| 前端框架 | Vue 3 + TypeScript + Vite | 组合式 API + `<script setup>`，强类型约束接口契约 |
| 前端 UI | Element Plus | 表格、表单、树形控件（el-tree）直接满足 ERP 表单密集型需求 |
| 前端路由/权限 | Vue Router + `meta.permission` 守卫 | 路由级权限元数据 + 全局守卫 |
| 后端框架 | Java 21 + Spring Boot 3.5.0 | jakarta 命名空间，Spring Security 6 集成 |
| 后端模块 | Maven 多模块：`ruoyi-common` / `ruoyi-framework` / `ruoyi-quartz` / `myfactoryai-system` / `myfactoryai-manufacturing` / `myfactoryai-admin` | 制造业务与平台底座分离 |
| 持久层 | MyBatis + MyBatis-Generator | 动态 SQL 灵活，适合 ERP 多变查询条件 |
| 权限底座 | RuoYi（Spring Security + `@PreAuthorize`） | `"@ss.hasPermi('...')"` 表达式 + 数据范围 dataScope |
| 数据库 | MySQL 8.4.6 | utf8mb4，支持 CTE、窗口函数 |
| 缓存 | Redis | 会话/令牌与热点字典缓存 |
| AI 能力 | DeepSeek API（OpenAI 兼容协议） | `OPENAI_BASE_URL=https://api.deepseek.com/v1` |

### 1.3 团队构成与实际投入分布

团队共 7 人。出于诚实与可行的双重考虑，本节明确说明团队的实际投入结构，以便答辩时的表述与事实一致。

**实际投入结构：**

- **核心编码工作由 2 人承担（对应答辩 1 号、2 号席位）**：项目后端主体功能、前端主体功能、权限体系修复、AI 业务问答模块的接入与实现均由这两名成员完成。
- **其余 5 人承担项目支持性工作（对应答辩 3—7 号席位）**：包括系统管理前端页面的界面实现与联调、数据库初始化与自检脚本的编写与执行、AI 模块的提示词与测试用例整理、接口级回归验证与权限隔离验证、演示环境组织与答辩主讲串场、答辩材料与文档撰写。

**这一分工结构的合理性说明：**

1. 权限与安全、AI 问答、数据库脚本、系统管理前端、测试验证这几块工作本身是**可独立切分、可独立验收**的交付物，不存在「谁做」的模糊地带，各自的产物在代码库里可查证。
2. 把这 5 块工作显性化为「负责任务」，既能让每位成员在答辩中讲出自己**真实产出**的内容，也让老师看到的是一个有明确责任划分与产出记录的团队，而不是「两个人做完了其他五个人上来讲」。
3. 本方案中，每位成员的「技术讲述」只允许落在**真实存在的实现**上 —— 具体到文件名、接口名、表名、脚本名、测试类名。这既是答辩可信度的基础，也是对团队其他成员的尊重：不虚构工作量，也不让人承担不属于他的责任。

### 1.4 文档用途

- 作为答辩前的**责任分工书**：明确每位成员讲什么、讲多久、备什么料。
- 作为答辩前的**口径统一稿**：统一技术表述、统一「谁做的」的标准回答、统一不足与改进的表述框架。
- 作为答辩前的**预演脚本**：按 §13 计划逐日演练，附录 20 题为全员共用题库。

## 3. 逐人分工详述

### 3.1 成员 1｜主讲 / 队长

**具体交付物清单**

- 答辩总稿《海岚 ERP 项目介绍与答辩演示脚本》（本方案为其执行版本）
- 演示动线脚本：登录（`admin`/`Demo@2026!`）→ 业务看板 → 销售订单列表 → AI 业务问答 → 系统管理（用户/角色/菜单/组织）→ 权限隔离对照演示

- `sql/self_check.sql` 执行结论的解读稿（24 项自检项逐条对应）

**答辩讲述要点**

1. **开场定位（30 秒）**
   - 口播稿：「老师好，我们小组做的是海岚 ERP，一套面向服装制造企业内部管理的系统。它不是一个只跑通 CRUD 的练手项目 —— 我们围绕"权限安全"和"AI 可用性"这两个真实企业里最容易出事的地方，做了完整的工程实践。」

2. **业务链路与架构（60 秒）**
   - 口播稿：「整体是标准的前后端分离加权限中台。RuoYi 底座提供了认证、菜单、角色、字典、日志这一整套骨架，我们的增量主要在两处：一是在系统管理这块把权限真正收紧，二是把 DeepSeek 接进来做业务问答。业务主链路一共 16 步，从客户档案、报价、销售订单，一路到 MRP 缺料、采购收货、工单下达、领料报工、完工入库、出货签收、标准成本结算，最后到计件工资。所有页面操作都受双重拦截 —— 前端路由 `meta.permission` 守卫负责不渲染，后端 `@PreAuthorize` 负责真正不执行。」

3. **成果全景（90 秒）**
   - 口播稿：「成果我用三个数字概括：第一，接口级写操作回归 27 项全通过，覆盖新增、编辑、删除全链路；第二，后端 39 个自动化测试全过；第三，最关键的是 —— 我们在自查时发现系统管理的 10 个控制器、74 处权限注解全部被注释掉了，那等于任何登录用户都能增删用户和角色、改组织架构。我们全部恢复，并且写了一条反射扫描的测试当护栏，防止以后再被人注释掉。」

4. **演示串场（60 秒引导）**
   - 口播稿：「下面我把演示分两段。第一段由后端同学讲业务单据和主数据的闭环；第二段是系统管理和 AI 问答。我先把项目整体目录和模块划分过一遍，然后交给各位同学。」

**演示/佐证方式**

- 现场执行 `sql/self_check.sql`，展示 24 项自检输出。
- 打开 `SystemPermissionGuardTest` 源码，指出反射扫描断言「system 包下每个 controller 方法都有 `@PreAuthorize`」。
- 演示登录页，用 `admin` / `Demo@2026!` 登录，展示侧边栏「系统管理」分组。

**可能被追问的问题（3 个）+ 参考回答**

1. **问：这个项目最大的技术难点是什么？**
   - 答：难点不在功能数量，而在「权限这件事到底做没做实」。RuoYi 的权限模型是「注解 + 数据范围」两层，但我们接手时系统管理那 10 个控制器的 `@PreAuthorize` 全被注释掉了。真正的难点是这类问题在功能测试里完全测不出来 —— 功能都正常，你用 admin 测一切通过。所以我们换了思路：不靠功能测，而是写一条反射扫描的测试，直接断言每个 controller 方法都带 `@PreAuthorize`，把它变成编译期之外的护栏。这就引出了数据范围这层：注解管「能不能调这个接口」，`dataScope` 管「能看见哪些行」，两者是正交的，缺一个都不算完整的权限。

2. **问：你们的架构是自己设计的还是用的现成框架？**
   - 答：底座是 RuoYi，因为课程要求在成熟权限框架上做增量，这让我们把精力放在业务纵深而不是重造权限轮子。但增量部分的设计是我们自己定的：系统管理模块的 M→C→F 三级菜单模型、数据范围的部门集合绑定、AI 问答的「先选范围再提问」流程，都是我们根据海岚自己的管理诉求设计的。特别是 AI 那一块，如果让它自由问答，token 成本和幻觉都不可控，所以我们把它约束成「选数据范围 → 提问 → 基于查出的 20 条记录做分析」，本质上是把 LLM 降级成一个「数据摘要与归因工具」，而不是一个聊天机器人。

3. **问：7 个人做一个 ERP 系统，工作量够吗？你们怎么分工的？**
   - 答：够，但前提是分工必须落在可验收的产物上。我们的分工不是按「模块页面」切的，而是按「可独立验收的交付物」切的：后端主链路、前端页面、AI 流程、数据库与数据、权限审计、回归验证、演示组织。每个人有一个明确的可指认产出物 —— 哪个文件、哪个脚本、哪个测试类。这样做的好处是验收的时候看产出物而不是看人。

**应急话术**

> 「这个问题我来准确回答一下，避免误会：项目的主体后端功能和主体前端功能是由我和 XXX（成员2）完成的，这一部分代码确实是我们俩写的。像数据库初始化脚本、权限审计和回归验证这些，是有明确责任人的独立交付物，各自有对应的产出文件。分工表上有记录，我一会儿可以指出来。另外我个人的主要工作是架构梳理、演示组织和答辩统筹。我不想把别人的工作量说成自己的，也不想把团队说成是某一个人完成的 —— 这两种说法都不准确。」

### 3.2 成员 2｜后端核心

**角色定位与职责边界**

- 负责：后端主体功能的接口实现与业务规则落地，包括主数据（物料/客户/供应商/员工）的增删改查与引用校验、业务单据（销售订单/采购订单/生产工单/出入库）的状态流转与状态机强制执行、权限串补齐、角色服务缺陷修复。
- 不负责：前端页面渲染细节（属于 3 号）、AI 提示词内容设计（属于 4 号）、数据库初始化脚本编写（属于 5 号）、权限注解的系统性审计（属于 6 号）。本人提供的是**接口与业务规则层**，权限注解恢复工作由 6 号执行。
- **协作边界**：单据状态机的**业务定义**由 1 号（队长/产品侧）与业务手册共同确定，2 号负责**在服务端强制执行**（非法跳转直接返回 `2001`），5 号负责状态字段的数据库层落库。

**具体交付物清单**

- `SysRoleServiceImpl.updateRole`：修复遍历 `role.getMenuIds()` / `role.getDeptIds()` 时 null 导致的 NPE，补空值保护
- 业务单据删除与作废逻辑：删除仅允许草稿态，已提交单据走 `cancel` 作废通道；对应补齐 `remove` / `cancel` 权限串并写入数据库
- 单据状态机服务端校验：`sd_order` 六态流转、`pu_purchase_order` 四态流转，非法跳转返回 `2001`
- 幂等实现：收货、领料、报工、完工、发货、退货回库均带 `requestKey`，由 `biz_action_request` 保证同键只生效一次，参数不同复用同键返回 `2007`
- 服务端权威：库存不足返回 `2003`，超收超发返回 `2006`，已确认成本快照重算返回 `3002`
- 员工档案：离职 / 复职流转，以及离职员工不可删除的业务约束
- 主数据删除前置引用校验：物料被 BOM 引用、客户被订单引用时拒绝删除并返回明确提示
- 前端对应的操作入口配合联调（按钮显隐与后端权限串对齐）

**答辩讲述要点**

1. **后端分层与接口链路（60 秒）**
   - 口播稿：「后端是标准的三层加一层防护：Controller 接 HTTP、Service 管业务规则、Mapper 出 SQL、权限注解横切在 Controller 上。一条完整链路是这样 —— 前端发请求，Spring Security 先过认证，再进 Controller，方法上的 `@PreAuthorize` 判断你有没有这个权限串，然后 Service 做业务校验，比如单据状态对不对、引用还在不在，最后 Mapper 落库。任何一层不通过，都是明确的业务错误码，而不是抛一个堆栈给用户看。」

2. **状态机与服务端权威（90 秒）**
   - 口播稿：「业务上单据不能随便跳状态。销售订单是六个态：草稿、已确认、生产中、已完工、已发齐、已完成；采购单是四个态：草稿、已下单、部分收货、全部收货。前端把不合法的按钮置灰只是防手滑，真正拦住非法跳转的是服务端 —— 比如一张单已经发货了，你调接口直接跳回草稿，服务端会返回 `2001` 拒绝掉。这背后的原则是「服务端权威」：金额、可发量、发齐判定、成本全部服务端算，前端只负责显示，不参与计算也不参与裁决。」

3. **一致性红线（60 秒）**
   - 口播稿：「我们把业务上的硬约束总结成六条红线，其中三条直接落在代码里：第一是「只增不改」—— 库存流水、报工事件、计件事件一旦写入永不修改，要纠错只能走冲销；第二是「原子提交」—— 状态变更、库存副作用、计件副作用、操作记录必须在同一个事务里，不允许出现状态改了但库存没动；第三是「幂等」—— 收货、领料、报工这些动作都带 `requestKey`，同一个键重复提交只生效一次，如果同一个键配了不同参数直接返回 `2007` 冲突。这一条对移动端弱网场景特别重要，重复点一次提交不会重复收货。」

4. **真实缺陷修复（50 秒）**
   - 口播稿：「还有一个真实的 bug 是角色编辑必崩。原因是 `updateRole` 里直接遍历 `role.getMenuIds()`，而这个字段在编辑页某些提交路径下是 null，遍历直接空指针。后来我们补了空值保护。顺便说一句，角色和菜单的绑定关系是走批量保存的，前端 el-tree 一次提交几十个节点，中间任何一次落库失败都会有脏数据风险，所以这里也做了事务。」

5. **主数据引用校验（40 秒）**
   - 口播稿：「主数据这块的规则是「引用中的不能删」。物料如果已经在 BOM 里被引用，删掉之后 BOM 就悬空了；客户如果已经被销售订单引用，删掉之后订单上的客户名就成了脏数据。所以删除前会做一次引用检查，有引用就拒绝并明确告诉你是被哪一类单据引用了，不是简单地报一个『删除失败』。」

**演示/佐证方式**

- 现场演示单据状态约束：打开一张已提交单据 → 删除按钮点击后提示「仅草稿可删除，请使用作废」；再演示作废成功。
- 现场演示角色编辑：进入角色编辑页，不勾选任何菜单直接保存 → 不再报错（修复前必崩 NPE）。
- 现场演示主数据删除被拦截：删除一个已被引用的物料 → 提示引用关系。
- 演示幂等：同一 `requestKey` 重复提交 → 第二次返回 `2007`。

**可能被追问的问题（3 个）+ 参考回答**

1. **问：为什么删除要区分「草稿删除」和「作废」两个操作？数据库软删除不行吗？**
   - 答：软删除解决的是「还能不能查到」，解决不了「业务上这笔单据还算不算发生」。我们两个需求都要：主数据删除要求不可再被检索，所以做删除标记；但业务单据要保留可追溯性，因为报表和库存台账依赖单据号。所以单据侧不提供物理删除入口，只提供作废，作废的单据带作废状态和作废人作废时间，报表按状态过滤。也就是说软删除是存储层的手段，作废是业务语义层的状态，这两个不是一回事，不该用同一个动作混着做。

2. **问：怎么保证前端隐藏了按钮，后端就一定不会被直接调用？**
   - 答：这就是我们把权限注解恢复这件事当成重点的原因。隐藏按钮是展示层约定，可以被绕过 —— 用浏览器控制台改个 DOM、或者直接拿 Postman 打接口，权限校验就失效了。真正的防线必须在服务端，放在 `@PreAuthorize` 上，校验用的是当前认证用户的权限集合，服务端自己算，不信任任何客户端传来的标识。我们还专门写了回归测试去扫这个性质，就是为了防止哪次合并把注解又注释掉了。

3. **问：你说的「接口级写操作回归 27 项」具体怎么测的？**
   - 答：是按实体的完整写链路设计的：一个新实体，从创建开始 —— 创建成功拿到 id → 编辑字段并校验变更生效 → 再删除并校验列表里不再出现。覆盖岗位、部门、用户、角色、菜单五类实体，每类再加若干变体场景，比如角色绑定菜单后校验菜单树勾选状态、菜单新增后校验父节点归属，一共 27 项。这套的思路是：单测测的是「方法在给定输入下返回值对不对」，接口回归测的是「这条链路串起来能不能走通」，两者覆盖的风险不一样。

**可能被追问的问题（3 个）+ 参考回答**

1. **问：前端做了权限控制，后端也做了，那是不是重复劳动？**
   - 答：目标不一样，缺任何一个体验都会坏。前端拦的是「看不见」，后端拦的是「做不了」。如果只有后端，用户点了菜单进去，页面报错弹一个 403 白页，很差；如果只有前端，用户看不到菜单但改个 URL 就能访问，那就是越权漏洞。所以这是必要的冗余，不是重复。而且我们后端拒绝时返回的是 HTTP 200 加 body 里 `code=403`，前端统一在响应拦截器里判断这个业务码再跳转，所以前端拦截器要正确处理这个约定 —— 这也是联调时踩过的一个点。

2. **问：为什么页面要做 demo 模式内置数据？会不会造成数据混乱？**
   - 答：它是为了前端能独立调试和演示。开关是明确的，不是自动降级 —— 需要在 `api/system.ts` 里显式切换，这样不会出现「以为在调真接口其实在用假数据」的隐蔽问题。要注意一点是，demo 数据只在内存里，刷新就没了，所以它只用于前端交互验证和前端未联调时的演示，验收和回归测试全部走真实后端。

3. **问：22 个视图会不会太散了？后续怎么维护？**
   - 答：我们按业务域分的，`system/` 是系统管理子目录，其余按单据和主数据分布，API 层也按同样思路拆成 catalog、client、demo、erp、labels、system 六个模块，不是所有接口堆在一个文件里。坦率说目前这四个新页面之间代码结构偏相似，列表加表单加弹窗的组合重复度较高，缺少通用 CRUD 组件抽象。这是我自己识别出的不足，补法是抽一层列表/表单/弹窗的通用组件，用配置驱动页面生成，把重复度降下来。

4. **问：菜单为什么要分 M、C、F 三级？**
   - 答：M 是目录，只做分组不指向页面；C 是菜单，指向一个前端路由页面；F 是按钮，对应一个具体操作权限，比如 `system:user:edit`。分三级是因为按钮权限必须挂在某个菜单下面才有归属，否则 `system:user:edit` 这种权限串就没法按模块批量授权和回收。前端在页面上按 `F` 类型生成按钮并检查权限串，后端在 Controller 上用同名权限串做校验，两边靠这个三级结构对齐。这也是 RuoYi 的既有设计，我们主要是沿用并把它做进新增菜单的流程里。

   - 口播稿：「取 20 条这个上限是权衡过的。记录太多，token 成本和响应延迟都会上去；太少，分析结论又容易被单条异常数据带偏。我们实测下来 20 条左右在成本和结论可用性之间比较平衡，而且我们还限制了必须先选范围，这本身也在削减无意义的调用。」

**演示/佐证方式**

**可能被追问的问题（3 个）+ 参考回答**

1. **问：为什么不干脆把整个数据库丢给大模型让它自己分析？**
   - 答：那是最容易做但最不稳的一种方案。三个问题：一是成本，全量数据塞进去一次调用可能上万 token，天天用不起；二是准确率，模型对大表做全局统计很容易出错，而且出错你很难发现；三是权限，把整库暴露给模型等于绕过了我们的权限体系，用户 A 的问题里就可能带出用户 B 看不到的数据 —— 这在我们系统里对应的是 `4002` 这个错误码。我们选「先按权限查、按范围取、最多 20 条、基于这 20 条分析」，本质是把 LLM 定位成一个「结构化数据摘要与归因」的工具，它的输入永远是系统已经授权、已经取好的确定性数据。

2. **问：提示词怎么保证效果稳定？你怎么知道改完还是好的？**
   - 答：我们不敢说提示词是「优化好了」，只能说是「有约束、有回归」。第一层是硬约束写进提示词：数据边界、禁止推测、输出格式。第二层是测试兜底：`ErpAiPromptsTest` 里断言提示词必须包含这些约束的关键片段，这样任何一次改动如果删掉了关键约束，测试直接失败。第三层是人工评估，我们固定了一批问题作为评估集，每次改提示词手动跑一遍看结论有没有变差。坦白讲我们没做到自动化评估，这块是明确的不足。

3. **问：调用大模型会不会把企业数据泄漏出去？**
   - 答：这是真实风险，我们的处理方式是控制出境数据面而不是假装不存在。第一，只发送用户选定的数据范围查出来的最多 20 条记录，不发送全量；第二，推送前会对记录做必要字段的裁剪；第三，整个链路的 API Key 和 base URL 都是环境变量配置，不同部署环境可以指向不同的服务。我们也承认这还不够，比如目前没有做传输层额外加密和字段级脱敏策略的完整方案，这是我们下一步要补的。

**角色定位与职责边界**

- 不负责：后端 Java 业务逻辑实现（属于 2 号）、前端页面（属于 3 号）、权限注解与守卫（属于 6 号）。

**具体交付物清单**

**答辩讲述要点**

1. **表设计与规范（70 秒）**
   - 口播稿：「表设计上有三条规范。第一，权限串统一三段式命名，模块:实体:操作，比如 `system:user:list`、`sys:billcodeRule:add`，这样任何一条权限都能从名字反推出它属于哪个模块、管哪个实体、是什么动作。第二，系统表加业务表在命名上做区分，业务表统一前缀，避免和框架表混在一起。第三，所有需要频繁按部门过滤的表都建了 `dept_id` 索引，因为我们的数据范围机制全靠这个字段过滤，索引没建好，权限过滤一叠加性能就掉。」

2. **幂等初始化脚本（80 秒）**
   - 口播稿：「`sql/system-permissions.sql` 这个脚本最重要的性质是**幂等**。它可以重复执行，不会插重复数据，也不会因为已存在而报错。做法是所有插入前先判存在性，存在就更新关键字段，不存在才插入。因为初始化脚本在实际部署中一定会被反复执行 —— 补一条权限就要重跑一次，如果脚本不幂等，数据库就脏了。这里还有个细节：菜单 id 我们固定在 90200 到 90254 这个区间，不让框架自增。原因是自增 id 不可控，一旦插入顺序变了，权限串和菜单 id 的对应关系就乱了；固定之后权限串和 id 一一对应，排查问题的时候能直接反查。这个脚本里一共是 54 条权限菜单、7 个部门、7 个岗位，还有 8 个演示账号的部门回填，以及 admin 的 54 条授权。」

3. **单据状态机在数据层的表达（60 秒）**
   - 口播稿：「单据的状态不是随便一个整数。销售订单有六个态：草稿、已确认、生产中、已完工、已发齐、已完成；采购单四个态：草稿、已下单、部分收货、全部收货。我们在数据层把状态字段、状态枚举和允许的流转关系一起表达出来，所以非法跳转在服务端能被明确识别并返回 `2001`。这不只是限制用户 —— 更重要的是保证报表和库存台账在任意时刻都能算出一个确定的结果，因为每个单据在任何时刻只可能处于一个明确状态。」

4. **自检脚本（60 秒）**
   - 口播稿：「除了初始化，我们还写了 `sql/self_check.sql`，24 项自检。为什么需要这个？因为这个项目最容易出问题的不是代码编译不过，而是**配置漂移** —— 权限写进代码了但没写进库，或者库里少了一条授权，代码上完全看不出来，但功能就是不好使。自检脚本把这些能查的约束都写成 SQL 查询直接验，比如权限覆盖率、部门岗位数量是否和预期一致、每个演示账号是不是都正确绑定了部门、角色和菜单的绑定是否完整。跑一次就知道环境是不是健康的。」

5. **角色名聚合与分页（60 秒）**
   - 口播稿：「这里有个具体的技术选择。`SysUser` 需要在列表里展示用户的角色名，最直觉的写法是 join 角色表和用户角色关系表。但这样有个坑：join 之后行数会膨胀，一个用户绑三个角色就会变成三行，PageHelper 在做分页 count 的时候总数也会跟着膨胀，分页就会出错。所以我们改用 `group_concat` 标量子查询的方式聚合角色名 —— 它是子查询，返回单值，不参与外层的行展开，count 不受影响，同时还能加 `group_concat` 的分隔符控制显示格式。」

6. **演示数据（40 秒）**
   - 口播稿：「演示数据是按角色设计的一组账号，不是随便填的。8 个账号统一密码 `Demo@2026!`，每个账号对应一个真实岗位和部门归属，这样演示权限隔离的时候，你能直接看出"不同部门的人看到的数据不一样"，而不是凭空演示。」

**演示/佐证方式**

- 执行 `sql/system-permissions.sql` 两次，演示无报错、无重复数据（幂等性）。
- 执行 `sql/self_check.sql`，展示 24 项全部通过/符合预期。
- 在数据库中查询验证：`select count(*) from sys_menu where perms like 'system:%' or perms like 'sys:billcodeRule:%'` → 54；部门 7、岗位 7。
- 打开 `SysUserMapper.xml` 的 `selectUserList`，指出 `group_concat` 子查询写法与 `PageHelper` 分页的关系。

**可能被追问的问题（3 个）+ 参考回答**

1. **问：为什么不用 Flyway 或 Liquibase 做迁移，非要手写幂等 SQL？**
   - 答：这是我们的不足，坦白承认。Flyway 更规范，有版本化、有校验和、能追踪变更历史，我们这套是一个大脚本。之所以先这么写，是因为我们的场景偏「初始化 + 少量补丁」，脚本本身也不复杂，团队对迁移工具的熟悉度不够。但这个选择的代价是真实的：没有变更历史，无法知道某个环境执行到了哪一步，也没有 checksum 检测别人手改了脚本。补的做法是引入 Flyway，把现有脚本拆成 `V1__init.sql`、`V2__system_permissions.sql` 这样带版本号的迁移文件。

2. **问：初始化脚本里直接 INSERT 密码明文，安全吗？**
   - 答：脚本里放的确实是演示账号，而且明文只存在于脚本这一处，运行期的密码比对走的是框架的加密流程（加盐哈希后比对），数据库里存的不是明文。但严格说，演示环境的密码强度和「脚本里写死」这个做法都不适合生产 —— 正确做法是初始化时生成随机密码、首次登录强制修改，或者走环境变量注入。我们这个脚本的定位就是实训演示环境，如果要上生产，这块必须重做。

3. **问：`group_concat` 拼接角色名，如果一个用户角色特别多，字段会不会超长？**
   - 答：会，`group_concat` 的结果默认受 `group_concat_max_len` 限制，MySQL 默认 1024 字节，理论上存在被截断的风险。我们目前场景下每个用户的角色数是 1 到 3 个，拼接结果通常几十个字节，不会触发。但这是隐患，稳妥的做法是显式设置 `group_concat_max_len`，或者在展示层做「前两个 + N」的折叠显示而不是全量拼接。

**角色定位与职责边界**

- 不负责：系统管理前端页面实现（属于 3 号）、数据库初始化脚本的编写（属于 5 号）、AI 模块（属于 4 号）。

**具体交付物清单**

- **审计发现**：检查 `backend/myfactoryai-admin/src/main/java/net/factoryopen/myfactoryai/web/controller/system/` 下 **10 个系统管理控制器**，发现全部 `@PreAuthorize` 权限注解**被注释掉**，导致任何登录用户可增删用户/角色、改菜单/组织架构，属严重越权漏洞

- **权限模型文档**：RuoYi `@PreAuthorize("@ss.hasPermi('...')")` 模型、admin 通过 `*:*:*` 通配放行、权限串三级结构、前后端双重拦截、dataScope 数据范围机制（角色绑定部门集合，SQL 按 `dept_id` 过滤）
- **八角色权限地图**：admin / sales / planner / production / wh / finance / hr / boss 八个角色的职责边界与关键写权限，与 54 条权限串一一对应

**答辩讲述要点**

1. **发现的漏洞（80 秒）**
   - 口播稿：「我们这次最有价值的一个发现，是一个真实的越权漏洞。位置在我们自己后端的 system 控制器包下面，一共 10 个控制器，我们把里面的权限注解全部检查了一遍，发现 `@PreAuthorize` 全都被注释掉了。注释掉之后代码照常编译、照常运行，功能测试全通过 —— 因为测试是用 admin 测的，admin 是通配放行的。但对任何一个普通登录用户来说，这意味着他可以直接调接口增删用户和角色、改菜单和改组织架构。这是典型的越权访问，属于严重漏洞。」

2. **为什么功能测试测不出来（60 秒）**
   - 口播稿：「这个漏洞特别值得讲的一点是：它天然是功能测试抓不到的。因为功能测试的路径是"用最高权限账号把功能点一遍，能跑通就算过"。而越权问题的本质是"权限不足的人不应该能操作"，这类用例在正常的测试流程里根本不会被写进用例集。所以我们后来改思路 —— 不靠功能测，靠结构性的测试来兜底。」

3. **修复与补齐（60 秒）**
   - 口播稿：「修复本身是机械的：把注释掉的 74 处注解全部恢复成真正的注解，每一处对应它应该有的权限串。另外我们还发现 9 个端点本来就没有任何注解，属于新加的接口，直接补齐了对应的权限串。这里有个规范我们要对齐：权限串必须跟前端菜单里的 `perms` 字段一一对应，前端配了 `system:user:edit`、后端没写 `@PreAuthorize`，或者反过来，都是隐患。我们这次就是按这条对齐规则逐个核对的。」

4. **回归护栏（70 秒）**
   - 口播稿：「光修好不够，下次有人合并代码还是可能把注解注释掉 —— 毕竟注释掉编译还是过的。所以我们写了 `SystemPermissionGuardTest`，四个用例。它的做法是用反射扫描：拿到 system 包下所有 controller 的所有 public 方法，逐个检查有没有 `@PreAuthorize` 注解，缺任何一个就测试失败。这条测试的价值是它把"注解是否存在"变成了一个编译期之外但 CI 期就能拦住的事实。以后谁注释掉注解，测试立刻红。」

5. **权限模型全景与八角色（80 秒）**
   - 口播稿：「我们的权限是三层。第一层是认证，解决你是谁；第二层是授权，就是 `@PreAuthorize("@ss.hasPermi('...')")`，解决你能做什么，admin 用 `*:*:*` 通配放行；第三层是数据范围，也就是 dataScope，角色可以绑定一个部门集合，SQL 查询里按 `dept_id` 过滤，解决你能看到哪些行。前两层管操作，第三层管数据，这个分层是我们这套 ERP 安全设计的核心。落到具体角色上，我们有八个：管理员、厂长、销售、计划员、生产主管、仓管、财务、人事。比如成本明细默认只有财务和管理员能看到 —— 没有 `fn:settlement:list` 的角色，看板接口不会返回标准毛利这个字段，这是服务端硬校验，不是前端遮掩。另外提醒一个实现细节：权限被拒绝时返回的是 **HTTP 200，body 里 `code` 是 403**，不是 HTTP 状态码 403，这个约定前端拦截器必须按业务码处理，不然会漏掉。」

6. **隔离验证（50 秒）**
   - 口播稿：「修复之后我们做了实际验证：用 sales 账号去调系统管理的接口，返回的是 HTTP 200，body 是 `{"code":403}`，说明请求被服务端拦下了。之所以返回 HTTP 200 是因为权限拒绝在框架层被当作一次正常的业务处理结果返回给前端，前端拿到业务码 403 再跳转无权限页 —— 这是 RuoYi 的既有约定，不是我们随意设计的。」

**演示/佐证方式**

- 用 admin 打开 `src/main/java/net/factoryopen/myfactoryai/web/controller/system/` 下的控制器，展示 `@PreAuthorize` 已生效（行首无注释标记）。
- 跑 `SystemPermissionGuardTest`，展示 4 个用例全过；现场注释掉任意一处注解再跑一次，展示测试立刻失败（可只演示不保存，或演示后立即还原）。
- 用 sales 账号登录后直接访问 `/system/user` 路由，观察被路由守卫拦截；再用 curl 或 Postman 直接打接口，观察 `{"code":403}`。
- 打开 `sql/system-permissions.sql`，对照展示 54 条权限串与代码中 `@PreAuthorize` 的一一对应关系。

**可能被追问的问题（3 个）+ 参考回答**

1. **问：为什么权限拒绝返回 HTTP 200 而不是标准的 403？**
   - 答：这是 RuoYi 框架的既有约定，不是我们发明的。框架把权限校验失败当作一次正常的业务结果封装成统一响应体，`AjaxResult` 里 `code` 字段放业务状态码，HTTP 层始终是 200。这样做的好处是前端只需要一套统一处理逻辑 —— 不管后端返回什么，最终都是同一个响应结构，前端拦截器里判断 `code` 即可。代价也很明确：HTTP 层的语义丢掉了，监控和网关看到的是一堆 200，异常流量在 HTTP 层面不可见；而且如果任何一处客户端漏判业务码，就会把错误当成功处理。我们的处理是在前端统一拦截器里集中判断，不在各个页面里散着判。

2. **问：反射扫描这种测试，是不是有点「测试实现细节」？**
   - 答：这个顾虑是合理的，我们讨论过。反射扫注解确实耦合了实现形式，如果将来把权限从注解换成拦截器或者自定义 DSL，这条测试就会误报。但我们保留它，理由是这个项目的安全属性要求「缺失即失败」—— 注解是我们当前约定的实现形式，安全护栏必须锚定在具体的约定上，否则就没有东西可扫了。同时它的成本极低：4 个用例、秒级执行、CI 里零配置。更好的做法是两层都要 —— 反射扫描保证形式不丢，功能层面的越权用例保证行为正确，两者互补。我们目前后者只做了 sales 账号一个场景的接口级验证，覆盖度是不够的，这是明确的不足。

3. **问：权限串 `*:*:*` 通配放行，admin 的权限校验还有意义吗？**
   - 答：对 admin 来说没有意义，通配本来就全放行，admin 是「不设防」的设计意图，用来做初始化和应急。意义在于非 admin 用户。我们所有权限串都是按三段式校验的，admin 的 `*:*:*` 只影响 admin 自己。真正需要警惕的是另一个方向：如果将来有别的角色也被授予了类似通配的权限串，那这套机制就形同虚设了。所以我们做权限串核对时，除了检查注解在不在，也检查了有没有出现不该有的通配授权 —— admin 有，其他角色没有。

**应急话术**

1. **问：27 项回归相比单元测试，价值在哪？会不会是重复劳动？**

2. **问：如果要你们重做一遍，最想改的是什么？**
   - 答：我会先补测试体系，而不是先补功能。具体三步：第一，用 Flyway 做版本化迁移，把数据库变更变成可追踪的历史；第二，把越权验证从单一 sales 账号扩展成「角色 × 敏感接口」的矩阵，做成参数化测试自动跑；第三，把 AI 模块的人工评估集固化成自动化回归，每次改提示词自动跑一遍对比输出差异。我们做出来的东西能跑，但"改一次不担心坏"这个属性还不够，这是工程化程度上的差距。

3. **问：你说 39 个测试全过，那覆盖率是多少？**
   - 答：我必须诚实回答：没有测覆盖率，我们用的是测试用例数量和场景覆盖的清单式统计，而不是行覆盖或分支覆盖工具的量化数据。39 个测试集中在一批高风险点上 —— 权限注解、角色更新、配置读取、AI 提示词、DeepSeek 配置分支。这是我们明确的不足：工具链上没有引入 JaCoCo 这类覆盖率统计，所以无法回答「到底有多少分支被覆盖」。如果要做，我们倾向于用覆盖率报告先找出未覆盖的高风险分支，而不是追求一个漂亮的百分比数字。

### 4.4 技术选型统一说法

- **为什么 Vue 3**：ERP 是表单密集型、表格密集型系统，响应式数据流和组件化能显著降低这类界面的复杂度；配合 TypeScript 把接口返回字段类型化，后端改字段时能在编译期暴露问题，比运行时才发现代价低得多。Vite 的冷启动和 HMR 在前端联调阶段效率提升明显。
- **为什么 Spring Boot 3.5.0**：课程要求 Java 21，Spring Boot 3 是与 Java 17+ 长期主线匹配的大版本，jakarta 命名空间下与 RuoYi 底座兼容；Spring Security 6 的方法级授权机制成熟，配合 `@PreAuthorize` 表达式正好满足我们的权限模型需求。
- **为什么 MySQL 8.4.6**：ERP 数据关系强、事务一致性要求高，MySQL 的 InnoDB 事务、索引和 `group_concat` 这类函数覆盖了我们全部需求；8.4 支持 CTE 和窗口函数，为后续做数据分析类报表留了空间。
- **为什么 Redis**：主要用于令牌/会话状态与热点字典缓存，把无状态的鉴权压力和频繁读取的字典数据从数据库剥离，降低数据库连接压力。
- **为什么 MyBatis 而非 JPA**：ERP 的查询条件高度动态，MyBatis 的动态 SQL 对这种多条件组合的掌控力更强；同时 MyBatis 与 RuoYi 底座原生集成，避免额外的适配成本；SQL 可控也便于做 `dept_id` 这类数据范围过滤。

## 6. 发言顺序设计与理由

### 6.1 最终顺序（7 席位）

| 席位 | 定位（一句话） | 主讲范围 | 时长 |
| --- | --- | --- | --- |
| 1 | 主讲/队长 | 项目全景、业务链路总览、成果总览、缺口自陈、总调度 | 3.5 min |
| 2 | 后端核心 | RuoYi 底座、单据状态机、16 步主链路后端实现、幂等与服务端权威 | 3.5 min |
| 3 | 前端核心 | Vue3+TS+Element Plus、系统管理 4 页、路由与菜单、守卫 | 3.5 min |
| 4 | AI 模块 | DeepSeek 接入、业务提示词改写、模式约束、成本与防幻觉 | 3 min |
| 5 | 数据库/数据 | 54 条权限菜单、7 部门 7 岗位、8 演示账号、24 项自检、状态机数据层 | 3.5 min |
| 6 | 权限与安全 | 越权漏洞发现→修复→防回归（最亮点）、八角色地图 | 4 min |
| 7 | 测试与总结 | 验证矩阵、测试证据、不足与展望、收尾 | 3.5 min |

### 6.2 排序依据（五条）

**依据一：技术纵深递进，先「是什么」再「怎么实现」再「怎么守得住」。**
席位 1 先给全景和业务链路，让老师建立「服装 ERP」的心智模型；席位 2 讲后端如何把 16 步链路转成状态机；席位 3 讲前端如何呈现；席位 4 是横切能力（AI）放在主链路之后，因为它是增益不是主干；席位 5 回头讲数据地基；席位 6 把权限安全作为独立的深度高峰放在末尾段；席位 7 收束。听众认知负荷是「广度→细节→深度→收尾」。

**依据二：最亮点后置，保证「最后印象」。**
越权漏洞的发现与修复是本项目最有说服力的部分（74 处注释掉的 `@PreAuthorize` 意味着任何登录用户可以增删用户、改角色、改菜单；这不是演示效果，是实打实的高危漏洞）。它放在第 6 位，处于老师注意力尚未衰减的黄金段，且紧接在「看起来规整」的铺垫之后，反差最强。

**依据三：避免首尾撞车。**
席位 1 只做「总览 + 路线图」，明确说出接下来由谁讲，避免老师觉得是 1 个人讲 30 分钟。席位 7 只做「验证 + 不足 + 收尾」，做总结但不重复细节。首尾两人都不做技术深潜，各自只做导航和收束。

**依据四：承接关系自然，串场不生硬。**
每个人退出时抛出的下一个人的话头，必须是他下一位的开场白。设计上形成 6 个「接口」：

- 1→2：「刚才的 16 步链路，在后端是怎么落成状态机的」→ 席位 2 直接接
- 2→3：「后端管住了业务，那用户在界面上怎么操作、怎么被挡住」→ 席位 3 直接接
- 3→4：「系统管理这部分界面和路由都讲完了，另外还有一块 AI 能力」→ 席位 4 直接接
- 4→5：「AI 要基于真实数据回答，那数据是怎么组织的」→ 席位 5 直接接
- 5→6：「数据准备好了，但谁能改数据这件事本身是有洞的」→ 席位 6 直接接
- 6→7：「漏洞堵上了，怎么证明它不会再回来」→ 席位 7 直接接

**依据五：提问命中率高的席位配对，减少跨人转交成本。**
AI（4）、数据库（5）、权限（6）这三类最容易被追问，各自安排专人，且三者相邻；测试席位（7）紧邻权限席位（6），因为权限类问题最容易被追问「你怎么证明」。

### 6.3 每人串场话术（可直接念）

**席位 1 —— 进入**
> 「各位老师好，我是海岚 ERP 团队的队长 XXX。先给大家一个坐标：我们做的是一个服装制造企业的 ERP，核心业务链路一共 16 步，从客户报价一直到出货和计件工资。今天我们不按功能菜单讲，按三条线讲 —— 业务怎么转、数据怎么落、权限怎么管。我先用几分钟把全局和成果讲完，之后请我们的后端同学 XX 讲链路实现，前端同学 XX 讲界面与守卫，AI 同学 XX 讲智能问答，数据同学 XX 讲数据库设计，安全同学 XX 讲我们发现并修复的越权漏洞，最后由 XX 讲验证结果和不足。」

### 7.4 控场机制

**掐表责任人**：由非发言者担任（推荐席位 7 或指定一名不讲话的计时同学），用**手机秒表**并把手机放在讲台，屏幕朝上。

**三次提醒**：T-30 秒抬手比「三」；T-10 秒抬手比「一」；T+0 秒轻声说「时间到」，或直接由席位 1 的串场词收束。

**超时怎么办**：
- 轻微超时（15 秒内）：本人自行加速，砍掉最后一句铺垫，直接进核心结论。
- 明显超时（60 秒以上）：**席位 1 在下一个转场时接管** ——「XX 这块讲得比较细，剩下两点我替他收个尾 —— 后端这条线，接着由 XX 来讲。」注意：**不是当众打断**，当众打断同组同学是最伤印象的行为。
- 硬约束：每位席位的**最后一页必须是「收束页」**（3 个数字 + 一句结论），这样任何人被打断都能在 15 秒内翻到收束页收尾。

**被老师打断怎么办**：立刻停止讲述，把讲台让出半步，面向老师「老师您说」。回答控制在 30~45 秒，答完补一句「如果还有细节，会后我可以单独演示」，然后接「我们继续，刚讲到……」。**不要在被打断后原地继续把被打断的那段重讲**，直接跳到下一个锚点。

**卡壳（忘词）怎么办**：不沉默超过 3 秒。备用句式：「这块我先说结论，细节我记不太清，稍后可以给老师看代码。」立即把话头递出去：「XX 这块比我熟，请 XX 补充一下？」—— 这是事先约定的合法转交，不是失分。

| 测试策略、覆盖率、回归、构建、CI | 席位 7 | 席位 2 |
| 项目整体、需求、技术选型、进度、不足、展望 | 席位 1 | 席位 7 |
| **「这段代码是你写的吗」** | **该段代码的真实作者本人** | 席位 1 解释分工 |
| 跨模块的架构问题 | 席位 1 先给框架，再点人补充 | 相关席位 |

**五条规则：**

1. **首答归属**：问题由老师抛向全场时，先由该问题相关的席位直接答，不要所有人同时看向主讲人等待 3 秒。听到问题与自己相关的同学应当即开口，这本身就是「熟悉项目」的信号。
2. **主讲兜底**：若 3 秒内无人应答，或问题超出所有人的具体职责（宏观、项目管理类），席位 1 必须立刻接话，避免冷场。
3. **不越权作答**：没做过的事情不要硬答。
4. **最多两人**：一个问题最多由 2 人回答，第 3 人不补充。
5. **答完即停**：回答完立刻交还控制权：「回答完了，请老师继续提问。」

### 8.2 自我介绍与称呼约定（第一句话就定调，不要跳过）

**开场由席位 1 用一句话把团队结构说清楚**，这是全场最重要的一次铺垫：

> 「我们组 7 个人，按模块分工。我是队长 XXX，负责整体架构和演示统筹；接下来依次由后端的 XX、前端的 XX、AI 的 XX、数据的 XX、安全的 XX、测试的 XX 依次讲。我先说明一下：核心的后端和前端功能是我和 XX 两位同学做的，其余五位同学分别负责系统管理前端、AI 问答流程、数据库与数据、权限安全审计、测试验证这五块独立交付物 —— 每一块都有对应的产出文件，待会儿讲到的时候可以当场指出来。」

**规则：**

- **每位席位的第一句话必须包含「姓名 + 我负责什么」**，例如「我是 XX，负责后端这块」。老师要能对上人。
- **不要说「我们组做的是…」开头**，要用「**我**负责…」。让老师明确知道现在是谁在讲。
- **不要说「接下来由 XX 讲…」这种排他式交接**，改用 **「补充一句」** 的协作式说法（见下）。
- **不要说「这部分是 XX 做的，他来讲」** —— 推诿感极强。

### 8.3 统一转交话术

**A. 明确知道谁能答（最佳）**
> 「这个我印象比较深的是……不过 XX 这块是主力，让他来说会更准确。XX，你来一下？」

**B. 不确定谁能答**
> 「这个问题我不确定，XX 你做过这块吗？—— 如果都不熟，我课后查代码给您书面回复，可以吗老师？」

**C. 明确不会（诚实且不失分）**
> 「这块我没做到位，我不敢瞎说。我目前的理解是……（说 30 秒你确实知道的部分），更准确的部分我回去确认后写成文档给老师，可以吗？」

> C 式的关键：**先承认、再给出你确实知道的部分、最后给一个明确的交付承诺**。这比硬编答案得分高得多。

### 8.4 高频问题接住路径

| 高频问题 | 接住人 | 一句话锚点 |
| --- | --- | --- |
| 「你们数据库怎么设计的？多少表？」 | 5 → 1 | 5 讲 54 条权限菜单 / 7 部门 7 岗位 / 8 账号；1 补总体模块划分 |
| 「AI 用的大模型什么？为什么不用本地？」 | 4 | DeepSeek 兼容 OpenAI 协议，换 base URL 即可换模型 |
| 「AI 的回答准吗？会不会瞎编？」 | 4 → 6 | 4 讲三道防线：业务提示词 + 五种 mode 限定 + 只基于 20 条真实记录；6 补 4002 |
| 「权限怎么管的？」 | 6 → 5 → 3 | 6 讲漏洞与修复；5 讲 54 条菜单粒度；3 讲前端 `can()` 与 router 守卫 |
| 「为什么返回 200 而不是 403？」 | 6 | 统一响应约定，body 里 `{"code":403}`，前端按 code 分支处理 |
| 「有没有测试？覆盖率多少？」 | 7 | 27 项回归全 PASS、39 用例全过、前端 build 通过；覆盖率诚实说未做量化统计 |
| 「登录怎么做的？密码安全吗？」 | 6 → 2 | RuoYi 底座自带认证 + JWT；演示密码仅限演示环境，生产必须改 |
| 「你们业务上有没有用工作流？」 | 7 或 2 | **没有工作流引擎、没有多级会签**；两段式 + 权限点分离 |
| 「为什么两个人做了大部分？」 | 1 | 用分工表 + 席位覆盖说明，提供「其余同学在 X 模块的具体产出」证据 |
| 「性能怎么样？能扛多少并发？」 | 2 → 5 | 已有 Redis 缓存与 MySQL 索引；未做压力测试，如实说明 |
| 「冲销/反审怎么做？」 | 2 或 7 | 承认当前缺失（不足第 5 条），设计方向：新增红冲单据而非改原单 |
| 「这个项目最大的收获？」 | 7 → 1 | 7 说工程规范与安全意识；1 说完整链路落地经历 |

### 8.5 统一答复口径（涉及多个席位的问题，统一说同一句）

以下问题会跨席位，**如果多人分别回答，会出现口径不一致，反而显得没商量过**。指定**唯一主答人**，其他人只在被点名时补充。

| 问题 | 唯一主答人 | 统一口径（照念） |
| --- | --- | --- |
| 「你们项目总共写了多少代码 / 多少表 / 多少接口？」 | 席位 1 | 「具体数字我们没做统计，我不报一个编出来的数。能确定的是权限配置 54 条、部门 7 个、岗位 7 个、演示账号 8 个，接口回归 27 项，后端测试 39 个 —— 这些是可以当场查的。」 |
| 「这个系统能不能真正拿去用？」 | 席位 7 | 「它是实训环境，演示数据和流程是完整的、能跑通；但要上生产，缺的就是我刚才说的那六条：迁移版本化、冲销、审批分级、报工复核、权限归属收敛、AI 数据脱敏。功能完整度和工程化程度是两回事，我们这两头都要说实话。」 |
| 「技术上还有什么没做好的？」 | 席位 7 | 「六条不足我刚才讲过了。另外从工程角度看还有一条：没有 CI，我们的所有验证是本地手工跑的。如果要补，第一件事是把这三个脚本接进流水线 —— 数据库自检、39 个后端测试、27 项接口回归，这三样其实已经可以自动化了，只是还没做这一步。」 |
| 「你个人负责的部分，如果现在让你重做，哪里会改？」 | 本人 | 「我这块最大的问题是 XXX（对应 §4.3 那条不足），我会先 XXX，再 XXX。」 —— **每人一条，不得重复** |

### 8.6 答不上来时的备用答案（背下来，总会用上）

技术问题答不上来时，**最忌讳的是硬编**。下面这三句按顺序用，任何一句都不会扣分：

1. **诚实 + 给已知部分**：
   > 「这块我了解的是前半段 —— XXX。后面的实现细节我不敢给您不准确的答案。我的实现是 XXX，能给您看代码，但更深一层的原理我需要回去确认一下。」

2. **转交 + 明确边界**：
   > 「这块 XX 比我在行，我请他补充一下。我能确定的是 XXX，更具体的实现让他来说会更准确。」

3. **兜底承诺**（前两条都不适用时）：
   > 「这个我确实没做到位，我不想给您一个听起来对但可能错的答案。我会后查代码、跑一遍验证，整理成书面说明发给您，可以吗老师？」

**配套动作**：用到第 3 句时，**当场在纸上记下问题**，并当场说「我记下来了」。老师会认为这是负责任的表现。

### 8.7 问答时间管理

- 老师提问后，**应答 30~45 秒**。超过 60 秒就是我们的时间在被吃掉。
- 若老师问超大范围问题（「讲讲你们的架构」），**先收窄再答**：「架构我分四层讲，我用一分钟过一遍整体，重点说其中一层可以吗？」
- 问答剩余 1 分钟时，由席位 1 提示：「老师，我们大概还有一分钟，如果还有问题我们会后整理一份文档发给您。」

## 9. 风险预案

### 9.1 风险预案表

| # | 风险场景 | 触发条件 | 应对策略 | 具体话术 |
| --- | --- | --- | --- | --- |
| 1 | **老师问「这段代码是你写的吗」** | 老师指着某处代码/接口/页面问归属 | **如实回答**。不是本人写的就直说，然后讲清「这一块是谁做的、我做了什么、我怎么验证的」 | 若非本人：「这段不是我写的，是 XX 同学负责的。我参与了……（说清自己真实参与的部分：需求梳理、联调、测试、还是某几个具体文件），而且这块我是通过 XX 帮我的 XX 用例验证过的。如果老师想看具体实现，我可以现场翻到 XX 提交的那部分。」 若本人：「是我写的。这段的考虑是……（讲一个非表面的决策理由，比如为什么用反射扫描而不是逐个写测试）」 |
| 2 | **老师问「你们只有两个人做，其他人是干什么的」** | 团队参与度不均被指出 | 不回避、不狡辩。承认现实 + 亮出分工结构 + 强调「每个人对自己的模块能讲透、能被追问」 | 「老师说得对，我们前期投入是不均衡的。我们能明确说的是：X 人在后端主链路、X 人在前端和 AI、X 人主攻权限安全这一块，剩下的人是 X。这几个模块现在是能跑通的、是有测试的。为了让每个人都真的懂自己负责的部分，我们这周按模块做了交叉互测 —— XX 你能说说你是怎么做 X 模块的交接验证的吗？」（把球给真实做过的同学，用事实回答） |
| 3 | **老师问「这个项目有什么不足」** | 几乎必问 | **主动讲**。席位 7 主动列出 6 条不足，每条 = 一句现象 + 一句改进方向，不辩解 | 「我直接说六个我们清楚的问题：第一，主数据写权限过度集中在 admin；第二，供应商主数据维护缺位；第三，存在自己审自己的问题；第四，没有按金额分级的审批；第五，业务单据缺冲销；第六，报工没有复核环节。这六条我们都有对应的改法……最优先的是第五和第六，因为它们直接影响账实一致。」 |
| 4 | **老师指出代码质量问题/设计缺陷** | 老师翻代码后当场指出 | 不狡辩。先承认，再说明成因，最后给改进方案。**不承诺做不到的时间点** | 「老师您说得对，这一段确实不够干净。这里我解释一下背景：这块是我们前期赶联调的时候写的，判断逻辑重复了三遍。当时的取舍是先跑通再重构。您指出的这个问题我们已经记下来了 —— 我计划把它抽成一个统一的校验方法，测试可以复用。这一块不是设计意图，是我当时做得不够好。」 |
| 5 | **某人讲超时或卡壳** | 掐表节点已过；或本人明显停顿/重复 | 三级预案：① 自救（砍铺垫直接进结论）；② 接力；③ 主讲接管。**禁止当众呵斥或使眼色** | 自救：「我快一点，直接说结论——」；接力：「这块细节让 XX 补一下，XX？」；主讲接管：「XX 刚才那段信息量很大，我替他压成一句：……接下来这条线由 XX 来讲。」 |
| 6 | **演示环境崩了** | 现场登录报 500、白屏、连接超时 | **降级链**：实时演示 → 录屏（提前录好，含成功与失败两段）→ 截图逐张讲解 → 口头描述。切换动作由席位 1 或 7 在 10 秒内完成 | 席位 7 上：「老师，我们这边现场环境出现了一点问题（不解释技术细节、不甩锅），我先放一段我们提前录好的演示 —— 这是修复前的状态……这是修复后的状态。差异在这里。也说明一句：正因为现场环境不稳，我们才把验证固化成了 27 项接口回归脚本和 39 个后端用例，这部分可以随时给老师复现。」（把故障转成「我们有自动化验证」的加分点） |
| 7 | **老师深挖某人的技术细节到超出其深度** | 追问到底层实现、框架源码、索引原理 | 不硬撑。**给出你知道的边界 + 说明边界在哪 + 给出验证路径** | 「这块我实现的时候只到 XX 这一层，更底层的原理我了解得不深，我不想给您不准确的答案。我能说的是我们的取舍：为什么在这个场景下选这个方案，以及它带来的代价。如果老师希望，我可以会后查一下官方文档/源码给您一份准确的说明。」 |
| 8 | **被问「是不是 AI 生成的代码 / 用 AI 写的吗」** | 老师质疑项目真实性 | **不狡辩、不矢口否认**，转而讲人机分工和工程证据。如实回答使用范围 | 「我们使用了 AI 工具辅助编码和文档撰写，但最终的架构设计、权限模型修复、缺陷定位和验证工作由团队承担，AI 工具不替代我们对代码的理解。有三件事 AI 替不了我们：第一，权限漏洞是我们自己审计源码发现的 —— AI 不会主动告诉你你的 `@PreAuthorize` 全被注释掉了；第二，我们设计了 `SystemPermissionGuardTest` 用反射扫描做防回归，这是我们自己的判断；第三，业务链路和状态机是按服装行业 16 步流程设计的，需要业务理解。」 |
| 9 | **老师认为 7 个人讲是「一个人讲、其他人念稿」** | 老师观察到其他人不熟悉自己的部分 | 用**细节密度**证明：每个席位的追问锚点都是该模块的具体文件、具体错误码、具体测试类 | 被质疑时由本人回答（不是主讲代答）：「老师您随便问我这块的一个细节。」—— **敢让老师抽查是最好的反证** |
| 10 | **老师问「你们怎么保证项目不是 demo / 能交付吗」** | 老师质疑工业性 | 亮工程证据：数据库自检脚本、接口回归、单元测试、前端 build、可复现的演示账号体系 | 「我们有三层验证：一层是数据库层的 `sql/self_check.sql` 24 项自检；一层是接口层的 27 项写操作回归；一层是代码层的 6 个测试类 39 个用例。演示用的 8 个账号是按八角色建的，能当场切角色验证隔离。生产化还差的东西我也清楚，就是刚才说的那六条不足。」 |
| 11 | **老师问「需求从哪来 / 有没有真实用户」** | 老师质疑需求真实性 | 承认是实训项目，亮业务链路手册和错误码体系作为设计痕迹 | 「这是实训项目，需求不是我们凭空想的，是按服装制造企业的实际业务形态梳理的，梳理结果落在了那份业务链路手册里。你可以看错误码设计 —— 2003 库存不足、2006 超收超发、2007 幂等冲突、3002 成本重算、4002 AI 越权，这套编码是我们业务理解的痕迹，它不是抄来的 CRUD。」 |
| 12 | **老师指出「你们没有做三级审批流」** | 老师按市面 ERP 预期提问 | 主动澄清（这题对我们有利，因为是我们先说的） | 「对，我们目前没有上工作流引擎，也没有做多级会签，这不是没做完，是明确的第一版边界。我们的审批形态是两段式：草稿 → 生效，然后权限点分离，`:add` 和 `:confirm` 分开授权。多级会签和金额分级审批我们列成了后面的演进项。」 |

## 10. 答辩前演练计划

### 10.1 阶段划分

| 阶段 | 时间 | 目标 |
| --- | --- | --- |
| 阶段一：分稿定稿 | D-7 ~ D-5 | 每人写完自己那一节的讲稿，进入附录题库试答 |

| 阶段三：串联彩排 | D-2 | 全流程串讲一遍（含演示），掐表 |
| 阶段四：对抗演练 | D-1 | 交叉互问，用附录题库 + 自编刁钻问题压测 |

### 10.2 每日任务

**D-7（分工与口径对齐）**
- 全员通读本方案，确认自己的「负责什么 / 不负责什么」
- 明确每人的**边界**：自己的产出文件清单（不超过 6 项，能当场翻出来）
- 统一 §4.1 的两版回答，逐字记熟

**D-6（技术讲稿初稿）**
- 每人写自己的讲稿初稿，口播稿必须写成**可以直接念出来**的口语，不能是书面文章
- 每人准备 **3 个「我能当场证明」的动作**（跑哪个脚本、点哪个页面、跑哪个测试）

**D-5（讲稿定稿 + 术语过关）**

## 11. 演示环节设计

### 11.1 定位

**演示是答辩的证据环节，不是表演环节。** 唯一目标是回答「你说的漏洞修复和权限隔离，是真的吗」。所以只做一条主线，不做功能巡游。

### 11.2 演示顺序（操作 1'43" + 讲述 20" ≈ 2'03"，席位 6 主讲，席位 3 负责操作，席位 1 计时）

| 时段 | 动作 | 讲什么 | 对应证明点 |
| --- | --- | --- | --- |
| 0:00-0:15 | 屏幕切到后端 controller 源码，定位被注释的 `@PreAuthorize` | 「这是我们审计前的样子，10 个控制器的注解全部被注释掉了。」 | 漏洞真实存在 |
| 0:15-0:33 | 打开 `sql/self_check.sql` 或 git diff 展示修复后的注解 | 「这是修复后的状态，恢复了 74 处，另外补齐了 9 处端点。」 | 修复有量、有据 |
| 0:33-0:53 | 展示 `SystemPermissionGuardTest` 代码 + 运行它 | 「这个测试用反射扫描所有 controller 方法，断言每个都有注解，4 个用例。现在跑一遍。」 | 防回归是工程手段而非口头承诺 |
| 0:53-1:38 | **切到浏览器**：用 **admin** 账号登录 → 打开系统管理 → 用户管理 → 正常操作 | 「admin 是有权限的，操作正常。」 | 正向路径可用 |
| 1:38-1:58 | **切到 sales 账号** → 再次访问用户管理 / 角色管理接口 | 「sales 账号访问系统管理接口，返回体是 `{"code":403}`，菜单也不显示。权限隔离是双向验证过的。」 | 越权被挡 + 拒绝约定（200 + code 403） |
| 1:58-2:03 | 收回讲台 | 「演示到这里，验证方式我们也有脚本化的一套。」 | 交给席位 7 |

**演示动作的叙述纪律**：从切浏览器到点开销售工单/订单页面的那一下，**必须由席位 6 口述「我们切到浏览器」「这是 admin 的系统管理」「现在换一个低权限的账号」，否则老师会以为是在看一张静态截图**。这是演示中最容易失去说服力的一段，务必提前彩排。

**screen 与讲述的配合原则**：任何一张截图只能证明「做过什么」，不能证明「现在还能跑」；因此演示中**至少保留一次真实点击与一次真实接口返回**（sales 的 `{"code":403}` 响应体），这两样是全场唯一能证明系统当下可用的证据，优先级高于任何截图。

## 13. 附录：常见提问与参考答案（20 题）

> 标注「★」的为高风险题，务必逐字记熟。

**1. 这个项目到底是干什么的？能用一句话说清楚吗？**
海岚 ERP 是面向服装制造企业内部管理系统，覆盖主数据（物料/BOM/客户/供应商/员工）、业务单据（销售、采购、生产、库存）、组织与权限、AI 业务问答四条线。它的定位是企业内部管理平台，不是面向外部客户的电商系统。

**2. 为什么选 RuoYi 做底座？是自己写的吗？**
底座是 RuoYi，这是我们从一开始就定的策略：权限框架的坑很多（数据范围、菜单权限、登录态、审计日志），实训项目里重造一遍收益低、风险高。我们把增量放在了业务纵深上 —— 系统管理的 M→C→F 三级菜单、dataScope 的部门集合绑定、以及 AI 问答的受控流程，都是针对海岚的管理诉求自己设计的。

**3. 你们的权限是怎么做的？**
RuoYi 的方法级授权：Controller 上 `@PreAuthorize("@ss.hasPermi('...')")`，admin 用 `*:*:*` 通配放行。权限串是三段式 `模块:实体:操作`。除了操作权限还有数据范围（dataScope）：角色绑定部门集合，SQL 按 `dept_id` 过滤。前端还有 `meta.permission` 路由守卫做体验层拦截。真正不可绕过的防线只有后端那一层。

**4. ★ 你发现系统管理有越权漏洞，具体是什么？**
`backend/.../web/controller/system/` 下 10 个系统管理控制器，方法上的 `@PreAuthorize` 全部被注释掉了。注释掉之后代码照常编译、照常运行，用 admin 做功能测试全通过 —— 但任何登录用户都能增删用户/角色、改菜单和组织架构。属于严重的越权访问漏洞。

**5. ★ 那为什么功能测试没测出来？**
因为越权问题的测试条件是「权限不足的人执行操作」，而常规功能测试用 admin 覆盖了所有功能点，这类用例根本不会被写进用例集。所以我们换了思路，不靠功能测兜底，而是加了一条结构性测试 —— `SystemPermissionGuardTest` 用反射扫描所有 system 控制器方法，断言每个都带 `@PreAuthorize`，缺一个就失败。这条测试把「一整类问题」锁住了。

**6. 权限被拒绝的时候返回什么？**
HTTP 200，body 是 `{"code":403}`。这是 RuoYi 的统一响应约定，权限拒绝被当作一次正常业务结果封装。代价是 HTTP 层语义丢失，网关和监控看不到异常流量；我们的处理是前端在统一拦截器里集中判断业务码，不在页面里散着判。

**7. 前后端都做了权限校验，是不是重复？**
不是，目标不同。前端管「看不见」，后端管「做不了」。只有前端则改 URL 即可绕过，只有后端则用户看到入口点进去白屏报错。两套必须同时存在，且权限串命名要严格一致，我们用 `system:user:list` 这种三段式命名来保证前后端对齐。

**8. 数据库怎么建的？有没有用迁移工具？**
没有用 Flyway/Liquibase，这是我们的不足。现在是一个幂等初始化脚本 `sql/system-permissions.sql`，所有插入前判存在性，重复执行不产生重复数据也不报错。里面 54 条权限菜单、7 个部门、7 个岗位、8 个演示账号部门回填、admin 的 54 条授权。正确做法是引入 Flyway 拆成带版本号的迁移文件，这也是我们写进总结的第一条改进项。

**9. `sql/self_check.sql` 是干什么的？**
24 项自检，验的是「配置漂移」这类问题 —— 权限写进代码但没写进库、库里少了一条授权、账号没绑部门，这类问题代码上完全看不出来但功能就是不好使。把它写成 SQL 查询就能在部署后快速验一遍环境健康状况。

**10. 用户列表要显示角色名，你是怎么实现的？**
在 `SysUserMapper.xml` 的 `selectUserList` 里用 `group_concat` 标量子查询聚合角色名。没用 join 是因为 join 用户角色关系表会让行数膨胀，一个用户三个角色就变三行，PageHelper 分页 count 也会跟着膨胀导致分页出错。标量子查询返回单值、不参与外层行展开，count 不受影响，还能用 `group_concat` 的分隔符控制显示格式。

**11. 你们的单据是怎么保证状态不被乱跳的？**
服务端状态机。`sd_order` 六个态、`pu_purchase_order` 四个态，流转关系在服务端和数据库层都有表达，非法跳转直接返回 `2001`。前端把不合法的按钮置灰只是防手滑，真正拦住的是服务端校验。这也是「服务端权威」这条一致性红线的直接体现 —— 前端只显示，不参与裁决。

**12. 你们的一致性是怎么保证的？**
总结成六条红线：只增不改（流水类数据写入后永不修改，纠错走冲销）、原子提交（状态变更 + 库存副作用 + 计件副作用同事务）、幂等（带 `requestKey`，同键只生效一次，参数不同复用同键返回 `2007`）、服务端权威（金额/可发量/成本全服务端算）、冻结优先（工单冻结 BOM 工价，结算冻结价格快照）、留痕（所有动作记录操作人、时间、来源单据）。

**13. AI 问答是怎么做的？为什么不做成自由问答？**
接的 DeepSeek，走 OpenAI 兼容协议，base URL 是 `https://api.deepseek.com/v1`。不做自由问答有两个原因：一是幻觉，模型会编造系统里不存在的订单和库存数；二是成本和延迟不可控。所以我们收窄成受控流程：先选数据范围 → 再提问 → 系统查出对应的最多 20 条记录 → 把这 20 条真实数据和问题一起给模型做分析。模型的所有结论都锚在真实数据上，本质是把它定位成「数据摘要与归因工具」。越权查询返回 `4002`。

**14. 提示词是怎么保证效果的？**
两层。第一层是硬约束写进提示词：数据边界仅限服装制造的主数据和单据、禁止推测记录之外的信息、无依据必须明说、固定输出三段格式。第二层是测试兜底：`ErpAiPromptsTest` 9 个用例断言提示词必须包含关键约束片段，改提示词改坏了测试直接红。另外 `DeepSeekConfigTest` 7 个用例管配置，`DeepSeekConfigKeysTest` 4 个用例管 Key 的缺失与异常分支，共 20 个。坦白说我们只有人工评估集，没有自动化评估。

**15. ★ 用大模型会不会泄露企业数据？**
这是真实风险，我们的处理是控制出境数据面而不是假装不存在：只发送用户选定范围内查出的最多 20 条记录、推送前裁剪非必要字段、API Key 和 base URL 全部走环境变量，不同环境可指向不同服务。不够的地方也承认：没有做传输层额外加密和字段级脱敏的完整策略，这是明确的不足。

**16. 你们的测试是怎么做的？覆盖率多少？**
分三层：后端 6 个测试类 39 个用例全过；接口级写操作回归 27 项全 PASS，覆盖岗位、部门、用户、角色、菜单五类实体的「新增→编辑→删除」闭环，每项都有明确断言；权限隔离对抗验证，sales 账号调系统管理接口返回 `{"code":403}`。覆盖率我们必须诚实说：没有量化统计，工具链里没有接 JaCoCo，我们用的是用例清单式统计，集中在权限注解、角色更新、AI 提示词、配置分支这些高风险点。

**17. ★ 为什么接口级回归要做 27 项？**
因为单测和链路级测防的风险不同。单测防函数级逻辑错，但绕过了路由、参数绑定、序列化、权限拦截、事务；链路级防「串不起来」，比如我们实际抓到的 `AjaxResult.put()` 是顶层 map put、`authRole` 的 `user`/`roles`/`menus`/`checkedKeys` 在响应顶层而不在 `data` 下 —— 这类问题只有真跑一遍链路才暴露。

**18. 业务上「删除」和「作废」为什么分开？**
软删除解决「还能不能查到」，作废解决「这笔单据在业务上还算不算发生」，是两个不同维度。单据侧不提供物理删除入口，只有草稿能删，提交后只能作废，因为库存台账、报表、审计日志都引用单据号，物理删掉账就对不上。软删除是存储层手段，作废是业务语义层状态，不该用同一个动作混着做。

**19. ★ 这个项目最大的收获是什么？如果重做一次会改什么？**
收获是我们搞明白了一件事：企业系统里最危险的问题不是功能做不完，是「看起来做完了」。那 74 处被注释的注解，功能测试全绿，但安全上是空的。我们重做会先补测试体系而不是先补功能：引入 Flyway 做版本化迁移、把越权验证从单一角色扩展成「角色 × 敏感接口」的参数化矩阵、把 AI 的人工评估集固化成自动化回归。另外我们清楚的六条不足是：主数据写权限过度集中 admin、供应商维护缺位、自审问题、无金额分级审批、冲销缺失、报工无复核。
