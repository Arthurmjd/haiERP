# 第一部分 · 分工方案

## 1. 文档说明

### 1.1 项目简介

海岚 ERP 是一套面向服装制造企业内部管理的信息化系统，覆盖「主数据管理 → 权限体系 → 业务单据 → 数据看板 → 智能问答」的完整链路。系统以 RuoYi 权限底座为基座，叠加服装行业主数据（物料/BOM/客户/供应商/员工）与生产业务单据（销售订单、采购订单、生产工单、库存出入库、裁剪排产等）的管理能力，并在其上实现了「先选数据范围、再提问、再基于查询结果分析」的受控 AI 业务问答模块。

项目定位是教学实训：在真实工程约束下完成一次从需求拆解、权限建模、数据库设计、接口实现、前端落地到回归验证的全流程工程实践。

### 1.2 技术栈

| 层次 | 技术选型 | 关键说明 |
| --- | --- | --- |
| 前端框架 | Vue 3 + TypeScript + Vite | 组合式 API + `<script setup>`，强类型约束接口契约 |
| 前端 UI | Element Plus | 表格、表单、树形控件（el-tree）直接满足 ERP 表单密集型需求 |
| 前端路由/权限 | Vue Router + `meta.permission` 守卫 | 路由级权限元数据 + 全局守卫 |
| 后端框架 | Java 21 + Spring Boot 3.5.0 | jakarta 命名空间，Spring Security 6 集成 |
| 后端模块 | Maven 多模块 6 个：`ruoyi-common`(103 个 java) / `ruoyi-framework`(44) / `ruoyi-quartz`(18) / `myfactoryai-system`(61) / `myfactoryai-manufacturing`(55) / `myfactoryai-admin`(44)，合计 325 个 java | 制造业务与平台底座分离 |
| 持久层 | MyBatis + MyBatis-Generator | 动态 SQL 灵活，适合 ERP 多变查询条件 |
| 权限底座 | RuoYi（Spring Security + `@PreAuthorize`） | `"@ss.hasPermi('...')"` 表达式 + 数据范围 dataScope |
| 数据库 | MySQL 8.4.6 | utf8mb4，支持 CTE、窗口函数 |

### 1.3 团队构成与分工维度

团队共 7 人。分工按两条可验收的坐标切分，每位席位都对应到具体的代码目录和文件：

**坐标一：18 个 ERP 业务控制器**（`myfactoryai-admin/.../web/controller/erp/`，共 1276 行）

**坐标二：4 个前端页面群**（`frontend/src/views`，28 个 .vue；全量 31 个 .vue + 15 个 .ts，4953 行）

**这一分工结构的合理性说明：**

1. 控制器、Service、Mapper、页面、SQL 脚本、测试类都是**可独立切分、可独立验收**的交付物，各自的产物在代码库里可查证（`ls` 一下目录就能对上）。
2. 7 个席位覆盖全部 18 个业务控制器与 28 个视图，没有「没人负责」的模块，也没有两个人声称同一份代码。
3. 本方案中，每位成员的「技术讲述」只允许落在**真实存在的实现**上 —— 具体到文件名、接口名、表名、脚本名、测试类名。这既是答辩可信度的基础，也是对团队其他成员的尊重：不虚构工作量，也不让人承担不属于他的责任。

**可能被追问的问题（3 个）+ 参考回答**

1. **问：这个项目最大的技术难点是什么？**
   - 答：难点不在功能数量，而在「权限这件事到底做没做实」。RuoYi 的权限模型是「注解 + 数据范围」两层，注解管「能不能调这个接口」，`dataScope` 管「能看见哪些行」，两者是正交的，缺一个都不算完整的权限。我们的做法是把两层都变成可核查的事实：注解这层用反射扫描测试锁死，228 处必须一条不少；数据范围这层用 8 个角色的权限矩阵加 `sql/p4-rbac-completion.sql` 的 7 项自检来验，不靠人工点页面。这类问题在功能测试里完全测不出来 —— 功能都正常，你用 admin 测一切通过，但换成 sales 账号就可能看到不该看的数据。

2. **问：你们的架构是自己设计的还是用的现成框架？**
   - 答：底座是 RuoYi，因为课程要求在成熟权限框架上做增量，这让我们把精力放在业务纵深而不是重造权限轮子。但增量部分的设计是我们自己定的：制造业务域独立成 `myfactoryai-manufacturing` 模块，55 个文件 5051 行，分成 domain/mapper/service/support 四层；业务错误码独立成 `ErpErrorCode` 枚举，8 个码值写死在枚举里，前端按码分支处理；AI 问答的「先选范围再提问」流程也是按海岚自己的管理诉求设计的 —— 如果让它自由问答，token 成本和幻觉都不可控，所以我们把它约束成「限 5 种业务模式 → 提问 → 基于查出的最多 20 条记录做分析」，本质上是把 LLM 降级成一个「数据摘要与归因工具」，而不是一个聊天机器人。

3. **问：7 个人做一个 ERP 系统，工作量够吗？你们怎么分工的？**
   - 答：够，但前提是分工必须落在可验收的产物上。我们不是按「模块页面」平均切的，是按两条坐标切的：一条是 18 个 ERP 业务控制器，`web/controller/erp/` 目录下能一个个列出来；另一条是 4 个前端页面群，28 个 .vue 文件按业务域分成主数据、单据、财务看板、AI 与系统管理四组。每个人能当场把自己负责的控制器和页面文件翻出来，验收的时候看产出物而不是看人。

**应急话术**

> 「这个问题我来准确回答一下，避免误会：我们的分工是按「18 个 ERP 业务控制器 + 4 个前端页面群」两条线切的，每个席位对应一组具体的控制器和页面文件，`ls` 一下目录就能对上。像数据库初始化脚本、权限审计、验证体系这些，是另外几条独立的交付线，各自有对应的产出文件。分工表上有记录，我一会儿可以指出来。我个人的主要工作是架构梳理、平台级单号规则与单据冻结两个控制器、演示组织和答辩统筹。我不想把别人的工作量说成自己的，也不想把团队说成是某一个人完成的 —— 这两种说法都不准确。」

**答辩讲述要点**

1. **后端分层与接口链路（60 秒）**
   - 口播稿：「后端是标准的三层加一层防护：Controller 接 HTTP、Service 管业务规则、Mapper 出 SQL、权限注解横切在 Controller 上。一条完整链路是这样 —— 前端发请求，Spring Security 先过认证，再进 Controller，方法上的 `@PreAuthorize` 判断你有没有这个权限串，然后 Service 做业务校验，比如单据状态对不对、引用还在不在，最后 Mapper 落库。任何一层不通过，都是明确的业务错误码，而不是抛一个堆栈给用户看。这套错误码集中在一个枚举里 —— `ErpErrorCode`，8 个码值：1001 参数校验失败、1002 数据重复、2001 状态不允许、2003 余额或库存不足、2005 试算前提不满足、2006 数据已变化、2007 请求记录不一致、4002 没有该业务数据权限。」

2. **状态机与服务端权威（90 秒）**
   - 口播稿：「业务上单据不能随便跳状态。销售订单是七个值：0 草稿、1 已确认、2 生产中、3 已完工、4 已出货、5 已完成、9 已取消；报价是四个：0 待确认、1 已接受、2 已失效、3 已转单；采购单是 0 草稿、1 已下单、2 部分到货、3 已到货、9 已取消；工单是 0 待下达、1 生产中、2 已完工；出货单是 0 待发货、1 已发货、2 已签收、9 已取消。前端把不合法的按钮置灰只是防手滑，真正拦住非法跳转的是服务端 —— 比如一张单已经出货了，你调接口直接跳回草稿，服务端会返回 `2001` 拒绝掉。这背后的原则是「服务端权威」：金额、可发量、发齐判定、成本全部服务端算，前端只负责显示，不参与计算也不参与裁决。」

3. **一致性红线（60 秒）**
   - 口播稿：「我们把业务上的硬约束总结成六条红线，其中三条直接落在代码里：第一是「只增不改」—— 库存流水 `st_stock_txn`、报工事件、计件事件一旦写入永不修改，要纠错只能走冲销；第二是「原子提交」—— 状态变更、库存副作用、计件副作用、操作记录必须在同一个事务里，不允许出现状态改了但库存没动；第三是「幂等」—— 收货、领料、报工这些动作都带 `requestKey`，落在 `biz_action_request` 表里，同一个键重复提交只生效一次，如果同一个键配了不同参数直接返回 `2007` 冲突。这一条对移动端弱网场景特别重要，重复点一次提交不会重复收货。」

4. **报价转订单（50 秒）**
   - 口播稿：「销售链路里有一段容易做错的是报价转订单。报价有四个状态，转单之后不是把报价删掉，而是把它标成 3 已转单，同时生成一张新的销售订单，两张单据通过来源字段关联。这样做的好处是报价的历史价格后来被改了，也不会污染已经生单的那张单 —— 演示库里就留着一张已转单的报价，能当场翻出来看这条链路。」

5. **主数据引用校验（40 秒）**
   - 口播稿：「主数据这块的规则是「引用中的不能删」。物料如果已经在 BOM 里被引用，删掉之后 BOM 就悬空了；客户如果已经被销售订单引用，删掉之后订单上的客户名就成了脏数据。所以删除前会做一次引用检查，有引用就拒绝并明确告诉你是被哪一类单据引用了，不是简单地报一个『删除失败』。这里的返回码是 `2007`，因为它和幂等冲突共用一个语义：请求和目标记录的状态不一致。」

**可能被追问的问题（3 个）+ 参考回答**

1. **问：为什么删除要区分「草稿删除」和「作废」两个操作？数据库软删除不行吗？**
   - 答：软删除解决的是「还能不能查到」，解决不了「业务上这笔单据还算不算发生」。我们两个需求都要：主数据删除要求不可再被检索，所以做删除标记；但业务单据要保留可追溯性，因为报表和库存台账依赖单据号。所以单据侧不提供物理删除入口，只提供作废，作废的单据带作废状态和作废人作废时间，报表按状态过滤。也就是说软删除是存储层的手段，作废是业务语义层的状态，这两个不是一回事，不该用同一个动作混着做。

2. **问：怎么保证前端隐藏了按钮，后端就一定不会被直接调用？**
   - 答：隐藏按钮是展示层约定，可以被绕过 —— 用浏览器控制台改个 DOM、或者直接拿 Postman 打接口，权限校验就失效了。真正的防线必须在服务端，放在 `@PreAuthorize` 上，校验用的是当前认证用户的权限集合，服务端自己算，不信任任何客户端传来的标识。我们全库 228 处注解逐条核对过，还专门写了反射扫描的回归测试去锁这个性质，就是为了防止哪次合并把注解又删掉。

3. **问：你们的错误码是怎么设计的？为什么不用 HTTP 状态码？**
   - 答：因为业务失败的种类比 HTTP 状态码细得多。HTTP 的 400 只能说明「你请求有问题」，但我们需要区分「状态不允许」（2001）和「参数不合法」（1001）；也不会把「库存不够」（2003）和「这条记录别人刚改过」（2006）混成一个码。8 个码值写在 `ErpErrorCode` 枚举里，注释里明确写了「码值本身是前后端契约的一部分，禁止改动数值，只允许新增」—— 因为前端是按码分支处理的，改一个数值就可能让某个提示语错位。

**可能被追问的问题（3 个）+ 参考回答**

1. **问：前端做了权限控制，后端也做了，那是不是重复劳动？**
   - 答：目标不一样，缺任何一个体验都会坏。前端拦的是「看不见」，后端拦的是「做不了」。如果只有后端，用户点了菜单进去，页面报错弹一个 403 白页，很差；如果只有前端，用户看不到菜单但改个 URL 就能访问，那就是越权漏洞。所以这是必要的冗余，不是重复。而且我们后端拒绝时返回的是 HTTP 200 加 body 里 `code=403`，前端统一在响应拦截器里判断这个业务码再跳转，所以前端拦截器要正确处理这个约定 —— 这也是联调时踩过的一个点。

2. **问：为什么有一批页面走统一的目录页，而不是一页一个组件？**
   - 口播稿外的答法：因为主数据类的页面结构高度同构 —— 都是「左侧分类 + 右侧表格 + 弹窗表单」，差异只在字段和接口。这类页面我们用一个 `CatalogView` 配合目录配置驱动，路由是 `/:group/:key`，配置里带 `permission`。好处是加一个新主数据台账不用新写一个组件；代价是这类页面的定制能力弱，遇到交互特殊的页面（比如款式成本页 `StylePlanView`）就必须单独写一个组件，这也是为什么 28 个页面里两种形态并存。

3. **问：28 个视图会不会太散了？后续怎么维护？**
   - 答：我们按业务域分成四个群：主数据与计划、单据与库存、财务与看板、AI 与系统管理。API 层也按同样思路拆成六个模块，不是所有接口堆在一个文件里。坦率说目前有一批页面之间代码结构偏相似，列表加表单加弹窗的组合重复度较高，缺少通用 CRUD 组件抽象 —— 只有主数据那批做了目录页驱动。这是我自己识别出的不足，补法是把这套配置驱动扩到单据页，抽一层列表/表单/弹窗的通用组件。

4. **问：菜单为什么要分 M、C、F 三级？**
   - 答：M 是目录，只做分组不指向页面；C 是菜单，指向一个前端路由页面；F 是按钮，对应一个具体操作权限，比如 `system:user:edit`。分三级是因为按钮权限必须挂在某个菜单下面才有归属，否则 `system:user:edit` 这种权限串就没法按模块批量授权和回收。我们库里现在一共 186 项菜单：ERP 业务段 132 项（1 个目录 + 32 个菜单 + 99 个按钮），系统管理段 54 项（1 个目录 + 9 个菜单 + 44 个按钮）。前端按 `F` 类型生成按钮并检查权限串，后端在 Controller 上用同名权限串做校验，两边靠这个三级结构对齐。

**可能被追问的问题（3 个）+ 参考回答**

1. **问：为什么不干脆把整个数据库丢给大模型让它自己分析？**
   - 答：那是最容易做但最不稳的一种方案。三个问题：一是成本，全量数据塞进去一次调用可能上万 token，天天用不起；二是准确率，模型对大表做全局统计很容易出错，而且出错你很难发现；三是权限，把整库暴露给模型等于绕过了我们的权限体系，用户 A 的问题里就可能带出用户 B 看不到的数据 —— 在我们的实现里，这一步是在调模型之前就被 `4002` 拦掉的。我们选「先按权限查、每条查询硬性 `LIMIT 20`、基于这 20 条分析」，本质是把 LLM 定位成一个「结构化数据摘要与归因」的工具，它的输入永远是系统已经授权、已经取好的确定性数据。

2. **问：提示词怎么保证效果稳定？你怎么知道改完还是好的？**
   - 答：我们不敢说提示词是「优化好了」，只能说是「有约束、有回归」。第一层是硬约束写进提示词：数据边界、禁止推测、输出格式。第二层是测试兜底：`ErpAiPromptsTest` 里 9 个用例断言提示词必须包含这些约束的关键片段，这样任何一次改动如果删掉了关键约束，测试直接失败。第三层是人工评估，我们固定了一批问题作为评估集，每次改提示词手动跑一遍看结论有没有变差。坦白讲我们没做到自动化评估，这块是明确的不足。

3. **问：调用大模型会不会把企业数据泄漏出去？**
   - 答：这是真实风险，我们的处理方式是控制出境数据面而不是假装不存在。第一，只发送当前用户有权限、且被 `LIMIT 20` 限制的那一小批记录，不发送全量；第二，查询本身是只读的，模型不生成 SQL、不改单据，它没有写回系统的通道；第三，整个链路的 API Key 和 base URL 都是环境变量配置，不同部署环境可以指向不同的服务。我们也承认这还不够，比如目前没有做传输层额外加密和字段级脱敏策略的完整方案，这是我们下一步要补的。

**可能被追问的问题（3 个）+ 参考回答**

1. **问：为什么不用 Flyway 或 Liquibase 做迁移，非要手写幂等 SQL？**
   - 答：这是我们的不足，坦白承认。Flyway 更规范，有版本化、有校验和、能追踪变更历史，我们这套是按阶段编号的一组脚本（`p1` / `p2` / `p3` / `p4` 就是补丁序号）。之所以先这么写，是因为我们的场景偏「初始化 + 少量补丁」，脚本本身也不复杂，团队对迁移工具的熟悉度不够。但这个选择的代价是真实的：没有变更历史，无法知道某个环境执行到了哪一步，也没有 checksum 检测别人手改了脚本。补的做法是引入 Flyway，把现有脚本拆成 `V1__init.sql`、`V2__system_permissions.sql` 这样带版本号的迁移文件。

2. **问：初始化脚本里直接 INSERT 密码明文，安全吗？**
   - 答：脚本里放的确实是演示账号，而且明文只存在于脚本这一处，运行期的密码比对走的是框架的加密流程（加盐哈希后比对），数据库里存的不是明文。但严格说，演示环境的密码强度和「脚本里写死」这个做法都不适合生产 —— 正确做法是初始化时生成随机密码、首次登录强制修改，或者走环境变量注入。我们这个脚本的定位就是实训演示环境，如果要上生产，这块必须重做。

3. **问：`group_concat` 拼接角色名，如果一个用户角色特别多，字段会不会超长？**
   - 答：会，`group_concat` 的结果默认受 `group_concat_max_len` 限制，MySQL 默认 1024 字节，理论上存在被截断的风险。我们目前 8 个角色、每个演示账号 1 到 3 个角色，拼接结果通常几十个字节，不会触发。但这是隐患，稳妥的做法是显式设置 `group_concat_max_len`，或者在展示层做「前两个 + N」的折叠显示而不是全量拼接。

**可能被追问的问题（3 个）+ 参考回答**

1. **问：为什么权限拒绝返回 HTTP 200 而不是标准的 403？**
   - 答：这是 RuoYi 框架的既有约定，不是我们发明的。框架把权限校验失败当作一次正常的业务结果封装成统一响应体，`AjaxResult` 里 `code` 字段放业务状态码，HTTP 层始终是 200。这样做的好处是前端只需要一套统一处理逻辑 —— 不管后端返回什么，最终都是同一个响应结构，前端拦截器里判断 `code` 即可。代价也很明确：HTTP 层的语义丢掉了，监控和网关看到的是一堆 200，异常流量在 HTTP 层面不可见；而且如果任何一处客户端漏判业务码，就会把错误当成功处理。我们的处理是在前端统一拦截器里集中判断，不在各个页面里散着判。

2. **问：反射扫描这种测试，是不是有点「测试实现细节」？**
   - 答：这个顾虑是合理的，我们讨论过。反射扫注解确实耦合了实现形式，如果将来把权限从注解换成拦截器或者自定义 DSL，这条测试就会误报。但我们保留它，理由是这个项目的安全属性要求「缺失即失败」—— 注解是我们当前约定的实现形式，安全护栏必须锚定在具体的约定上，否则就没有东西可扫了。同时它的成本极低：4 个用例、秒级执行、CI 里零配置。更好的做法是两层都要 —— 反射扫描保证形式不丢，行为层的越权用例保证语义正确，两者互补。我们目前行为层只有 `ErpAccessTest` 的 3 个用例加 sales 账号一个人工场景，覆盖的角色还不够全，这是明确的不足。

3. **问：权限串 `*:*:*` 通配放行，admin 的权限校验还有意义吗？**
   - 答：对 admin 来说没有意义，通配本来就全放行，admin 是「不设防」的设计意图，用来做初始化和应急。意义在于非 admin 用户。我们所有权限串都是按三段式校验的，admin 的 `*:*:*` 只影响 admin 自己。真正需要警惕的是另一个方向：如果将来有别的角色也被授予了类似通配的权限串，那这套机制就形同虚设了。所以我们做权限串核对时，除了检查注解在不在，也检查了有没有出现不该有的通配授权 —— admin 有，其他 7 个角色没有。系统管理这块我们甚至更严：用户、角色、菜单、部门四个模块的权限只授给 admin，其他角色一条都不给。

2. **为什么自检要写成 SQL 而不是写测试（80 秒）**
   - 口播稿：「这一点我想专门讲，因为它是我们这个项目里成本最低、收益最高的一件事。单元测试查的是代码逻辑，但 ERP 最容易出问题的地方不在代码 —— 在数据。比如库存流水加总起来和库存表的余额对不上，代码一行都没错，可账是错的。这类问题你用 Java 测试查不出来，因为你要造一整套数据。写成 SQL 就简单了：一条 `SELECT` 把两边各自加总再对比，不相等就 FAIL。`self_check.sql` 里 29 项大部分是这种对账式检查 —— 库存和流水双向一致、报工总量和工序进度一致、成本明细和汇总一致、应收必须有真实出货单支撑。它还有一个隐含好处：这些 SQL 本身就是业务口径的文档，新人读一遍就知道每条约束到底是怎么定义的。」

3. **演示组织（60 秒）**
   - 口播稿：「演示我做了三轮彩排。第一轮跑通流程，第二轮专门练衔接，第三轮压缩到时间盒内。我们用的是 8 个演示账号、统一密码 `Demo@2026!`，每个账号对应一个岗位和部门。演示里有一个关键对比动作：同一个财务页面，分别用 finance 账号和 boss 账号打开，让老师看到 boss 是只读、finance 才能登记收付款 —— 这个对比比讲十遍权限矩阵都有用。另外权限隔离那段我们是故意先给结论再展示证据，效率比现场等接口报错高。」

4. **项目总结与不足（80 秒）**
   - 口播稿：「总结一下我们的产出：一套跑通的 ERP 实训系统，6 个 Maven 模块 325 个 java、43 个控制器 260 个接口、66 张表 9 个视图、186 项菜单、228 处权限注解、32 个单元测试、60 项 SQL 自检全 PASS。不足我先说六条，都是我们清楚的问题：第一，审批只有两段式 —— 待办里点通过或驳回，没有工作流引擎、没有多级会签；第二，没有按金额分级的审批规则，boss 一个人可以审所有金额；第三，存在自审问题，财务既能做成本试算又能确认，计划员既能建采购单又能确认收货；第四，业务单据缺冲销流程，已生效的单据只能作废，长跑会积累"想改改不了"的单据；第五，报工没有复核环节，报工直接生成计件工资，缺少班长或质检确认，这是工资准确性的单点风险；第六，没有 CI，32 个用例和 60 项自检都是本地手工跑的，也没有接 JaCoCo 这类覆盖率统计。这六条我们都有对应的改法 —— 比如第三条只要改 `sys_role_menu` 的授权，把 `:confirm` 收给主管就能变成真审批，不需要改代码，这是权限点分离设计带来的红利。」

**演示/佐证方式**

- 展示测试执行记录（6 个测试类 / 32 个用例 / 全部 PASS），可现场重跑其中任意一个类。
- 依次跑四个 SQL 自检脚本，展示 60 项全 PASS。
- 演示财务页 8 个标签：总览 / 账户 / 资金流水 / 月度现金流 / 应收 / 应付 / 账龄汇总 / 收付款。
- 演示 `npm run build` 成功输出。
- 现场用 boss 与 finance 两个账号打开同一张应收单，展示 boss 只读、finance 可登记收款。

**可能被追问的问题（3 个 + 参考回答）**

1. **问：把自检写成 SQL，和单元测试比，会不会重复或者有盲区？**
   - 答：防的风险不同，盲区也互补。单测在没有数据库的环境里也能跑、跑得快，但它绕过了路由、参数绑定、序列化、权限拦截、事务这些环节，也看不到真实数据的一致性；SQL 自检正好相反，它验证的是「这些数据现在是否自洽」，但验不了「某段代码在某个入参下分支对不对」。我们实际抓到的 `AjaxResult.put()` 顶层结构问题，是链路联调发现的；抓到的库存与流水对不上，是 `self_check.sql` 第 3 项发现的，两者都不是对方能替代的。

2. **问：如果要你们重做一遍，最想改的是什么？**
   - 答：我会先补测试体系，而不是先补功能。具体三步：第一，用 Flyway 做版本化迁移，把数据库变更变成可追踪的历史；第二，把权限验证从 sales 一个账号扩展成「角色 × 敏感接口」的矩阵，做成参数化测试自动跑；第三，把这 60 项 SQL 自检和 32 个用例接进 CI，现在是本地手工跑，这是最大的工程化缺口。我们做出来的东西能跑，但"改一次不担心坏"这个属性还不够。

3. **问：你说 32 个测试全过，那覆盖率是多少？**
   - 答：我必须诚实回答：没有测覆盖率，我们用的是测试用例数量和场景覆盖的清单式统计，而不是行覆盖或分支覆盖工具的量化数据。32 个测试集中在一批高风险点上 —— 权限注解反射扫描 4 个、AI 提示词 9 个、DeepSeek 配置与 Key 11 个、单据草稿更新 5 个、访问控制 3 个。这是我们明确的不足：工具链上没有引入 JaCoCo 这类覆盖率统计，所以无法回答「到底有多少分支被覆盖」。如果要做，我们倾向于用覆盖率报告先找出未覆盖的高风险分支，而不是追求一个漂亮的百分比数字。

**应急话术**

> 「生产、库存、成本、人事这 10 个控制器是我写的，`ErpWorkOrderController`、`ErpCostController`、`ErpSalaryController` 这些文件可以当场翻。验证体系这块 —— 32 个用例的执行归档、60 项 SQL 自检、演示三轮彩排、页面群 C 的 10 个页面 —— 也是我做的。我要说明的是，`SystemPermissionGuardTest` 那条护栏测试是 XXX（成员6）写的，我负责的是把它纳入回归流程并跑通；财务页里资金域的设计口径是以 XXX（成员6）的权限矩阵为准的。」

### 4.4 技术选型统一说法

- **为什么 Vue 3**：ERP 是表单密集型、表格密集型系统，响应式数据流和组件化能显著降低这类界面的复杂度；配合 TypeScript 把接口返回字段类型化，后端改字段时能在编译期暴露问题，比运行时才发现代价低得多。Vite 的冷启动和 HMR 在前端联调阶段效率提升明显。
- **为什么 Spring Boot 3.5.0**：课程要求 Java 21，Spring Boot 3 是与 Java 17+ 长期主线匹配的大版本，jakarta 命名空间下与 RuoYi 底座兼容；Spring Security 6 的方法级授权机制成熟，配合 `@PreAuthorize` 表达式正好满足我们的权限模型需求。
- **为什么 MySQL 8.4.6**：ERP 数据关系强、事务一致性要求高，MySQL 的 InnoDB 事务、索引和 `group_concat` 这类函数覆盖了我们全部需求；8.4 支持 CTE 和窗口函数，为后续做数据分析类报表留了空间。
- **为什么 Redis**：主要用于令牌/会话状态与热点字典缓存，把无状态的鉴权压力和频繁读取的字典数据从数据库剥离，降低数据库连接压力。
- **为什么 MyBatis 而非 JPA**：ERP 的查询条件高度动态，MyBatis 的动态 SQL 对这种多条件组合的掌控力更强；同时 MyBatis 与 RuoYi 底座原生集成，避免额外的适配成本；SQL 可控也便于做 `dept_id` 这类数据范围过滤。

### 6.2 排序依据（五条）

**依据一：技术纵深递进，先「是什么」再「怎么实现」再「怎么守得住」。**
席位 1 先给全景和业务链路，让老师建立「服装 ERP」的心智模型；席位 2 讲后端如何把 19 步链路转成状态机；席位 3 讲前端如何呈现；席位 4 是横切能力（AI）放在主链路之后，因为它是增益不是主干；席位 5 回头讲数据地基；席位 6 把权限安全作为独立的深度高峰放在末尾段；席位 7 收束。听众认知负荷是「广度→细节→深度→收尾」。

**依据二：最亮点后置，保证「最后印象」。**
权限这张网是本项目最有说服力的部分：43 个控制器、228 处 `@PreAuthorize`、8 个角色的权限矩阵、系统管理四个模块只授 admin、99 个业务按钮权限逐条对齐。这件事的难度不在写注解，而在「证明它真的生效」—— 一条反射扫描的测试 + 7 项 SQL 自检 + sales 账号实测 403，三样都不是嘴上说。它放在第 6 位，处于老师注意力尚未衰减的黄金段，且紧接在「看起来规整」的铺垫之后，反差最强。

**依据三：避免首尾撞车。**
席位 1 只做「总览 + 路线图」，明确说出接下来由谁讲，避免老师觉得是 1 个人讲 30 分钟。席位 7 只做「验证 + 不足 + 收尾」，做总结但不重复细节。首尾两人都不做技术深潜，各自只做导航和收束。

**依据四：承接关系自然，串场不生硬。**
每个人退出时抛出的下一个人的话头，必须是他下一位的开场白。设计上形成 6 个「接口」：

- 1→2：「刚才的 19 步链路，在后端是怎么落成状态机的」→ 席位 2 直接接
- 2→3：「后端管住了业务，那用户在界面上怎么操作、怎么被挡住」→ 席位 3 直接接
- 3→4：「系统管理这部分界面和路由都讲完了，另外还有一块 AI 能力」→ 席位 4 直接接
- 4→5：「AI 要基于真实数据回答，那数据是怎么组织的」→ 席位 5 直接接
- 5→6：「数据准备好了，但谁能改数据这件事本身是有洞的」→ 席位 6 直接接
- 6→7：「权限配齐了，怎么证明它不会再退化」→ 席位 7 直接接

**依据五：提问命中率高的席位配对，减少跨人转交成本。**
AI（4）、数据库（5）、权限（6）这三类最容易被追问，各自安排专人，且三者相邻；测试席位（7）紧邻权限席位（6），因为权限类问题最容易被追问「你怎么证明」。

### 6.3 每人串场话术（可直接念）

**席位 1 —— 进入**

### 7.4 控场机制

**掐表责任人**：由非发言者担任（推荐席位 7 或指定一名不讲话的计时同学），用**手机秒表**并把手机放在讲台，屏幕朝上。

**三次提醒**：T-30 秒抬手比「三」；T-10 秒抬手比「一」；T+0 秒轻声说「时间到」，或直接由席位 1 的串场词收束。

**超时怎么办**：
- 轻微超时（15 秒内）：本人自行加速，砍掉最后一句铺垫，直接进核心结论。
- 明显超时（60 秒以上）：**席位 1 在下一个转场时接管** ——「XX 这块讲得比较细，剩下两点我替他收个尾 —— 后端这条线，接着由 XX 来讲。」注意：**不是当众打断**，当众打断同组同学是最伤印象的行为。
- 硬约束：每位席位的**最后一页必须是「收束页」**（3 个数字 + 一句结论），这样任何人被打断都能在 15 秒内翻到收束页收尾。

**被老师打断怎么办**：立刻停止讲述，把讲台让出半步，面向老师「老师您说」。回答控制在 30~45 秒，答完补一句「如果还有细节，会后我可以单独演示」，然后接「我们继续，刚讲到……」。**不要在被打断后原地继续把被打断的那段重讲**，直接跳到下一个锚点。

**卡壳（忘词）怎么办**：不沉默超过 3 秒。备用句式：「这块我先说结论，细节我记不太清，稍后可以给老师看代码。」立即把话头递出去：「XX 这块比我熟，请 XX 补充一下？」—— 这是事先约定的合法转交，不是失分。

## 8. 问答环节组织

### 8.1 应答规则（谁懂谁答，主讲兜底）

| 老师问题类型 | 首选应答人 | 备选 |

| 数据库设计、权限菜单表、索引、演示账号、自检 SQL | 席位 5 | 席位 6 |

| 测试策略、覆盖率、回归、构建、CI | 席位 7 | 席位 2 |

| 跨模块的架构问题 | 席位 1 先给框架，再点人补充 | 相关席位 |

**五条规则：**

1. **首答归属**：问题由老师抛向全场时，先由该问题相关的席位直接答，不要所有人同时看向主讲人等待 3 秒。听到问题与自己相关的同学应当即开口，这本身就是「熟悉项目」的信号。
2. **主讲兜底**：若 3 秒内无人应答，或问题超出所有人的具体职责（宏观、项目管理类），席位 1 必须立刻接话，避免冷场。
3. **不越权作答**：没做过的事情不要硬答。
4. **最多两人**：一个问题最多由 2 人回答，第 3 人不补充。
5. **答完即停**：回答完立刻交还控制权：「回答完了，请老师继续提问。」

### 8.2 自我介绍与称呼约定（第一句话就定调，不要跳过）

**开场由席位 1 用一句话把团队结构说清楚**，这是全场最重要的一次铺垫：

> 「我们组 7 个人，按业务域分工。我是队长 XXX，负责整体架构、平台级的单号规则与单据冻结两个控制器、以及演示统筹；接下来依次由主数据与销售的 XX、前端的 XX、AI 与系统管理的 XX、数据的 XX、权限安全的 XX、生产与成本的 XX 依次讲。我先说明一下分工方式：后端 18 个 ERP 业务控制器分成四条线 —— 主数据与销售 7 个、生产与成本人事 10 个，加上平台 2 个；前端 28 个页面分成四个群。每一块都有对应的产出文件，待会儿讲到的时候可以当场指出来。」

**规则：**

- **每位席位的第一句话必须包含「姓名 + 我负责什么」**，例如「我是 XX，负责后端这块」。老师要能对上人。
- **不要说「我们组做的是…」开头**，要用「**我**负责…」。让老师明确知道现在是谁在讲。
- **不要说「接下来由 XX 讲…」这种排他式交接**，改用 **「补充一句」** 的协作式说法（见下）。
- **不要说「这部分是 XX 做的，他来讲」** —— 推诿感极强。

### 8.3 统一转交话术

**A. 明确知道谁能答（最佳）**
> 「这个我印象比较深的是……不过 XX 这块是主力，让他来说会更准确。XX，你来一下？」

**B. 不确定谁能答**
> 「这个问题我不确定，XX 你做过这块吗？—— 如果都不熟，我课后查代码给您书面回复，可以吗老师？」

**C. 明确不会（诚实且不失分）**
> 「这块我没做到位，我不敢瞎说。我目前的理解是……（说 30 秒你确实知道的部分），更准确的部分我回去确认后写成文档给老师，可以吗？」

> C 式的关键：**先承认、再给出你确实知道的部分、最后给一个明确的交付承诺**。这比硬编答案得分高得多。

### 8.4 高频问题接住路径

| 高频问题 | 接住人 | 一句话锚点 |
| --- | --- | --- |
| 「你们数据库怎么设计的？多少表？」 | 5 → 1 | 5 讲 66 张表 / 9 个视图 / 186 项菜单 / 7 部门 7 岗位 / 8 账号；1 补 6 个 Maven 模块划分 |
| 「AI 用的大模型什么？为什么不用本地？」 | 4 | DeepSeek 兼容 OpenAI 协议，换 base URL 即可换模型 |
| 「AI 的回答准吗？会不会瞎编？」 | 4 → 6 | 4 讲三道防线：业务提示词 + 五种 mode 限定 + 只基于 20 条真实记录；6 补 4002 |
| 「权限怎么管的？」 | 6 → 5 → 3 | 6 讲 228 处注解与 8 角色矩阵；5 讲 186 项菜单粒度（99 + 44 个按钮）；3 讲前端 `can()` 与 router 守卫 |
| 「为什么返回 200 而不是 403？」 | 6 | 统一响应约定，body 里 `{"code":403}`，前端按 code 分支处理 |
| 「有没有测试？覆盖率多少？」 | 7 | 6 个测试类 32 用例全过、60 项 SQL 自检全 PASS、前端 build 通过；覆盖率诚实说未做量化统计 |
| 「登录怎么做的？密码安全吗？」 | 6 → 2 | RuoYi 底座自带认证 + JWT；演示密码仅限演示环境，生产必须改 |

| 「冲销/反审怎么做？」 | 2 或 7 | 承认当前缺失（不足第 5 条），设计方向：新增红冲单据而非改原单 |
| 「这个项目最大的收获？」 | 7 → 1 | 7 说工程规范与安全意识；1 说完整链路落地经历 |

### 8.5 统一答复口径（涉及多个席位的问题，统一说同一句）

以下问题会跨席位，**如果多人分别回答，会出现口径不一致，反而显得没商量过**。指定**唯一主答人**，其他人只在被点名时补充。

| 问题 | 唯一主答人 | 统一口径（照念） |
| --- | --- | --- |
| 「你们项目总共写了多少代码 / 多少表 / 多少接口？」 | 席位 1 | 「数字我们统计过：后端 6 个 Maven 模块 325 个 java、43 个 REST 控制器、260 个方法级接口、228 处 `@PreAuthorize`；数据库 66 张表、9 个视图、186 项菜单；前端 31 个 .vue、15 个 .ts 共 4953 行；测试 6 个类 32 个用例，SQL 自检 60 项。这些都可以当场用 `find` / `wc` / `select count(*)` 查出来。」 |
| 「这个系统能不能真正拿去用？」 | 席位 7 | 「它是实训环境，演示数据和流程是完整的、能跑通；但要上生产，缺的就是我刚才说的那六条：迁移版本化、冲销、审批分级、报工复核、权限归属收敛、AI 数据脱敏。功能完整度和工程化程度是两回事，我们这两头都要说实话。」 |
| 「技术上还有什么没做好的？」 | 席位 7 | 「六条不足我刚才讲过了。另外从工程角度看还有一条：没有 CI，我们的所有验证是本地手工跑的。如果要补，第一件事是把这三样接进流水线 —— 4 个 SQL 自检脚本共 60 项、6 个测试类 32 个用例、前端 build，它们其实已经可以自动化了，只是还没做这一步。」 |
| 「你个人负责的部分，如果现在让你重做，哪里会改？」 | 本人 | 「我这块最大的问题是 XXX（对应 §4.3 那条不足），我会先 XXX，再 XXX。」 —— **每人一条，不得重复** |

### 8.6 答不上来时的备用答案（背下来，总会用上）

技术问题答不上来时，**最忌讳的是硬编**。下面这三句按顺序用，任何一句都不会扣分：

1. **诚实 + 给已知部分**：
   > 「这块我了解的是前半段 —— XXX。后面的实现细节我不敢给您不准确的答案。我的实现是 XXX，能给您看代码，但更深一层的原理我需要回去确认一下。」

2. **转交 + 明确边界**：
   > 「这块 XX 比我在行，我请他补充一下。我能确定的是 XXX，更具体的实现让他来说会更准确。」

3. **兜底承诺**（前两条都不适用时）：
   > 「这个我确实没做到位，我不想给您一个听起来对但可能错的答案。我会后查代码、跑一遍验证，整理成书面说明发给您，可以吗老师？」

**配套动作**：用到第 3 句时，**当场在纸上记下问题**，并当场说「我记下来了」。老师会认为这是负责任的表现。

### 8.7 问答时间管理

- 老师提问后，**应答 30~45 秒**。超过 60 秒就是我们的时间在被吃掉。
- 若老师问超大范围问题（「讲讲你们的架构」），**先收窄再答**：「架构我分四层讲，我用一分钟过一遍整体，重点说其中一层可以吗？」
- 问答剩余 1 分钟时，由席位 1 提示：「老师，我们大概还有一分钟，如果还有问题我们会后整理一份文档发给您。」

### 9.1 风险预案表

| # | 风险场景 | 触发条件 | 应对策略 | 具体话术 |

| 10 | **老师问「你们怎么保证项目不是 demo / 能交付吗」** | 老师质疑工业性 | 亮工程证据：数据库自检脚本、单元测试、前端 build、可复现的演示账号体系 | 「我们有三层验证：一层是数据库层的 4 个自检脚本共 60 项；一层是代码层的 6 个测试类 32 个用例；一层是权限层的 228 处注解核对加 8 角色矩阵。演示用的 8 个账号是按八角色建的，能当场切角色验证隔离。生产化还差的东西我也清楚，就是刚才说的那六条不足。」 |

| 12 | **老师指出「你们没有做三级审批流」** | 老师按市面 ERP 预期提问 | 主动澄清（这题对我们有利，因为是我们先说的） | 「对，我们目前没有上工作流引擎，也没有做多级会签，这不是没做完，是明确的第一版边界。我们的审批形态是两段式：草稿 → 生效，然后权限点分离，`:add` 和 `:confirm` 分开授权。多级会签和金额分级审批我们列成了后面的演进项。」 |

## 10. 答辩前演练计划

### 10.1 阶段划分

| 阶段 | 时间 | 目标 |
| --- | --- | --- |
| 阶段一：分稿定稿 | D-7 ~ D-5 | 每人写完自己那一节的讲稿，进入附录题库试答 |
| 阶段二：单人抠稿 | D-4 ~ D-3 | 逐人过稿，纠正讲稿与事实不符之处 |
| 阶段三：串联彩排 | D-2 | 全流程串讲一遍（含演示），掐表 |
| 阶段四：对抗演练 | D-1 | 交叉互问，用附录题库 + 自编刁钻问题压测 |
| 阶段五：走场踩点 | 答辩当天 | 设备、账号、浏览器、网络、演示数据全部就位 |

### 10.2 每日任务

**D-7（分工与口径对齐）**
- 全员通读本方案，确认自己的「负责什么 / 不负责什么」
- 明确每人的**边界**：自己的产出文件清单（不超过 6 项，能当场翻出来）
- 统一 §4.1 的两版回答，逐字记熟

**D-6（技术讲稿初稿）**
- 每人写自己的讲稿初稿，口播稿必须写成**可以直接念出来**的口语，不能是书面文章
- 每人准备 **3 个「我能当场证明」的动作**（跑哪个脚本、点哪个页面、跑哪个测试）

**D-5（讲稿定稿 + 术语过关）**
- 讲稿定稿，各自计时（超时当场删内容，删最弱的一条）
- 全员各自把附录 20 题过一遍，写出自己不会的题，汇总
- **术语过关检查（集体必考）**：八角色名称、`sd_order` 七个状态值、8 个业务错误码（1001/1002/2001/2003/2005/2006/2007/4002）、六条一致性红线名称 —— 全员必须能当场报出

**D-4（单人抠稿，1 号主审）**
- 1 号逐人听讲稿，重点听三件事：有没有说超出自己范围的话、有没有夸大工作量、有没有书面腔
- 超出范围的表述当场改掉，这是**红线**

**D-3（追问演练）**
- 每人准备本节「可能被追问的问题」的答案，逐字记熟
- §4.3 的「不足 + 改进」每人一条，写成固定的两句话，练到能脱口而出

**D-2（全流程串联彩排 + 演示彩排）**
- 完整计时串讲一遍
- 演示部分至少完整跑 3 遍：第 1 遍跑通，第 2 遍练衔接，第 3 遍压缩到时间盒

## 11. 演示环节设计

### 11.1 定位

**演示是答辩的证据环节，不是表演环节。** 唯一目标是回答「你说的权限隔离和账实一致，是真的吗」。所以只做一条主线：**同一件事，换个人看，结果不一样**。不做功能巡游。

### 11.2 演示顺序（操作 1'43" + 讲述 20" ≈ 2'03"，席位 6 主讲，席位 3 负责操作，席位 1 计时）

| 时段 | 动作 | 讲什么 | 对应证明点 |
| --- | --- | --- | --- |
| 0:00-0:20 | 屏幕切到 `web/controller/` 目录，展开 erp 下 18 个控制器，再打开任意一个的 `@PreAuthorize` | 「这一层一共 43 个控制器、228 处权限注解。注解管能不能调这个接口，数据范围管能看见哪些行。」 | 权限覆盖是量化的 |
| 0:20-0:40 | 展示 `SystemPermissionGuardTest` 代码 + 运行它 | 「这个测试用反射扫描所有 controller 方法，断言每个都有注解，4 个用例。现在跑一遍。」 | 覆盖被工程手段锁住，不是口头承诺 |
| 0:40-1:00 | 跑 `sql/p4-rbac-completion.sql` | 「7 项自检，验的是 8 个角色的权限是不是真的授到位了。全部 PASS。」 | 矩阵落到数据，不靠人工点 |
| 1:00-1:35 | **切到浏览器**：用 **admin** 账号登录 → 侧边栏有「系统管理」→ 打开用户管理 → 正常增改 | 「admin 是通配放行，操作正常。」 | 正向路径可用 |
| 1:35-1:58 | **切到 sales 账号** → 地址栏直接敲 `/system/users`，再直接打接口 | 「菜单里看不到，硬敲地址被守卫拦回无权限页；直接打接口是 HTTP 200 加 `{"code":403}`。前后端两道都验了。」 | 越权被挡 + 拒绝约定（200 + code 403） |
| 1:58-2:03 | 收回讲台 | 「演示到这里，验证方式我们也有脚本化的一套。」 | 交给席位 7 |

**演示动作的叙述纪律**：从切浏览器到点开系统管理页面的那一下，**必须由席位 6 口述「我们切到浏览器」「这是 admin 的视角」「现在换 sales」，否则老师会以为是在看一张静态截图**。这是演示中最容易失去说服力的一段，务必提前彩排。

**screen 与讲述的配合原则**：任何一张截图只能证明「做过什么」，不能证明「现在还能跑」；因此演示中**至少保留一次真实点击与一次真实接口返回**（sales 的 `{"code":403}` 响应体），这两样是全场唯一能证明系统当下可用的证据，优先级高于任何截图。

### 11.5 演示动作推荐排序

1. **权限隔离对照**（最推荐）—— admin 与 sales 两个视角，同一条路由、同一个接口，一个通、一个被挡，配 228 处注解与 4 用例护栏，构成完整工程闭环。

3. **单据状态机流转**（第三）—— 展示 `sd_order` 从草稿到已确认；可顺带说非法跳转返回 `2001`。
4. **AI 业务问答五种模式 → 提问 → 返回分析**（第四）—— 重点展示「先过权限、再取数、最多 20 条」这条链，不是自由聊天框。
5. **60 项 SQL 自检全绿**（第五）—— 体现验收脚本化，尤其库存与流水双向对账那一项。

**不建议演示**：完整的进销存 CRUD 巡游（太长、看不出深度）、登录注册流程（不是亮点）、任何需要联网调 DeepSeek 的实时 AI（网络延迟不可控）—— AI 用录屏或截图。

## 13. 附录：常见提问与参考答案（20 题）

> 标注「★」的为高风险题，务必逐字记熟。

**1. 这个项目到底是干什么的？能用一句话说清楚吗？**
海岚 ERP 是面向服装制造企业内部管理系统，覆盖主数据（物料/BOM/客户/供应商/员工）、业务单据（销售、采购、生产、库存）、组织与权限、AI 业务问答四条线。它的定位是企业内部管理平台，不是面向外部客户的电商系统。

**2. 为什么选 RuoYi 做底座？是自己写的吗？**
底座是 RuoYi，这是我们从一开始就定的策略：权限框架的坑很多（数据范围、菜单权限、登录态、审计日志），实训项目里重造一遍收益低、风险高。我们把增量放在了业务纵深上 —— 系统管理的 M→C→F 三级菜单、dataScope 的部门集合绑定、以及 AI 问答的受控流程，都是针对海岚的管理诉求自己设计的。

**3. 你们的权限是怎么做的？**
RuoYi 的方法级授权：Controller 上 `@PreAuthorize("@ss.hasPermi('...')")`，admin 用 `*:*:*` 通配放行。权限串是三段式 `模块:实体:操作`。除了操作权限还有数据范围（dataScope）：角色绑定部门集合，SQL 按 `dept_id` 过滤。前端还有 `meta.permission` 路由守卫做体验层拦截。真正不可绕过的防线只有后端那一层。

**4. ★ 权限这块你们具体做了什么？怎么证明它有效？**
三层都落了实：第一层，43 个控制器上 228 处 `@PreAuthorize` 逐条与 `sys_menu.perms` 对齐，前端 99 个业务按钮权限 + 44 个系统按钮权限和后端用的是同一套三段式权限串；第二层，8 个角色的权限矩阵，`sql/p4-rbac-completion.sql` 用 7 项自检验授权是否真的到位；第三层，系统管理四个模块（用户/角色/菜单/部门）只授给 admin，其他 7 个角色一条 `system:*` 都没有。证明方式也不是靠说 —— `SystemPermissionGuardTest` 4 个用例反射扫描、`ErpAccessTest` 3 个用例验行为、再加 sales 账号实测返回 `{"code":403}`。

**5. ★ 那为什么功能测试测不出权限问题？**
因为越权/漏权的测试条件是「权限不足的人执行操作」，而常规功能测试用 admin 把功能点了一遍就收工 —— 这类用例根本不会被写进用例集。所以我们换了思路，不靠功能测兜底，而是加结构性测试：`SystemPermissionGuardTest` 用反射扫描所有控制器方法，断言每个都带 `@PreAuthorize`，缺一个就失败。这条测试的价值是它把「一整类问题」锁住了，而不是锁住某一个 bug。

**6. 权限被拒绝的时候返回什么？**
两层分开：框架层的权限不足返回 HTTP 200，body 是 `{"code":403}`；业务数据范围不足返回我们自己的 `4002`（`ErpErrorCode.DATA_SCOPE_DENIED`）。这是 RuoYi 的统一响应约定，权限拒绝被当作一次正常业务结果封装。代价是 HTTP 层语义丢失，网关和监控看不到异常流量；我们的处理是前端在统一拦截器里集中判断业务码，不在页面里散着判。

**7. 前后端都做了权限校验，是不是重复？**
不是，目标不同。前端管「看不见」，后端管「做不了」。只有前端则改 URL 即可绕过，只有后端则用户看到入口点进去白屏报错。两套必须同时存在，且权限串命名要严格一致，我们用 `system:user:list` 这种三段式命名来保证前后端对齐。

**8. 数据库怎么建的？有没有用迁移工具？**
没有用 Flyway/Liquibase，这是我们的不足。现在是一组按阶段编号的幂等脚本，`sql/` 下 30 个共 33932 行，主链是 `platform-schema` → `init_all` → `erp-permissions` → `ai-erp-13-seed-rich` → `ai-erp-14-boss-permissions` → `p4-rbac-completion` → `platform-demo-users` → `system-permissions` → `self_check`。其中 `system-permissions.sql` 是 147 行，所有插入前判存在性，重复执行不产生重复数据也不报错，里面是 54 项系统管理段菜单（1 目录 + 9 菜单 + 44 按钮，menu_id 90200–90299）、7 个部门、7 个岗位、8 个演示账号部门回填、admin 的 54 项授权。正确做法是引入 Flyway 拆成带版本号的迁移文件，这也是我们写进总结的第一条改进项。

**9. 你们的 SQL 自检是干什么的？**
四个脚本共 60 项：`self_check.sql` 29 项、`p3-chain-integrity.sql` 15 项、`p4-rbac-completion.sql` 7 项、`p2-demo-data-consistency.sql` 9 项，全部 PASS。验的是「配置漂移」和「账实不符」这两类问题 —— 权限写进代码但没写进库、账号没绑部门、库存流水加总对不上库存余额，这类问题代码上完全看不出来但功能就是不好使。它不只是数数量，还做双向对账：`self_check.sql` 第 3 项正着查流水加总、反着查每笔库存有没有流水来源；第 12 项核对 `v_style_cost` 的合计必须等于「已确认结算单」的真实合计（不写死数字，跑完新业务仍成立）。

**10. 用户列表要显示角色名，你是怎么实现的？**
在 `SysUserMapper.xml` 的 `selectUserList` 里用 `group_concat` 标量子查询聚合角色名。没用 join 是因为 join 用户角色关系表会让行数膨胀，一个用户三个角色就变三行，PageHelper 分页 count 也会跟着膨胀导致分页出错。标量子查询返回单值、不参与外层行展开，count 不受影响，还能用 `group_concat` 的分隔符控制显示格式。

**11. 你们的单据是怎么保证状态不被乱跳的？**
服务端状态机。`sd_order` 七个值（0 草稿 / 1 已确认 / 2 生产中 / 3 已完工 / 4 已出货 / 5 已完成 / 9 已取消）、`sd_quotation` 四个值（含 3 已转单）、`pu_purchase_order` 五个值、`pr_work_order` 三个值、`sh_shipment` 四个值，流转关系在服务端和数据库层都有表达，非法跳转直接返回 `2001`。前端把不合法的按钮置灰只是防手滑，真正拦住的是服务端校验。这也是「服务端权威」这条一致性红线的直接体现 —— 前端只显示，不参与裁决。

**12. 你们的一致性是怎么保证的？**
总结成六条红线：只增不改（流水类数据写入后永不修改，纠错走冲销）、原子提交（状态变更 + 库存副作用 + 计件副作用同事务）、幂等（带 `requestKey`，同键只生效一次，参数不同复用同键返回 `2007`）、服务端权威（金额/可发量/成本全服务端算）、冻结优先（工单冻结 BOM 工价，结算冻结价格快照）、留痕（所有动作记录操作人、时间、来源单据）。

**13. AI 问答是怎么做的？为什么不做成自由问答？**
接的 DeepSeek **HTTP 接口**（不是 Spring AI），配置在 `DeepSeekConfig.java`，base URL 是 `https://api.deepseek.com/v1`。不做自由问答有两个原因：一是幻觉，模型会编造系统里不存在的订单和库存数；二是成本和延迟不可控。所以收窄成受控流程：`POST /ai/erp/ask` 带 `{mode, question}`，mode 只有订单/库存/缺料/成本/准时率五种；系统先校验 `dashboard:overview:list`，再按 mode 映射到对应读权限；然后跑一条 `LIMIT 20` 的只读查询，把这最多 20 条真实数据和问题一起交给模型分析。模型只解释查询结果，不生成 SQL、不改单据；不可用时降级为规则摘要。越权查询返回 `4002`，超过 10 次/分钟或问题不在 1~500 字内直接拒绝。

**14. 提示词是怎么保证效果的？**
两层。第一层是硬约束写进提示词：数据边界仅限服装制造的主数据和单据、禁止推测记录之外的信息、无依据必须明说、固定输出三段格式。第二层是测试兜底：`ErpAiPromptsTest` 9 个用例断言提示词必须包含关键约束片段，改提示词改坏了测试直接红。另外 `DeepSeekConfigTest` 7 个用例管配置，`DeepSeekConfigKeysTest` 4 个用例管 Key 的缺失与异常分支，共 20 个。坦白说我们只有人工评估集，没有自动化评估。

**15. ★ 用大模型会不会泄露企业数据？**
这是真实风险，我们的处理是控制出境数据面而不是假装不存在：只发送用户选定范围内查出的最多 20 条记录、推送前裁剪非必要字段、API Key 和 base URL 全部走环境变量，不同环境可指向不同服务。不够的地方也承认：没有做传输层额外加密和字段级脱敏的完整策略，这是明确的不足。

**16. 你们的测试是怎么做的？覆盖率多少？**
分三层：代码层 6 个测试类 32 个用例全过 —— `ErpAiPromptsTest`(9)、`DeepSeekConfigTest`(7)、`DeepSeekConfigKeysTest`(4)、`ErpDraftUpdateTest`(5)、`ErpAccessTest`(3)、`SystemPermissionGuardTest`(4)；数据库层 4 个自检脚本共 60 项全 PASS；权限层 228 处注解核对、8 角色矩阵 7 项自检、sales 账号实测返回 `{"code":403}`。覆盖率我们必须诚实说：没有量化统计，工具链里没有接 JaCoCo，我们用的是用例清单式统计，集中在权限注解、AI 提示词、配置分支、草稿更新这些高风险点。

**17. ★ 为什么自检要写成 SQL，而不是都写成单元测试？**
因为两边防的风险不同。单测防函数级逻辑错，但它绕过了路由、参数绑定、序列化、权限拦截、事务，也看不到真实数据的自洽性；SQL 自检正好验的是「这堆数据现在是否自洽」。举两个实际抓到的例子：一个是 `AjaxResult.put()` 是顶层 map put，`authRole` 的 `user`/`roles`/`menus`/`checkedKeys` 在响应顶层而不在 `data` 下 —— 这个只有真跑一遍链路才暴露；另一个是库存流水加总对不上库存余额 —— 这个你写 Java 测试要造一整套数据，写成一条 SQL 双向对账就完了，`self_check.sql` 第 3 项就是干这个的。

**18. 业务上「删除」和「作废」为什么分开？**
软删除解决「还能不能查到」，作废解决「这笔单据在业务上还算不算发生」，是两个不同维度。单据侧不提供物理删除入口，只有草稿能删，提交后只能作废，因为库存台账、报表、审计日志都引用单据号，物理删掉账就对不上。软删除是存储层手段，作废是业务语义层状态，不该用同一个动作混着做。

**19. ★ 这个项目最大的收获是什么？如果重做一次会改什么？**
收获是我们搞明白了一件事：企业系统里最危险的问题不是功能做不完，是「看起来做完了」。功能点全绿，权限、账实一致性这些地方仍可能是空的 —— 所以我们把验证从「点页面」换成了「跑脚本」：60 项 SQL 自检、32 个用例、228 处注解核对。我们重做会先补工程化而不是先补功能：引入 Flyway 做版本化迁移、把权限验证从单一角色扩展成「8 角色 × 敏感接口」的参数化矩阵、把 AI 的人工评估集固化成自动化回归、把 60 项自检接进 CI。另外我们清楚的六条不足是：审批只有两段式无工作流、无金额分级审批、自审问题、无冲销流程、报工无复核、无 CI 无覆盖率统计。

**20. ★ 团队是怎么分工的？你具体负责什么？**
分工依据是可独立验收的交付物，按「18 个 ERP 业务控制器 + 4 个前端页面群」两条坐标切，不是按人头平摊。XXX（成员2）负责主数据与销售域的 7 个控制器和页面群 A；XXX（成员3）负责前端框架层（`router.ts` 26 条路由、`api` 6 个模块 1015 行、`stores/user.ts` 的 `can()`）和页面群 B 的 10 页；XXX（成员4）负责 AI 问答（`ErpAiQuestionController`、`DeepSeekConfig.java`、3 个测试类 20 个用例）和页面群 D 的 5 页；XXX（成员5）负责 66 张表、9 个视图、30 个 SQL 脚本和 4 个自检脚本共 60 项；XXX（成员6）负责 228 处注解核对、8 角色矩阵和 `SystemPermissionGuardTest`；XXX（成员7）负责生产/成本/人事的 10 个控制器、页面群 C 的 10 页和验证体系。我（成员1）负责整体架构、平台级 2 个控制器和演示统筹。请老师针对我这一块提问。
