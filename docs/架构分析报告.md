# 海岚 ERP 架构与设计分析报告

> 分析基线：`master` 分支，代码截至 2026-10-28。
> 分析方式：静态代码走查 + 演示库 `hai_erp` 实测（自检脚本 29 项、单据链路补丁 15 项、权限补丁 7 项全部 PASS）。

---

## 0. 结论速览

| 维度 | 结论 |
| --- | --- |
| 项目本质 | 服装制造 B2B ERP。RuoYi 底座 + 一条**自研的完整业务纵切** |
| 真实自研代码量 | 后端 **约 6,600 行**（18 个 ERP 控制器 1,276 行 + `erp` 包 5,051 行 + 2 个系统扩展控制器 199 行 + AI 配置 93 行）、前端 **4,953 行** |
| 仓库后端总量 | **37,037 行 / 325 个 Java 文件**（遗留制造模块已彻底移除，不再是"15 万行底座"） |
| 核心数据模型 | **47 张业务表** + 19 张平台表 + **9 个视图** |
| 权限模型 | RuoYi RBAC：`sys_user → sys_role → sys_menu.perms`，**228 处生效的 `@PreAuthorize`**（另有 21 处历史注释）、186 项菜单（ERP 132 项 = 1 目录 + 32 菜单 + 99 按钮），8 个岗位角色 |
| 接口规模 | **260 个方法级端点**，43 个 REST 控制器（自研 20 个） |
| 业务闭环 | 报价 → 订单 → 缺料 → 采购 → 收货 → 工单 → 领料/报工 → 完工 → 发货 → 退货 → 标准成本 → 下一轮报价 → 应收/收款 |
| 最重要的架构特征 | **配置/元数据驱动的窄代码面**：10 个主数据资源共用一个控制器 + 一份字段 Spec；30 余个列表页共用 1 个 CatalogView |
| 最大的架构风险 | 不再是"遗留模块"，而是**权限靠 SQL 脚本手工维护**与**读接口无类型契约**——漏一条 perm 或改一个字段名都不会编译报错 |

一句话：**底座稳定、纵切完整、边界清晰**。项目用约 1.15 万行自研代码 + 一份元数据配置，把服装 ERP 的"报价—订单—采购—生产—库存—出货—成本—资金"闭环的状态机、幂等、事务与权限都讲清楚了；遗留的 15 万行存量代码已清理出仓库，原来的最大技术债已经还掉。

### 3.1 两个"通用化"设计（省代码的关键）

**(a) 主数据 CRUD 元数据驱动** — `ErpMasterController` + `ErpMasterSql.SPECS`

```java
// 一个控制器处理 10 个资源：category/color/size/style/material/process/customer/supplier/sku/hr...
@PreAuthorize("@ss.hasPermi('md:' + #resource + ':list')")
@GetMapping("/{resource}/{id}")
public AjaxResult detail(@P("resource") @PathVariable String resource, ...)
```

权限字符串用 SpEL 拼接 `'md:' + #resource + ':list'`，并用 `@P("resource")` 显式绑定参数名（避免 `-parameters` 编译开关缺失导致 SpEL 取不到变量）。表名/列名/类型/必填/最大长度/默认值全部写在 `ErpMasterSql.SPECS` 里，**加一个主数据资源 ≈ 加一行 Spec + 一条 sys_menu**。

**(b) 只读聚合** — `ErpReadController` / `ErpModuleReadController`

看板、缺料、库存、流水、工资单等只读列表集中在两个控制器里，用 `@PreAuthorize` 逐条标注权限，前端 `catalog.ts` 的每个表格配置直接对应一个 `/erp/**/list` 路径。这就是"28 个页面共用 CatalogView"的后端配合面。

### 3.2 幂等设计（值得保留的工程习惯）

`biz_action_request` 表做跨业务动作的统一去重：

```java
// ErpStockService.begin(...)
mapper.reserveAction(key, action, targetType, targetId, hash, username);  // ON DUPLICATE KEY UPDATE 占位
Map prior = mapper.action(key);                                          // SELECT ... FOR UPDATE
if (!action.equals(prior.actionType) || !hash.equals(prior.payloadHash))  // SHA-256(payload)
    throw new ServiceException("请求键已用于不同操作或参数", 2007);
return prior.status == 1;   // true = 该请求已成功执行过，直接返回首次结果
```

- 前端每次动作生成 `crypto.randomUUID()` 作为 `requestKey`。
- 同一 key + 同一 payload → 返回首次结果；同 key + 不同 payload → `2007` 冲突。
- 动作记录与库存流水、库存结存在**同一事务**内（`@Transactional`）。

这套机制解决了"用户狂点提交 / 网络重试导致重复入库"的经典问题，比单纯唯一索引更完整。

### 3.3 状态机与副作用

单据状态只能通过动作端点迁移，例如 `sd_order.status`：
`0 草稿 → 1 已确认 → 2 生产中 → 3 已完工 → 4 已出货 → 5 已完成`，`9 已取消`。
报价单另有 `1 已接受 → 3 已转单`，转单由"建订单时带 `quoteId`"触发，`markQuoteConverted` 用条件更新保证并发下只能成功一次，重复转单返回 `2006`。

服务层在迁移前校验：上一步状态、下游是否存在、数量上限（如报工合格数不能超过上一工序合格数或冻结计划量）、库存是否足够、会计期间是否已结账（`workflow.assertOpen`）。

## 4. 前端设计

### 4.1 三层结构

```
router.ts  ── 全局守卫：token → load() → 角色识别 → 权限判定 → /forbidden
   │
roles.ts   ── 8 个岗位的 profile（label/heading/focus/navigation）
   │
views/     ── 2 类页面
   ├─ 业务操作页（10 个）：Orders/OrderDetail/OrderForm/Purchases/PurchaseDetail/
   │                      PurchaseForm/QuotationDetail/WorkOrderDetail/ShipmentDetail/
   │                      StylePlan/SettlementDetail/Finance/RoleDashboard/AiAssistant…
   └─ 通用页（CatalogView）：由 api/catalog.ts 的配置驱动，覆盖主数据、人事、报表等列表
```

`router.ts` 的守卫处理**两种身份**：真实登录（JWT）与无权限（`/forbidden`）；每个路由都带 `meta.permission`，没有权限直接跳 `/forbidden`，不靠"藏菜单"兜底。原来的 `/preview` 演示身份与 `api/demo.ts` 浏览器 mock 已删除，前端只有真实接口一条数据路径。

### 4.2 配置驱动的通用表格页

`catalog.ts` 用一张表描述每个菜单页：

```ts
styles: { title:'款式', path:'/erp/md/style/list', permission:'md:style:list',
          columns:[{prop:'code',label:'编码'},{prop:'name',label:'名称'},…] }
```

加一个列表页 = 加一段配置 + 一条 sys_menu，**不需要新写 Vue 文件**。`masterForms` 同理描述新增/编辑表单字段（含 `kind` 类型、必填、默认值），`masterResource()` 做 URL 段到资源名的归一（`categories→category`、`employees→employee`）。部分目录（计件、工资单、工单、出货、资金流水）支持 `filter:'month'`，页面上会出现年月选择器，后端对应端点接 `month` 参数。

### 4.3 状态文案集中维护

`api/labels.ts` 把 91 条"状态码 → 中文标签 + 标签色"收在一处（`sdOrderStatus`、`quoteStatus`、`shipmentStatus`、`periodStatus`…），各视图统一 `enumLabel()/enumTagType()` 取值，不再各写一套三元表达式。新增状态时必须同步两处：SQL 字段 `COMMENT`（权威定义）与 `labels.ts`（展示副本）—— `3 已转单` 就是这么补进来的。

## 5. 数据模型（47 张业务表 / 9 个视图）

| 域 | 表数 | 表 | 说明 |
| --- | --- | --- | --- |
| **主数据 md_** | 12 | `md_category` `md_color` `md_size` `md_style` `md_sku` `md_material` `md_process` `md_process_worker` `md_customer` `md_supplier` `md_bom` `md_style_process` | 款式-色-码三元组生成 SKU；BOM + 工序挂在款式上；工序可派工到员工 |
| **销售 sd_** | 4 | `sd_order` `sd_order_item` `sd_quotation` `sd_quotation_item` | 订单主子表；报价可引用已确认结算，成交后可一次性转订单 |
| **采购 pu_** | 2 | `pu_purchase_order` `pu_purchase_order_item` | 草稿不计在途，确认后计入 |
| **生产 pr_** | 5 | `pr_work_order` `pr_work_order_sku` `pr_work_order_material` `pr_work_order_process` `pr_process_report` | 建单时**冻结** SKU 计划 / BOM 用量 / 工序工价 |
| **库存 st_** | 3 | `st_inventory` `st_stock_txn` `st_reservation` | 结存按 (item_type,item_id,batch_no,warehouse_id) 唯一；流水只增不改 |
| **出货 sh_** | 4 | `sh_shipment` `sh_shipment_item` `sh_return` `sh_return_item` | 支持按批次分批发货、按剩余可退量退货 |
| **成本/财务 fn_** | 8 | `fn_cost_settlement` `fn_cost_detail` `fn_account` `fn_cash_txn` `fn_receivable` `fn_payable` `fn_payment` `fn_payment_line` | 标准成本试算 → 确认冻结；资金账户、流水、应收应付、收付款核销 |
| **人事 hr_** | 5 | `hr_department` `hr_employee` `hr_payroll_config` `hr_piece_wage` `hr_salary_slip` | 计件明细汇总成工资单 |
| **协作流 biz_** | 4 | `biz_action_request` `biz_todo` `biz_approval` `biz_period` | 幂等键、待办、审批、会计期间 |
| **视图** | 9 | `v_material_last_price` `v_mrp_demand` `v_style_cost` `v_order_ontime` `v_ar_aging` `v_ap_aging` `v_cash_balance` `v_cash_flow_monthly` `v_labor_variance` | 物料最近价、缺料、款式成本、准时率、应收/应付账龄、账户账实、月度现金流、人工差异 |

设计要点：
- **快照式冻结**：工单建单时把 SKU 计划量、BOM 用量、工价写进 `pr_work_order_*`，后续主数据改动不影响在产工单；成本用"冻结 BOM × 物料参考价快照"计算，保证可复算。
- **流水驱动**：采购收货、领料、完工、发货、退货回库、盘点差异**全部**写 `st_stock_txn`，结存表是流水的物化。`sql/self_check.sql` 按 `(item_type,item_id,batch_no,warehouse_id)` 四元组双向核对"结存=流水"。
- **分批发货**：`sh_shipment_item` 记录 SKU + 批次 + 数量，订单"发齐"由累计发货量判定，与"签收"是**两个独立状态**。
- **单据链路可追溯**：应收金额由"出货数量 × 订单单价"生成、到期日由"发货日 + 客户账期"生成，`p3-chain-integrity.sql` 专门校验这条链（15 项），避免出现"订单 ¥7,200、应收 ¥58,200"这类凭空数据。

## 6. 主业务闭环

```
基础档案 → 报价(可引用已确认成本) → 成交 → 转订单(报价置为已转单)
                                      → 订单草稿 → 确认(冻结色码/数量/单价/交期)
                                                    ├─→ 净缺料 = 活动订单BOM需求 − 现存 − 在途未收
                                                    │      └→ 采购草稿 → 确认(计在途) → 分批收货 → 入库流水 → 应付
                                                    └─→ 按订单款式建工单(冻结SKU/BOM/工价)
                                                              └→ 齐套校验 → 领料(只认现存) → 报工 → 完工入库
                                                                        ├─→ 计件明细 → 工资单 → 工资发放
                                                                        └─→ 分批发货 → 发齐 → 签收/退货
                                                                                        └→ 应收 → 收款核销 → 资金流水
                                                                                        └→ 标准成本试算 → 确认冻结 → 下一轮报价
看板 / 规则预警 / 受控 AI 问答  ← 贯穿全链路的只读视图
```

三个容易被误读的边界条件（文档里写得很清楚，代码也一致）：
1. **在途量只参与缺料计算，不参与领料**（领料只认 `st_inventory`）。
2. **发齐 ≠ 完成**：发齐看累计发货量，完成看是否全部出货单签收。
3. **成本是标准成本**，不是实际领料成本；退货不冲回已确认成本。

## 7. AI 设计（克制，值得肯定）

| 能力 | 端点 | 设计 |
| --- | --- | --- |
| 受控业务问答 | `POST /ai/erp/ask` | 前端传 `mode`（orders/inventory/shortage/cost/ontime），后端把 mode **映射成具体权限**再校验，然后跑**预设只读 SQL**，最多 20 条；模型只负责"解释这些记录"，**不生成 SQL、不执行写操作**；`modelUsed=false` 时降级为规则摘要；每用户每分钟 10 次、问题 1~500 字 |
| 规则预警 | `GET /erp/dashboard/alerts` + `POST /erp/dashboard/alerts/explain` | 缺料/逾期由业务 SQL 规则先算，模型只做可选解释 |
| NL2SQL / RAG / 预测 | 无 | 明确不做，避免幻觉与成本失控 |

`ErpAiQuestionController` 的核心防线：

```java
private static final Map<String,String> MODE_PERMISSIONS = Map.of(
    "orders","sd:order:list", "inventory","st:inventory:list",
    "shortage","pu:suggestion:list", "cost":"dashboard:styleCost:list",
    "ontime","dashboard:ontime:list");
if (!permissions.hasPermi(permission)) throw new ServiceException("没有该业务数据权限", 4002);
```

即**二次鉴权**——`@PreAuthorize` 只校验了看板权限，业务数据权限在方法内单独再查一遍。这是本项目最正确的一处安全设计。

## 8. 质量评估

### 做得好的
1. **代码面小且分层清楚**：约 1.15 万行自研代码实现完整 ERP 闭环，靠的是元数据驱动 + 配置驱动，扩展成本低。
2. **幂等 + 事务 + 状态机**三件套齐全，`biz_action_request` 的设计超出一般实训项目水平。
3. **AI 边界清晰**：预设 SQL + 二次鉴权 + 可降级，没有"让模型随便写 SQL"的危险动作。
4. **数据可对账**：29 项 + 15 项 + 7 项自检脚本覆盖库存双向对账、单据链路、权限完整度，能自动发现"幽灵出货单""应收凭空开票""无人拥有的按钮权限"这类隐蔽问题。
5. **权限按岗位落地**：`p4-rbac-completion.sql` 保证每个业务按钮至少有一个岗位能点，并锁死厂长资金域只读；`SystemPermissionGuardTest` 用反射扫描断言控制器方法都带 `@PreAuthorize`，防回归。

### 明确的架构债

| # | 问题 | 证据 | 影响 | 建议 |
| --- | --- | --- | --- | --- |
| 1 | **ID 类型文档与实现不一致** | 文档称"所有 ID 在 JSON 中为字符串"；但仓库内**无任何 Jackson 配置**，BIGINT 直接序列化为 number | 前端目前按 number 传递恰好工作，但 JS 安全整数上限 2^53 是潜在坑 | 加 `ToStringSerializer(Long.class)` 全局配置，或修订文档 |
| 2 | **SQL 全注解内联，无 XML** | `erp/mapper/*.java` 内 `@Select/@Insert` 三引号文本块；无 `*Mapper.xml` | 与 RuoYi 底座"XML 为主"的惯例不一致，长 SQL 无格式化/复用 | 复杂查询下沉到 `resources/mapper/erp/*.xml`；动态拼接务必保持参数绑定 |
| 3 | **读接口大量返回 `Map<String,Object>`** | `ErpOrderController.list` 等返回 `List<Map<String,Object>>` | 无类型契约，字段改名不报错；前端 `columns.prop` 靠字符串对齐 | 关键列表引入只读 record DTO |
| 4 | **权限与菜单靠 SQL 脚本维护** | `sql/erp-permissions.sql` + `p1`/`p4` 按 `perms` 字符串授权 | 新增端点若忘登记 `sys_menu`，前端按钮不出现、后端却已放行；本轮就查出 34 个按钮权限无人拥有 | 已有 `p4` 自检兜底；可再加一条"代码中的 perm 与 `sys_menu.perms` 求差集"的构建期检查 |
| 5 | **状态语义双份维护** | SQL 字段 `COMMENT` 是权威定义，前端 `labels.ts` 91 条是手抄副本 | 新增状态漏改一处，页面会显示成"未开工"或空白标签 | 由后端下发枚举字典接口，前端只做渲染 |
| 6 | **报价转订单的舍入取舍** | `ErpQuotationService.fromSettlement` 先按 2 位小数算收入，再乘回数量 | 大数量下与"数量 × 单价"有分位差，属已知取舍 | 业务已确认保留；如需精确可在明细上保存原始单价而非反推 |
| 7 | **21 处历史注释掉的权限注解** | `CacheController`/`ServerController`/`SysLogininforController`/`SysUserOnlineController`/`SysBillFrozenController` 里的 `@PreAuthorize` 被 `//` 注释 | 这些端点登录即可访问；其中 `/system/billFrozen` 是本项目自研的单据冻结 CRUD，前端未调用但接口开放 | 把这批权限码补进 `sys_menu` 后统一放开注解，并用 `SystemPermissionGuardTest` 盯住 |
| 8 | **单库直连、无数据级权限** | `application.yml` 单数据源；权限只到功能级 | 满足首期范围，多组织/多工厂时不适用 | 明确写在边界里，不当作缺陷 |
