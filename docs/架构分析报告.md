# 海岚 ERP 架构与设计分析报告

> 分析基线：`master` 分支，代码截至 2026-10-20（HEAD `9a40421`）。
> 分析方式：静态代码走查（未启动服务、未连数据库），结论均标注代码依据。

## 0. 结论速览

| 维度 | 结论 |
| --- | --- |
| 项目本质 | 服装制造 B2B ERP。开源底座 **myFactoryAI（RuoYi 派生）** + 一条**自研的轻量业务纵切** |
| 真实自研代码量 | 后端 **3,408 行**（25 个控制器 + 12 个服务 + 14 个 Mapper）、前端 **2,373 行** |
| 底座代码量 | 后端总量 **199,459 行**，其中遗留制造模块 **149,897 行 / 207 个控制器** |
| 核心数据模型 | **35 张业务表** + 19 张平台表 + **4 个汇总视图** |
| 权限模型 | RuoYi RBAC：`sys_user → sys_role → sys_menu.perms`，**79 条**权限项，8 个岗位角色 |
| 业务闭环 | 订单 → 缺料 → 采购 → 收货 → 工单 → 领料/报工 → 完工 → 发货 → 退货 → 标准成本 → 报价 |
| 最重要的架构特征 | **配置/元数据驱动的窄代码面**：10 个主数据资源共用一个控制器 + 一份字段 Spec；20 个页面共用 1 个 CatalogView |
| 最大的架构风险 | 15 万行遗留模块仍在 Spring 容器中对外暴露，而其表结构未初始化 → 一旦被访问即 500 |

一句话：**这是一个"宽底座 + 窄纵切"的教学/实训型项目**。真正需要读懂的是 3,400 行自研后端 + 2,373 行前端 + 35 张表，其余 15 万行是继承来的、与当前业务无关的存量代码。

### 3.1 两个"通用化"设计（省代码的关键）

**(a) 主数据 CRUD 元数据驱动** — `ErpMasterController` + `ErpMasterSql.SPECS`

```java
// 一个控制器处理 10 个资源：category/color/size/style/material/process/customer/supplier/sku/hr...
@PreAuthorize("@ss.hasPermi('md:' + #resource + ':list')")
@GetMapping("/{resource}/{id}")
public AjaxResult detail(@P("resource") @PathVariable String resource, ...)
```

权限字符串用 SpEL 拼接 `'md:' + #resource + ':list'`，并用 `@P("resource")` 显式绑定参数名（避免 `-parameters` 编译开关缺失导致 SpEL 取不到变量）。表名/列名/类型/必填/最大长度/默认值全部写在 `ErpMasterSql.SPECS` 里，**加一个主数据资源 ≈ 加一行 Spec + 一条 sys_menu**。

**(b) 只读聚合** — `ErpReadController` / `ErpModuleReadController`

看板、缺料、库存、流水、工资单等只读列表集中在两个控制器里，用 `@PreAuthorize` 逐条标注权限，前端 `catalog.ts` 的每个表格配置直接对应一个 `/erp/**/list` 路径。这就是"20 个页面共用 CatalogView"的后端配合面。

### 3.2 幂等设计（值得保留的工程习惯）

`biz_action_request` 表做跨业务动作的统一去重：

```java
// ErpStockService.begin(...)
mapper.reserveAction(key, action, targetType, targetId, hash, username);  // ON DUPLICATE KEY UPDATE 占位
Map prior = mapper.action(key);                                          // SELECT ... FOR UPDATE
if (!action.equals(prior.actionType) || !hash.equals(prior.payloadHash))  // SHA-256(payload)
    throw new ServiceException("请求键已用于不同操作或参数", 2007);
return prior.status == 1;   // true = 该请求已成功执行过，直接返回首次结果
```

- 前端每次动作生成 `crypto.randomUUID()` 作为 `requestKey`（见 `OrderDetailView.vue:58`）。
- 同一 key + 同一 payload → 返回首次结果；同 key + 不同 payload → `2007` 冲突。
- 动作记录与库存流水、库存结存在**同一事务**内（`@Transactional`）。

这套机制解决了"用户狂点提交 / 网络重试导致重复入库"的经典问题，比单纯唯一索引更完整。

### 3.3 状态机与副作用

单据状态只能通过动作端点迁移，例如 `sd_order.status`：
`0 待确认 → 1 已确认 → 2 生产中 → 3 已完工 → 4 已出货 → 5 已完成`，`9 已取消`。
服务层在迁移前校验：上一步状态、下游是否存在、数量上限（如报工合格数不能超过上一工序合格数或冻结计划量）、库存是否足够。

## 4. 前端设计

### 4.1 三层结构

```
router.ts  ── 全局守卫：token → load() → 角色识别 → 权限判定 → /forbidden
   │
roles.ts   ── 8 个岗位的 profile（label/heading/focus/navigation）+ demo 权限正则
   │
views/     ── 2 类页面
   ├─ 业务操作页（10 个）：Order/Purchase/WorkOrder/Shipment/Settlement/Quotation/StylePlan …
   └─ 通用页（CatalogView）：由 api/catalog.ts 的配置驱动，覆盖 30+ 个列表/表单
```

`router.ts` 的守卫同时处理**三种身份**：真实登录（JWT）、演示访客（`/preview`，仅 DEV）、无权限（`/forbidden`）。`canUseAi` 的判定是"有看板权限 **且** 至少有一个业务读权限"，避免只给看板权限的人调用 AI 越权。

### 4.2 配置驱动的通用表格页

`catalog.ts` 用一张表描述每个菜单页：

```ts
styles: { title:'款式', path:'/erp/md/style/list', permission:'md:style:list',
          columns:[{prop:'code',label:'编码'},{prop:'name',label:'名称'},…] }
```

加一个列表页 = 加一段配置 + 一条 sys_menu，**不需要新写 Vue 文件**。`masterForms` 同理描述新增/编辑表单字段（含 `kind` 类型、必填、默认值），`masterResource()` 做 URL 段到资源名的归一（`categories→category`、`employees→employee`）。

### 4.3 双轨数据源：真实接口 vs 演示模式

`api/demo.ts`（575 行）在浏览器内维护一套完整的模拟业务数据，`isDemoMode()` 为真时分流到 `demoApi.*`，256 个字符的假数据也能跑出完整流程。收益是**没有数据库时也能演示全流程**；代价是与真实接口形成**两套契约**，字段变更容易漂移（目前 `catalogPage` 里就为每个特殊路径单独写了 mock 映射，属于维护热点）。

## 5. 数据模型（35 张业务表）

| 域 | 表 | 说明 |
| --- | --- | --- |
| **主数据 md_** (11) | `md_category` `md_color` `md_size` `md_style` `md_sku` `md_material` `md_process` `md_customer` `md_supplier` `md_bom` `md_style_process` | 款式-色-码三元组生成 SKU；BOM + 工序挂在款式上 |
| **销售 sd_** (4) | `sd_order` `sd_order_item` `sd_quotation` `sd_quotation_item` | 订单主子表；报价可引用已确认结算 |
| **采购 pu_** (2) | `pu_purchase_order` `pu_purchase_order_item` | 草稿不计在途，确认后计入 |
| **生产 pr_** (5) | `pr_work_order` `pr_work_order_sku` `pr_work_order_material` `pr_work_order_process` `pr_process_report` | 建单时**冻结** SKU 计划 / BOM 用量 / 工序工价 |
| **库存 st_** (2) | `st_inventory` `st_stock_txn` | 结存按 (item_type,item_id,batch_no,warehouse_id) 唯一；流水只增不改 |
| **出货 sh_** (4) | `sh_shipment` `sh_shipment_item` `sh_return` `sh_return_item` | 支持按批次分批发货、按剩余可退量退货 |
| **成本 fn_** (2) | `fn_cost_settlement` `fn_cost_detail` | 标准成本试算 → 确认冻结 |
| **人事 hr_** (4) | `hr_department` `hr_employee` `hr_piece_wage` `hr_salary_slip` | 计件明细汇总成工资单 |
| **平台** (1) | `biz_action_request` | 幂等键 |
| **视图** (4) | `v_mrp_demand` `v_order_ontime` `v_style_cost` `v_material_last_price` | 缺料、准时率、款式成本、物料最近价 |

设计要点：
- **快照式冻结**：工单建单时把 SKU 计划量、BOM 用量、工价写进 `pr_work_order_*`，后续主数据改动不影响在产工单；成本用"冻结 BOM × 物料参考价快照"计算，保证可复算。
- **流水驱动**：采购收货、领料、完工、发货、退货回库、盘点差异**全部**写 `st_stock_txn`，结存表是流水的物化。便于对账，符合 ERP 常规做法。
- **分批发货**：`sh_shipment_item` 记录 SKU + 批次 + 数量，订单"发齐"由累计发货量判定，与"签收"是**两个独立状态**。

## 6. 主业务闭环

```
基础档案 → 销售订单草稿 → 确认(冻结色码/数量/单价/交期)
                             ├─→ 净缺料 = 活动订单BOM需求 − 现存 − 在途未收
                             │      └→ 采购草稿 → 确认(计在途) → 分批收货 → 入库流水
                             └─→ 按订单款式建工单(冻结SKU/BOM/工价)
                                        └→ 齐套校验 → 领料(只认现存) → 报工 → 完工入库
                                                                        ├─→ 计件明细 → 工资单
                                                                        └─→ 分批发货 → 发齐 → 签收/退货
                                                                                        └→ 标准成本试算 → 确认冻结 → 生成报价
看板 / 规则预警 / 受控 AI 问答  ← 贯穿全链路的只读视图
```

三个容易被误读的边界条件（文档里写得很清楚，代码也一致）：
1. **在途量只参与缺料计算，不参与领料**（领料只认 `st_inventory`）。
2. **发齐 ≠ 完成**：发齐看累计发货量，完成看是否全部出货单签收。
3. **成本是标准成本**，不是实际领料成本；退货不冲回已确认成本。

## 7. AI 设计（克制，值得肯定）

| 能力 | 端点 | 设计 |
| --- | --- | --- |
| 受控业务问答 | `POST /ai/erp/ask` | 前端传 `mode`（orders/inventory/shortage/cost/ontime），后端把 mode **映射成具体权限**再校验，然后跑**预设只读 SQL**，最多 20 条；模型只负责"解释这些记录"，**不生成 SQL、不执行写操作**；密钥不可用时降级为确定性摘要 |
| 规则预警 | `GET /erp/dashboard/alerts` + `POST /ai/alerts/explain` | 缺料/逾期由业务 SQL 规则先算，模型只做可选解释 |
| 底座 AI（管理员） | `/ai/nl2sql/*`、`/ai/insight/*`、`/ai/multimodal/ppt` | 沿用 myFactoryAI 的 NL2SQL + SQL 安全校验 + 11 维洞察 + PPT 生成 |

`ErpAiQuestionController` 的核心防线：

```java
String permission = switch (mode) { case "orders" -> "sd:order:list"; … };
if (!permissions.hasPermi(permission)) throw new ServiceException("没有该业务数据权限", 4002);
```

即**二次鉴权**——`@PreAuthorize` 只校验了看板权限，业务数据权限在方法内单独再查一遍。这是本项目最正确的一处安全设计。

## 8. 质量评估

### 做得好的
1. **代码面极小**：3.4k 后端 + 2.4k 前端实现完整 ERP 闭环，靠的是元数据驱动 + 配置驱动，扩展成本低。
2. **幂等 + 事务 + 状态机**三件套齐全，`biz_action_request` 的设计超出一般实训项目水平。
3. **AI 边界清晰**：预设 SQL + 二次鉴权 + 可降级，没有"让模型随便写 SQL"的危险动作。
4. **文档与代码同步度高**：`docs/业务逻辑图.md` 的 Mermaid 图与 `erp/service/*.java` 的实际校验逻辑基本一致；`开发启动说明.md` 如实标注了"待联调""不在本次范围"。
5. **错误码体系化**：1001/1002 输入、2001/2002 状态、2003/2005 库存、2006/2007 数量与幂等、3001/3002 成本、4001/4002 AI，前端可据码分流。

### 明确的架构债

| # | 问题 | 证据 | 影响 | 建议 |
| --- | --- | --- | --- | --- |
| 1 | **15 万行遗留模块仍被装配并对外暴露** | `scanBasePackages` 含 `net.factoryopen.core` 与 `myfactoryai.manufacturing`；207 个控制器在容器内 | 其依赖的表（`ord_so`、`eng_material`…）**不在 `init_all.sql` 中**，任何遗留路径被访问即 SQL 异常；同时扩大攻击面与启动时间 | 从 `@ComponentScan` 排除 `net.factoryopen.core.**` 和 `myfactoryai.manufacturing.**`；或拆为独立的 optional module |
| 2 | **接口文档与实现不一致（ID 类型）** | `AI-ERP接口设计文档.md` 称"所有 ID 在 JSON 中为字符串"；但**无任何 Jackson 配置**（无 `JacksonConfig`、yml 无 `spring.jackson`），BIGINT 直接序列化为 number | 前端目前按 number 传递恰好工作，但 JS 安全整数上限 2^53 是潜在坑；文档误导后续维护者 | 二选一：加 `ToStringSerializer(Long.class)` 全局配置落实文档，或修订文档 |
| 3 | **SQL 全注解内联，无 XML** | `erp/mapper/*.java` 内 `@Select/@Insert` 三引号文本块；`find -name "*Erp*Mapper.xml"` 为空 | 与 RuoYi 底座"XML 为主"的惯例不一致，长 SQL 无格式化/复用，改条件查全表风险高 | 复杂查询下沉到 `resources/mapper/erp/*.xml`；`ErpMasterSql` 这类动态拼接务必保持参数绑定 |
| 4 | **演示模式与真实接口双轨** | `demo.ts` 575 行手写 mock，含按路径特判的 `demoCatalogPage` | 字段/状态码变更时容易只改一边，联调期出现"演示正常、真实报错" | 从后端导出一份固定 JSON fixture 替换手写 mock；或把 mock 收敛到单一 `fixtures.ts` |
| 5 | **读接口大量返回 `Map<String,Object>`** | `ErpOrderController.list` 返回 `List<Map<String,Object>>` | 无类型契约，字段改名不报错；前端 `columns.prop` 靠字符串对齐 | 关键列表引入只读 record DTO（成本可控） |
| 6 | **`sys_menu` 由 SQL 硬编码，79 条权限靠脚本维护** | `sql/erp-permissions.sql` | 新增权限容易漏（例如某控制器上 `@PreAuthorize` 的 perm 未在 SQL 中） | 增加一条自检 SQL：扫描代码中出现的 perm 与 `sys_menu.perms` 求差集 |
| 7 | **`myfactoryai.profile: D:/factoryopen/myfactoryai/resource`** 写死本机绝对路径 | `application.yml` | 换机器上传/下载功能失效 | 改环境变量 `PROFILE_PATH` |

## 9. 上手路径（建议顺序）

5. `frontend/src/api/catalog.ts` → `views/CatalogView.vue` —— 理解"配一个页"的机制。
6. `frontend/src/roles.ts` + `stores/user.ts` —— 理解 8 岗位如何共用一套页面。

## 10. 一句话总结

**底座很重、纵切很轻、边界很清。** 项目最大的技术价值不在功能多少，而在于用 3,400 行代码 + 一份元数据配置，把服装 ERP 的"订单—采购—生产—库存—出货—成本"闭环的状态机、幂等、事务与权限都讲清楚了；最大的技术债则是那 15 万行没有表结构支撑却仍然活着的遗留模块。
