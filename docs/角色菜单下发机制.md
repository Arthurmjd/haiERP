# 角色菜单下发机制说明

> 本文说明当前 ERP 项目如何按用户角色下发不同菜单，涉及的技术、数据模型、前后端链路及扩展方式。
>
> 代码基线：2026-10-19，分支 `master`。

## 1. 概述

项目采用 **RBAC（Role-Based Access Control，基于角色的访问控制）**，核心是“用户 → 角色 → 菜单/权限”三层多对多关系。

技术栈：

| 层 | 技术 |
|----|------|
| 后端 | Spring Boot、Spring Security、JWT、MyBatis、MySQL（RuoYi 底座） |
| 前端 | Vue 3、Pinia、Vue Router、Element Plus |
| 权限载体 | 菜单实体 + 权限字符串（如 `sd:order:list`） |

权限控制分两层：

1. **菜单可见性**：后端 `GET /getRouters` 按角色返回菜单树，前端据此过滤导航。
2. **接口执行权**：后端 Controller 通过 `@PreAuthorize("@ss.hasPermi('...')")` 二次校验，防止绕过前端直接调接口。

## 2. 数据模型

```
sys_user ──< sys_user_role >── sys_role ──< sys_role_menu >── sys_menu
                                                              ├─ menu_type: M（目录）/ C（菜单）/ F（按钮）
                                                              └─ perms: 权限字符串
```

关键表及字段：

| 表 | 关键字段 | 说明 |
|----|----------|------|
| `sys_user` | `user_id`、`user_name`、`status`、`del_flag` | 用户；`user_id = 1` 为超级管理员 |
| `sys_role` | `role_id`、`role_name`、`role_key`、`data_scope`、`status` | 角色；`role_key` 如 `sales`、`planner` |
| `sys_user_role` | `user_id`、`role_id` | 用户与角色关联，支持一个用户多角色 |
| `sys_menu` | `menu_id`、`parent_id`、`menu_type`、`path`、`component`、`perms`、`visible`、`status` | 菜单/按钮定义 |
| `sys_role_menu` | `role_id`、`menu_id` | 角色与菜单的授权关系 |

`sys_menu` 的菜单类型：

- `M`：目录，用于分组，不直接对应页面；
- `C`：菜单页面，对应一个前端路由；
- `F`：按钮权限，只参与权限字符串校验，不生成路由。

菜单实体（`SysMenu.java`）主要路由字段：`menuId`、`menuName`、`parentId`、`orderNum`、`path`、`component`、`query`、`isFrame`、`isCache`、`menuType`、`visible`、`status`、`perms`、`icon`。

授权数据在 `sql/erp-permissions.sql:92-123` 初始化：先插入菜单（第 4 行起），再按 `role_key` 批量写入 `sys_role_menu`。

## 3. 后端实现

### 3.1 登录

`POST /login` 校验账号密码并签发 JWT：

- `SysLoginController.java:43-51`

Spring Security 通过 `UserDetailsServiceImpl` 加载用户，构建 `LoginUser`，其中包含角色与权限集合。

### 3.2 获取用户信息：`GET /getInfo`

`SysLoginController.java:58-70` 返回：

- `user`：用户基本信息；
- `roles`：角色标识集合；
- `permissions`：权限字符串集合。

组装逻辑在 `SysPermissionService.java:34-70`：

- 管理员（`user.isAdmin()`）直接获得 `admin` 角色和 `*:*:*` 通配权限；
- 普通用户按角色查询 `sys_role_menu → sys_menu.perms`，多角色取并集。

### 3.3 获取菜单树：`GET /getRouters`

`SysLoginController.java:77-82`：

```java
Long userId = SecurityUtils.getUserId();
List<SysMenu> menus = menuService.selectMenuTreeByUserId(userId);
return AjaxResult.success(menuService.buildMenus(menus));
```

`selectMenuTreeByUserId`（`SysMenuServiceImpl.java:132-144`）的处理：

- 管理员：调用 `selectMenuTreeAll`，返回全部 M/C 菜单（`SysMenuMapper.xml:51-55`）；
- 普通用户：调用 `selectMenuTreeByUserId`，通过 `sys_user_role`、`sys_role_menu`、`sys_role` 关联过滤（`SysMenuMapper.xml:76-85`），条件包括：
  - `u.user_id = #{userId}`
  - `m.menu_type in ('M','C')`
  - `m.status = 0`
  - `ro.status = 0`

查询结果再经 `getChildPerms(menus, 0)` 组装成父子树。

最后由 `buildMenus`（`SysMenuServiceImpl.java:166-215`）转换为前端路由结构 `RouterVo`：

- `path`、`component`、`query`
- `hidden`（由 `visible` 决定）
- `meta`（标题、图标、是否缓存）
- `children`（目录递归构建）

### 3.4 接口级权限校验

Controller 使用如下注解：

```java
@PreAuthorize("@ss.hasPermi('sd:order:list')")
@PreAuthorize("@ss.hasRole('admin')")
```

`ss` 是 `PermissionService` 的 Bean 名称，`hasPermi` 从当前 `LoginUser` 的权限集合中判断是否包含目标权限（`PermissionService.java:19-37`）。

另外，`DataScopeAspect` 会根据角色的 `data_scope`（1–5）向 SQL 追加数据范围条件，仅影响**数据查询范围**，不影响菜单下发。

## 4. 前端实现

### 4.1 用户信息与权限加载

Pinia 的 `useUserStore.load()`（`frontend/src/stores/user.ts:40-49`）在登录后依次请求：

1. `GET /getInfo` → 保存 `roles`、`permissions`；
2. `GET /getRouters` → 保存 `menus`。

### 4.2 路由守卫

项目**没有**使用 RuoYi 原版的 `addRoute` 动态注册，而是静态路由 + 守卫：

- 路由表在 `frontend/src/router.ts:7-29`，每条路由带 `meta.permission`；
- `router.beforeEach`（`frontend/src/router.ts:32-51`）读取权限串并调用 `user.can(permission)`，无权限跳转 `/forbidden`。

### 4.3 侧边栏菜单过滤

`frontend/src/App.vue:14-40`：

- `links` 是全部可用导航项的静态清单，每项带 `permission`；
- `roleProfiles[activeRole].navigation`（`frontend/src/roles.ts:11-20`）定义各角色的**主菜单顺序**；
- `primaryLinks`：按角色主菜单顺序取项，并要求 `user.can(link.permission)` 通过；
- `secondaryLinks`：其余有权限、但不在主菜单中的项，展示为“其他授权”。

### 4.4 按钮级权限

视图内通过 `v-if="user.can('...')"` 控制按钮/区块显隐，例如：

- `frontend/src/views/OrdersView.vue`
- `frontend/src/views/DashboardView.vue:45`
- `frontend/src/views/CatalogView.vue:16`

### 4.5 `can()` 判断规则

`frontend/src/stores/user.ts:45-53`：

- 由 `/getInfo` 下发的 `permissions` 逐条与目标权限串比对，命中即通过；
- 支持通配：`*:*:*`（管理员）与任意段通配都能匹配，实现方式是把 `*` 转成正则 `.*`（`permissionMatches`）；
- 前端只有真实登录一条路径，浏览器内的模拟数据分支已移除，因此 `can()` 的结论始终来自后端授权。

## 5. 端到端流程

```
用户登录
   │
   ├─ POST /login ──────────────► 签发 JWT
   │
   ├─ GET /getInfo ─────────────► 角色 + 权限字符串集合
   │
   ├─ GET /getRouters ──────────► 按角色过滤后的菜单树
   │                               admin：全部菜单
   │                               普通用户：user_role → role_menu → menu
   │
   ├─ 前端路由守卫 ─────────────► meta.permission + user.can() → 放行/禁止
   ├─ 侧边栏渲染 ───────────────► roleProfiles 主菜单 + 权限过滤
   ├─ 页面按钮 ─────────────────► v-if="user.can(...)"
   │
   └─ 调用业务接口 ─────────────► @PreAuthorize("@ss.hasPermi(...)") 兜底校验
```

## 6. 当前演示数据

演示库 `hai_erp` 共 8 个角色；ERP 业务段（`menu_id` 90000~90199）共 **132 项菜单**，其中目录 `M` 1 个、菜单 `C` 32 个、按钮权限 `F` 99 个；系统管理段（90200~90299）另有 54 项（`M` 1、`C` 9、`F` 44），只授给管理员。全部菜单项合计 186 项。

各角色在 ERP 业务段的获授权项数（`sys_role_menu`，含目录）：

| 角色 | role_key | 授权项 | 目录 M | 菜单 C | 按钮 F |
|------|----------|--------|--------|--------|--------|
| 计划员 | `planner` | 52 | 1 | 11 | 40 |
| 厂长 | `boss` | 47 | 1 | 30 | 16 |
| 财务 | `finance` | 35 | 1 | 13 | 21 |
| 销售 | `sales` | 34 | 1 | 7 | 26 |
| 仓管员 | `wh` | 27 | 1 | 7 | 19 |
| 生产主管 | `production` | 23 | 1 | 9 | 13 |
| 人事员 | `hr` | 12 | 1 | 4 | 7 |
| 管理员 | `admin` | 全部 | — | — | — |

管理员通过 `*:*:*` 通配放行，不依赖 `sys_role_menu`。授权口径是「谁执行这个动作就授给谁」：财务拿资金域全流程与期间结账，销售拿报价新建/编辑/转订单，计划员拿主数据维护，生产拿一键生成工单与退料，人事拿批量生成工资单；厂长保持业务只读 + 采购审批 + 资金只读，不因补权限获得写权限。`sql/p4-rbac-completion.sql` 负责保证这一点，并带 7 项自检（其中「无遗留孤儿按钮权限」除运维专用的 `monitor:operlog:remove` 外必须为 0）。

对应的登录账号与角色一一对应，演示密码见 `sql/platform-demo-users.sql` 文件头注释。

## 7. 如何新增角色或菜单

### 7.1 新增菜单

1. 在 `sys_menu` 插入菜单记录（`M` 或 `C`），设置 `path`、`component`、`perms`、`visible`、`status`；
2. 在 `sys_role_menu` 为需要该菜单的角色插入授权；
3. 前端新增对应路由（`frontend/src/router.ts`）并标注相同的 `meta.permission`；
4. 在 `frontend/src/App.vue` 的 `links` 中添加导航项；
5. 如需出现在某角色主菜单，在 `frontend/src/roles.ts` 的 `roleProfiles[角色].navigation` 中添加路径；
6. 页面内按钮使用 `v-if="user.can('权限串')"` 控制显隐。

### 7.2 新增角色

1. 在 `sys_role` 插入角色（`role_key` 唯一、`status = 0`）；
2. 在 `sys_user_role` 绑定用户；
3. 在 `sys_role_menu` 授权菜单与按钮权限；
4. 前端 `roleKeys` / `roleProfiles` 增加对应角色配置（`frontend/src/roles.ts`）。

## 8. 注意事项

1. **`/getRouters` 的结果当前未直接用于渲染导航**：`user.menus` 已保存，但侧边栏实际由 `App.vue` 的 `links` 与 `roles.ts` 的 `roleProfiles` 驱动。因此后端菜单配置与前端静态清单需要同步维护，否则会出现“后端有权限但前端看不到”或反之。
2. **管理员特判**：以 `user_id = 1` 判断，而不是 `role_key = 'admin'`。其他账号即使绑定 `admin` 角色，也不会走“全部菜单”分支。
3. **多角色取并集**：权限集合按用户所有角色聚合。
4. **没有前端本地权限规则**：早期用于 `/preview` 演示的 `demoRules` 已随演示模式一并删除，任何权限判断最终都回到后端 `permissions`。
5. **旧角色别名**：前端 `roles.ts` 的 `aliases` 兼容 `supervisor`、`salesAssistant`、`buyer`、`mc`、`dataVisitor` 等历史角色标识。
6. **`data_scope` 与菜单无关**：它只影响数据查询范围。
