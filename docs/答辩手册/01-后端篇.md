## 2. 分层：每一层只干一件事

```
HTTP 请求
   │
   ├─ SecurityFilterChain（JWT 解析，把用户放进 SecurityContext）
   │
   ├─ Controller（admin/web/controller/erp/*.java）
   │     只做三件事：① @PreAuthorize 鉴权 ② 参数边界（页码/页大小上限）③ 组装返回体
   │
   ├─ Service（manufacturing/erp/service/*.java，15 个 / 2,374 行）
   │     业务校验、状态机、事务、幂等、待办与审批
   │
   ├─ Mapper（manufacturing/erp/mapper/*.java，19 个 + 3 个 SQL Spec / 2,264 行）
   │     @Select/@Insert/@Update 注解里写 SQL，动态条件用 <script>
   │
   └─ MySQL
```

**一句话总结分层：Controller 薄，Service 厚，Mapper 直。**

举两个能立刻验证的例子：

- `ErpOrderService.update()` 里判断「仅草稿可编辑」，然后 `@Transactional` 里先锁行、再更新表头、再删明细重建。前端只是把按钮置灰，**真正拦在后端**。
- `ErpOrderController.create()` 只有一行 `service.create(request)`，参数校验全在 Service 的 `validate()`。

**为什么不写 XML？** 这是取舍：本项目 SQL 都不长，注解里写能"一个文件看完全部查询"，改动时不用两头跳。代价是长 SQL 不好格式化、不利于复用 —— 这条我们主动承认是技术债。

## 3. 一次请求的完整链路（拿订单列表当例子）

**前端调用**：`GET /api/erp/sd/order/list?pageNum=1&pageSize=10`
（Vite 开发代理把 `/api` 前缀剥掉转发到 `127.0.0.1:8080`）

**① Controller**：`web/controller/erp/ErpOrderController.java`

```java
@PreAuthorize("@ss.hasPermi('sd:order:list')")   // ← 第一道闸
@GetMapping("/list")
public TableDataInfo list(@RequestParam(defaultValue = "1") int pageNum,
                          @RequestParam(defaultValue = "10") int pageSize,
                          @RequestParam(required = false) String keyword) {
    int safePage = Math.max(1, pageNum);
    int safeSize = Math.max(1, Math.min(500, pageSize));  // ← 参数边界，防抖
    PageHelper.startPage(safePage, safeSize);             // ← 分页插件改写 SQL
    List<Map<String, Object>> rows = mapper.list(keyword);
    TableDataInfo response = new TableDataInfo();
    response.setCode(200); response.setMsg("查询成功");
    response.setRows(rows);
    response.setTotal(new PageInfo<>(rows).getTotal());
    return response;
}
```

要点（老师问「分页怎么做的」就答这段）：

- `PageHelper.startPage()` 不改 Mapper，靠**线程变量 + 拦截器**在 SQL 末尾拼 `LIMIT`，再单独发一条 `COUNT`。
- `pageSize` 强制夹在 1~500，防止有人传 `pageSize=1000000` 把库拖死。
- 列表返回 `TableDataInfo`（`rows` / `total` 在**顶层**），和普通接口的 `AjaxResult`（数据在 `data` 里）是**两种包络** —— 这是 RuoYi 底座的约定，前端 `api/client.ts` 分两种解析。

**② Service / Mapper**

写操作才走 Service，读列表直接 Controller → Mapper（省一层，因为列表没有业务规则）。写操作例如订单确认：

```java
@Transactional
public void confirm(Long orderId) {
    if (mapper.confirm(orderId, SecurityUtils.getUsername()) != 1) {
        throw new ServiceException("订单已确认、无明细或状态不允许确认", 2001);
    }
    workflow.todo("plan", "sd_order", orderId, "planner", "订单已确认，请采购物料并按款式生成工单", ...);
}
```

注意这里**不是先查状态再改**，而是把状态条件写进 `WHERE status=0`，用「影响行数是否等于 1」判断成功。这是本项目贯穿始终的写法：**用一条语句同时完成校验和更新**，天然防并发。

3. **金额只用 DECIMAL**，Java 侧只用 `BigDecimal`，前端不参与任何结算计算（`金额 = 数量 × 单价` 全在服务端算）。

## 5. 状态机：五张单据，只走动作、不直接改状态

| 单据 | 状态 |
|---|---|
| 销售订单 `sd_order` | 0 草稿 → 1 已确认 → 2 生产中 → 3 已完工 → 4 已出货 → 5 已完成；9 已取消 |
| 报价单 `sd_quotation` | 0 待确认 → 1 已接受 → **3 已转单**；2 已失效 |
| 采购单 `pu_purchase_order` | 0 草稿 → 1 已下单 → 2 部分到货 → 3 已到货；9 已取消 |
| 生产工单 `pr_work_order` | 0 待下达 → 1 生产中 → 2 已完工 |
| 出货单 `sh_shipment` | 0 待发货 → 1 已发货 → 2 已签收；9 已取消 |

**状态只能通过动作端点迁移**，每个动作都在 SQL 的 `WHERE` 里带上前置状态。三个必须会讲的校验：

1. **报价转订单只能一次**（`ErpOrderService.create`）：

```java
if (request.quoteId() != null) {
    if (quote == null || status != 1 || 客户不一致) throw new ServiceException("报价未接受或客户不一致", 2001);
    if (mapper.countOrdersByQuote(request.quoteId()) > 0) throw new ServiceException("该报价已生成订单，不能重复下单", 2006);
}
...
if (request.quoteId() != null && mapper.markQuoteConverted(...) != 1) {
    throw new ServiceException("该报价已转订单，不能重复下单", 2006);   // ← 条件更新：只有 status=1 才能改成 3
}
```

为什么两条都要？第一条是"友好提示"，第二条是**并发下的真正闸门**：两个请求同时进来，都可能通过第一条检查，但 `UPDATE ... WHERE status=1` 只有一个能影响 1 行，另一个抛异常并回滚整张订单。

2. **报工的三重数量校验**（`ErpWorkOrderService.report`）：

```java
if (priorGood + doneQty > planned)                    // 不能超过该 SKU 计划量
    throw new ServiceException("报工超过 SKU 计划量", 2006);
if (priorProcess != null && priorGood + doneQty > 前道工序合格数)
    throw new ServiceException("前一道工序合格数量不足", 2006);
if (!outsourced && 员工不在该工序) throw new ServiceException("员工不属于该工序，不能报工", 2001);
if (!outsourced && 该员工该月工资单已确认) throw new ServiceException("...已确认，不能补录", 2001);
```

3. **完工不超过末道工序合格数**（`finish`）：`completed + 本次完工 > 末道工序合格数` 就拒绝，防止"没做完就入库"。

**老师可能问「状态能不能直接改库？」** 答：能改，但那是绕过业务的动作。我们所有页面都只调动作接口，状态迁移只发生在 Service 里，改库等于破坏数据一致性（比如订单改成"已完工"却没有工单，自检第 28 项就会 FAIL）。

## 6. 并发与幂等：本项目最值得讲的一段

### 6.1 问题

用户点了"提交"，网络卡了 3 秒，他又点一次；或者前端重试机制又发了一遍。如果后端不做处理，就会**重复入库、重复计件、重复记账**。

### 6.2 方案：请求键 + 摘要 + 状态位

表 `biz_action_request` 只有几个关键列：`request_key`（唯一）、`action_type`、`target_type`、`target_id`、`payload_hash`、`status`。

```java
// ErpStockService.begin(...)  —— 每个写动作进来先过这一关
public boolean begin(String key, String action, String targetType, Long targetId, Object payload) {
    String hash = hash(payload);                       // SHA-256(整个请求体)
    mapper.reserveAction(key, action, targetType, targetId, hash, username);  // ① 占位
    Map<String,Object> prior = mapper.action(key);      // ② SELECT ... FOR UPDATE 锁住这行
    if (不匹配 action/target/hash) throw ...2007;       // ③ 同一个键换了参数 → 拒绝
    return ((Number) prior.get("status")).intValue() == 1;  // ④ true = 已经成功执行过
}
```

对应 SQL（`ErpStockMapper`）：

```sql
INSERT INTO biz_action_request(...) VALUES(...)
ON DUPLICATE KEY UPDATE request_key=request_key;   -- 已存在就什么也不做
SELECT ... FROM biz_action_request WHERE request_key=? FOR UPDATE;  -- 锁行，串行化同键请求
UPDATE biz_action_request SET status=1, result_json=? WHERE request_key=? AND status=0;
```

**四种结果**：

| 场景 | 结果 |
|---|---|
| 首次请求 | `begin` 返回 false → 继续执行业务 → 最后 `complete()` 置 status=1 |
| 同键重复请求（参数相同） | `begin` 返回 true → **直接 return，返回首次结果**，不重复入账 |
| 同键不同参数 | 抛 `2007 请求记录不一致` |
| 不同键（真的是两次业务） | 正常执行两次 |

`requestKey` 由前端每次动作生成（`crypto.randomUUID()`），不是"页面打开时生成一次"，所以两次真业务不会撞键。

### 6.3 防负库存：不要"先查再改"

```sql
-- ErpStockMapper.subtractStock
UPDATE st_inventory SET qty = qty - #{qty}
WHERE item_type=#{type} AND item_id=#{itemId} AND batch_no=#{batch}
  AND warehouse_id=1 AND qty >= #{qty}      -- ★ 关键：把"够不够"写进条件
```

调用处判断影响行数：

```java
if (stockMapper.subtractStock(2, skuId, batch, qty) != 1)
    throw new ServiceException("成品库存不足", 2003);
```

为什么这样能防超卖：**判断和扣减在同一条语句里，由 InnoDB 行锁保证原子性**。如果写成 `SELECT qty` 再 `UPDATE qty = 计算值`，两个线程可能都读到 100，都以为够，最后扣成 -100。

### 6.4 入库用 upsert

```sql
INSERT INTO st_inventory(...) VALUES(...)
ON DUPLICATE KEY UPDATE qty = qty + VALUES(qty), update_time=NOW();
```

同一批次第二次入库就是累加，不需要先判断"有没有这条库存行"。

## 7. 事务边界：51 个 `@Transactional`

原则：**一个业务动作的"状态 + 库存 + 计件 + 资金"必须在同一个事务里**。

以发货为例（`ErpShipmentService.ship`），一个事务里做了 7 件事：

1. `workflow.assertOpen(today)` 校验会计期间没结账
2. 校验订单状态 ∈ {2 生产中, 3 已完工}、出货单状态 = 0
3. 校验本次出货量不超过订单未发量
4. 逐行扣成品库存（条件更新）+ 写出库流水
5. 改出货单状态为已发货
6. 若全部发齐 → 订单置「已出货/已完成」
7. 生成应收（金额 = 出货量 × 单价）、置待办

任何一步失败，全部回滚。**这就是为什么"发货成功但没生成应收"这种情况不会出现** —— 老师如果问"怎么保证一致性"，答案就是这两句：单事务 + 条件更新。

反例（也讲，显得你想过）：跨天、跨系统的动作（比如对接物流）无法用一个数据库事务包住，那就要靠状态机 + 补偿，这部分我们没做，属于已知边界。

## 8. 权限：三道闸 + 一次二次鉴权

### 8.1 第一道：接口注解

```java
@PreAuthorize("@ss.hasPermi('sd:order:confirm')")
@PostMapping("/confirm/{id}")
public AjaxResult confirm(@PathVariable Long id) { ... }
```

`@ss` 是注册成 Bean 的 `PermissionService`，`hasPermi` 会拿当前登录用户的权限集合做匹配；管理员账号的权限是 `*:*:*`，所以全放行。

**权限不足时返回什么？** HTTP 状态码仍是 **200**，响应体 `{"code":403,"msg":"没有权限..."}`。原因：RuoYi 的全局异常处理把 `AccessDeniedException` 包装成了业务码。前端 `client.ts` 里判断 `code !== 200` 就抛 `ApiError`，并按 `code` 分流（401 掉登录态、403 提示无权限）。**这点很容易被问，答错显得没做过。**

### 8.2 第二道：前端（不渲染）

路由守卫 + 侧边栏过滤 + 按钮 `v-if`。前端只是**体验层**，绕过它就等于直接打接口 —— 所以必须有后端。

### 8.3 第三道：方法内二次鉴权（AI 场景）

AI 问答入口只要求"能看看板"，但用户可能没有"看订单"的权限。所以方法里再查一次：

```java
private static final Map<String,String> MODE_PERMISSIONS = Map.of(
    "orders","sd:order:list", "inventory","st:inventory:list",
    "shortage","pu:suggestion:list", "cost":"dashboard:styleCost:list",
    "ontime":"dashboard:ontime:list");
...
if (!permissions.hasPermi(permission)) throw new ServiceException("没有该业务数据权限", 4002);
```

**这是全项目最正确的一处安全设计**，答辩时可以当亮点讲：`@PreAuthorize` 保护不到"方法内部按参数决定的数据范围"，必须自己再查一遍。

### 8.4 动态权限串（主数据）

主数据 10 个资源共用一个控制器，权限串是拼出来的：

```java
@PreAuthorize("@ss.hasPermi('md:' + #resource + ':list')")
@GetMapping("/{resource}/{id}")
public AjaxResult detail(@P("resource") @PathVariable String resource, ...)
```

`@P("resource")` 是显式绑定参数名 —— 因为 SpEL 默认靠编译时的 `-parameters` 开关，没开就取不到变量名，会报错。加一个主数据资源 ≈ 加一行 Spec + 一条菜单，不用写新接口。

### 8.5 角色与授权落地

8 个角色：`admin` / `sales` / `planner` / `production` / `wh` / `finance` / `hr` / `boss`。
授权原则：**谁执行动作就授给谁**。财务拿资金全流程，销售拿报价新建与转单，计划员拿主数据维护，厂长只读 + 采购审批。
`sql/p4-rbac-completion.sql` 专门保证这点，并带 7 项自检（比如"除运维专用外，每个按钮至少有一个岗位能用"、"厂长资金权限必须保持只读"）。

> 可以主动讲的发现：这轮检查发现 **34 个按钮权限没分给任何非 admin 角色**，财务角色连打开财务页的权限都没有。这不是功能没写，是授权漏了 —— 我们用一个脚本 + 自检把它补上并锁住。

## 9. 会计期间与审批

**期间结账**：`biz_period` 表按月记状态。所有会过账的动作先调 `workflow.assertOpen(date)`：

```java
public void assertOpenPeriod(String period) {
    if (Integer.valueOf(1).equals(mapper.periodStatus(period)))
        throw new ServiceException("会计期间 " + period + " 已结账，不能补录或过账", 2001);
}
```

覆盖的动作：采购收货、发货、退货、报工、盘点、收付款、工资生成。**这就是"月结之后不能补单"**。

**采购审批阈值**：`workflow.purchaseThreshold()` 读 `sys_config` 的 `erp.purchase.approval.threshold`，读不到默认 10000。超过阈值走厂长审批，审批通过后自动付款；没超过就销售直接确认。

> 诚实备注：演示库里没有配这条 `sys_config`，所以现在走的是**默认 10000**。老师问"能不能改"→ 能，插一条配置即可，代码里已经留了口子。

## 10. 单号与错误码

**单号**（`support/DocNos.java`）：正式单号形如 `PO2026000001`，依赖自增主键，只能 insert 后回填。所以流程是：

1. insert 时写 27 字符占位值 `PO-TMP-<20 位随机>`（列宽 30，留了余量）
2. 拿到主键后 `UPDATE ... SET no = formal(prefix, id)` 覆盖

> 这里有个真实踩坑可以讲：占位值早期写成 `prefix + "-TMP-" + 完整 UUID`，43 个字符，超过 `varchar(30)`，导致**所有单据新建都报 `Data too long`**。后来把随机段截到 20 位并统一走工具类才解决。这种"踩过坑并沉淀成工具"的细节，比背概念更容易得分。

**错误码**（`support/ErpErrorCode.java`，8 个，数值是前后端契约，只增不改）：

| 码 | 含义 | 典型场景 |
|---|---|---|
| 1001 | 参数校验失败 | 必填缺失、格式不对、记录不存在 |
| 1002 | 数据重复 | 编码已存在、订单色码行重复 |
| 2001 | 状态不允许 | 已确认订单再编辑、期间已结账 |
| 2003 | 余额或库存不足 | 扣库存影响行数 0、账户余额不够 |
| 2005 | 试算前提不满足 | 成本试算缺 BOM/工价 |
| 2006 | 数据已变化 | 条件更新失败、并发冲突 |
| 2007 | 请求记录不一致 | 同一个请求键换了参数 |
| 4002 | 没有该业务数据权限 | AI 问答越权 |

## 11. AI：受控问答，不是一个聊天机器人

**一句话**：模型只负责"解释已经查出来的 20 条记录"，不生成 SQL、不改单据。

流程（`ErpAiQuestionController.ask`）：

```
POST /ai/erp/ask  {mode, question}
  ├─ 限流：Redis 计数，每用户每分钟 10 次
  ├─ 校验：question 1~500 字；mode ∈ {orders,inventory,shortage,cost,ontime}
  ├─ 二次鉴权：按 mode 映射到具体读权限
  ├─ 执行预设只读 SQL，最多 20 条
  ├─ 拼提示词（含数据日期、字段说明、行数）
  ├─ 调 DeepSeek；temperature=0.3、thinking=disabled、max_tokens=800、超时 10s
  └─ 返回 {answer, rows, source, dataTime, modelUsed}
```

**三个设计细节值得讲：**

1. **关掉思考模式**：`deepseek-v4` 默认先输出推理内容，推理 token 也算进 `max_tokens`，预算不够时正文会是空的 —— 表现就是"接口 200 但没有回答"。所以显式传 `thinking: disabled`。
2. **静默降级但不静默失败**：模型不可用或超时，返回规则摘要并把 `modelUsed` 置 false，同时打一条 WARN 日志（"配了 key 却没回答"才查得出来）。
3. **不配密钥也能用**：`DeepSeekConfig.isConfigured()` 判断，未配置直接走摘要。所以答辩现场没网、没 key 也不影响演示。

## 12. 测试与自检：怎么证明"它真的对"

**32 个单元测试，6 个类，覆盖三件事：**

| 测试类 | 用例 | 验什么 |
|---|---|---|
| `SystemPermissionGuardTest` | 4 | **反射扫描**所有系统控制器方法必须有 `@PreAuthorize`；权限串必须在种子 SQL 里存在；每个模块都有菜单 |
| `ErpDraftUpdateTest` | 5 | 订单/采购单只有草稿能改；非法明细被拒；改草稿会重建明细 |
| `ErpAccessTest` | 3 | 报价非法状态流转被拒；AI 先验权限再查数据；无成本权限时看板不下发标准毛利 |
| `ErpAiPromptsTest` | 9 | 提示词只允许 5 个范围；空结果输出 `[]`；日期可读；护栏不丢 |
| `DeepSeekConfigTest` | 7 | base-url 带不带 `/v1`、带尾斜杠、占位 key 都判为"未配置" |
| `DeepSeekConfigKeysTest` | 4 | 代码用到的配置键必须在 yaml 里存在（防改名漏改） |

**60 项 SQL 自检**（四个脚本，都幂等）：

| 脚本 | 项数 | 验什么 |
|---|---|---|
| `sql/self_check.sql` | 29 | 表/视图数量、库存双向对账、报工与工序一致、计件=工资单、权限种子、**已发货必须有出库流水**、**应收必须挂本订单出货单**、**生产中必须有工单**、订单金额=明细合计 |
| `p2-demo-data-consistency.sql` | 9 | 单据合计=明细、工单数量=色码计划、期初补流水、状态回填 |
| `p3-chain-integrity.sql` | 15 | 出货-库存-应收-收款-资金全链条、报价转单一致性、待发货明细能否真发出去 |
| `p4-rbac-completion.sql` | 7 | 每个按钮至少一个岗位能用、财务能打开财务页、厂长资金只读 |

> 挑一项讲深一点最加分，例如「库存双向对账」：不只查"结存 > 流水"，还查"有流水却没有结存行"——单向比对会漏掉后一种。
