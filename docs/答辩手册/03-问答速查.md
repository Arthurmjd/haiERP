# 问答速查：60 个问题 + 标准答法

> 用法：**不要背全文，背每条的加粗那半句**。被问到时先说那半句，再补一句解释。
> 原则：**会的说细节，不会的说边界。** 不知道就说"这块没做/没测到"，然后给一个"如果做我会怎么做"，比硬编好得多。

---

## A. 项目与选题（6 题）

**1. 你们这个项目解决什么问题？**
> 服装代工厂的"订单到成本"整条链路。核心痛点有三个：一是**订单和物料脱节**（接了单不知道缺多少料），二是**库存账实不符**（有台账没流水），三是**成本算不清**（报价靠拍脑袋）。我们对应的三块：净缺料（MRP 视图）、库存流水+结存双向对账、标准成本试算并可被下一轮报价引用。

**2. 市面上有 ERP，为什么自己做？**
> 课程要求是在成熟权限底座上做业务纵深。我们复用 RuoYi 的认证、菜单、角色、日志，把精力放在服装行业的单据链路和账实一致上。市面 ERP 的广度我们做不了，但这一段链路的状态机和一致性是真做了。

**3. 覆盖了哪些角色？**
> 8 个：管理员、销售、计划员、生产主管、仓管、财务、人事、厂长。每个角色一个演示账号，权限是**按钮级**的，不是只有菜单级。

**4. 一个人能跑通全流程吗？**
> 能。用 `admin` 一个账号可以从报价一路点到收款。但为了演示权限差异，我们准备了 8 个账号，比如财务能登记收付款、厂长只能看。

**5. 数据是真的还是造的？**
> 既是真的也是造的 —— 表结构和约束是真的，业务数据是种子脚本灌的。但**数据之间是自洽的**：出货单一定能追到工单和入库流水，应收金额一定是"出货量 × 单价"算出来的。这一点有 60 项 SQL 自检兜着。

**6. 为什么不做一个 App / 小程序？**
> 这是内部管理系统，使用者是工厂的计划、仓管、财务，桌面浏览器更合适（表格多、字段多）。移动端优先的场景是报工和审批，属于后续可以做的。

## B. 架构与技术选型（8 题）

**7. 为什么用 Spring Boot 而不是微服务？**
> 单工厂、单库、团队 7 个人，微服务只会带来分布式事务和运维成本。我们的业务边界已经用**模块**分开了（manufacturing 管业务、admin 管入口），将来真要拆，按模块拆就行。

**8. 为什么后端分 6 个模块？**
> `common` 公共库、`framework` 安全与数据源、`quartz` 定时任务、`system` 系统管理、`manufacturing` 业务域、`admin` 启动类和控制器。分模块的价值是**依赖方向明确**：admin 依赖 manufacturing，manufacturing 不依赖 admin，业务代码里不可能出现"为了拿个 Controller 顺手 import"的循环。

**9. 前后端怎么联调？**
> 前端 Vite 起 5173，把 `/api` 代理到 8080 并剥掉前缀；后端返回统一包络。开发时两个进程各自热更新，不需要打包。

**10. 为什么不用 GraphQL / gRPC？**
> 我们的接口是"页面驱动"的，一个页面一两个接口，REST 够用且调试直观（浏览器能直接看）。GraphQL 的收益在"多端复用同一份数据源"，我们只有一个 Web 端。

**11. 有没有用 Redis？用在哪？**
> 两处：一是 RuoYi 底座的登录态缓存；二是 AI 问答的限流（每个用户每分钟 10 次，用 `INCR` + `EXPIRE`）。

**12. 有没有消息队列？**
> 没有。我们的业务动作都是同步的、要在同一个事务里完成（扣库存 + 写流水 + 改状态），引入 MQ 反而破坏一致性。将来要做异步的是"通知、报表刷新"这类不影响主链路的。

**13. 部署怎么部署？**
> 后端打成一个 jar（`mvn package` 后 `java -jar`），前端 `npm run build` 出静态文件交给 Nginx。数据库 MySQL、缓存 Redis。开发环境有一键脚本 `scripts/start-all.bat`。

**14. 代码量多少？**
> 后端 325 个 Java 文件 37,037 行，其中业务域 55 个文件 5,051 行；前端 31 个 `.vue` + 15 个 `.ts` 共 4,953 行。**真正自研的核心约 1.1 万行**，其余是 RuoYi 底座。

## C. 后端实现（12 题）

**15. 一次请求怎么走的？**
> Security 过滤器解析 JWT → Controller 过 `@PreAuthorize` → 参数边界 → Service 做校验、状态机、事务 → Mapper 执行注解 SQL → 返回 `AjaxResult` 或 `TableDataInfo`。读列表可以 Controller 直接调 Mapper，写操作必须过 Service。

**16. 为什么 Service 这么厚？**
> 业务规则只允许有一处。比如"仅草稿可编辑"只在 `ErpOrderService.update()` 里判一次；Controller 不判、前端不判。这样加接口不会漏校验。

**17. SQL 写在注解里，为什么不写 XML？**
> 取舍。我们的 SQL 都不长，注解能让"一个文件看完全部查询"，改条件不用两头跳。代价是长 SQL 不好格式化、不利于复用，这是已知技术债，后续复杂查询应该下沉到 XML。

**18. 分页怎么实现的？**
> PageHelper：`PageHelper.startPage()` 把分页参数放线程变量，拦截器在 SQL 末尾拼 `LIMIT` 并单独发一条 `COUNT`。另外 `pageSize` 在 Controller 里夹在 1~500，防止有人传超大值。

**19. 怎么防超卖 / 负库存？**
> 不"先查再改"，而是把"够不够"写进更新条件：
> `UPDATE st_inventory SET qty=qty-? WHERE ... AND qty>=?`，影响行数不等于 1 就抛"库存不足"。判断和扣减在同一条语句里，由行锁保证原子性。

**20. 用户重复提交怎么办？**
> 前端每个动作生成一个 `requestKey`（UUID），后端落到 `biz_action_request` 表：同键同参数 → 直接返回首次结果；同键不同参数 → 报 2007；不同键 → 正常执行两次。表上 `request_key` 唯一，配合 `ON DUPLICATE KEY` + `SELECT ... FOR UPDATE` 把并发同键请求串行化。

**21. 一个业务动作涉及多张表，怎么保证一致？**
> 单事务。比如发货一个 `@Transactional` 里做 7 件事：校验期间、校验状态、校验未发量、扣库存+写流水、改出货状态、改订单状态、生成应收。任何一步失败全回滚。全项目 51 个 `@Transactional` 方法。

**22. 状态能直接改数据库吗？**
> 技术上能，业务上不行。状态只通过动作端点迁移，SQL 里带前置状态（`WHERE status=0`）。直接改库会出现"已完工但没有工单"这类矛盾，自检第 28 项就会 FAIL。

**23. 单据号怎么生成的？**
> 正式号形如 `PO2026000001` 依赖自增主键，只能 insert 后回填。所以先写一个 27 字符占位值，拿到主键再覆盖。这里踩过坑：早期占位值是完整 UUID，43 字符超过 `varchar(30)`，导致所有单据新建报 `Data too long`，后来统一收到工具类 `DocNos`。

**24. 错误码怎么设计的？**
> 8 个码，数值是前后端契约，只增不改：1001 参数、1002 重复、2001 状态、2003 库存/余额、2005 试算前提、2006 数据已变化、2007 请求记录不一致、4002 数据权限。前端按码分流，不靠解析文案。

**25. 会计期间结账做了什么？**
> `biz_period` 按月记状态，所有会过账的动作（收货、发货、退货、报工、盘点、收付款、工资）先调 `assertOpen(date)`，已结账直接拒绝。这样"月结之后不能再补单"是硬约束。

**26. 并发真的测过吗？**
> 说实话没做压测。我们做的是**机制层面**的保证：条件更新 + 唯一键 + 行锁 + 幂等表，这些是数据库层面就成立的。真要压测，会用 JMeter 对"同一请求键并发 100 次"和"同一批次并发扣库存"两个场景打。

## D. 前端实现（10 题）

**27. 前端怎么组织的？**
> 28 个页面，但手写页面只有 10 个，其余是配置驱动：`api/catalog.ts` 里一张表描述每个列表页（接口、权限、列、枚举、是否要年月筛选），`CatalogView.vue` 一个组件渲染出来。加列表页只加配置。

**28. 权限在前端怎么控制？**
> 三处：路由守卫（没权限跳 `/forbidden`）、侧边栏（`can()` 过滤）、按钮（`v-if`）。但这三处都只是"不渲染"，真正的拦截在后端 `@PreAuthorize`。

**29. 为什么权限不足还返回 200？**
> 这是 RuoYi 的约定：`AccessDeniedException` 被全局异常处理包装成业务码，HTTP 仍是 200，响应体 `code=403`。所以前端不能只看 HTTP 状态码，要看包络里的 `code`。

**30. Token 存哪？**
> `localStorage`，键 `hai-erp-token`。请求拦截器统一加 `Authorization: Bearer`。401 时清 token 并派发事件，路由跳到登录页。

**31. 为什么不做动态路由（`/getRouters`）？**
> 现在是静态路由表 + 后端菜单鉴权。诚实的说法：`/getRouters` 接口是有的，但前端没用，导致后端加菜单和前端加导航要改两处。这是已知的前端债，正解是改成"拉菜单→映射组件→`addRoute`"。

**32. 枚举文案在哪维护？**
> `api/labels.ts`，91 条"状态码 → 标签 + 标签色"。好处是全站文案一致；代价是它和 SQL 字段 `COMMENT` 是两份，新增状态要改两处。

**33. 前端怎么保证不出类型错误？**
> `npm run build` 里先跑 `vue-tsc -b`，类型不过就不出包。另外有 `npm run typecheck` 和 ESLint。

**34. 有没有前端单测？**
> 没有，这是缺口。现在靠类型检查 + 后端测试 + 8 个账号手工验收。要补的话优先补 `stores/user.ts` 的权限通配匹配和 `api/client.ts` 的包络解析。

**35. 为什么用 Element Plus？**
> 组件齐全、文档中文、和 RuoYi 生态一致。代价是包体偏大，已经配了按需引入但没做深度裁剪。

**36. 大表格卡不卡？**
> 我们每页固定 10 条，不会渲染上千行。真要展示大量数据，做法是服务端分页 + 虚拟滚动，后者没做。

## E. 数据库（8 题）

**37. 一共多少张表？**
> 66 张，其中业务表 47 张（md/hr/sd/pu/pr/st/sh/fn/biz 九个前缀）、平台表 19 张（`sys_*`），另有 9 个视图。

**38. 为什么库存要两张表？**
> `st_inventory` 是结存（当前有多少，按物料+批次+仓库唯一），`st_stock_txn` 是流水（每一次进出都记一条，只增不改）。结存是流水的物化，任何时点的库存都能从流水重算，这就是"账实可对账"的前提。

**39. 怎么对账？**
> 按 `(item_type, item_id, batch_no, warehouse_id)` 四元组**双向**比：既查"结存比流水多"，也查"有流水却没有结存行"。单向比对会漏掉后一种，这是自检第 3 项。

**40. 为什么工单要冻结 BOM 和工价？**
> 因为主数据会变。工单建单时把色码计划量、BOM 用量、工序工价抄一份到 `pr_work_order_*`，之后改款式或改工价不影响在产工单，成本也能复算。

**41. 成本是实际成本吗？**
> 不是，是**标准成本**：冻结 BOM × 物料参考价快照 + 计划合格量 × 冻结工价 + 冻结费率。它不等于实际领料成本，也不等于净利润。这个口径我们文档里写得很明白，避免被误解。

**42. 应收/应付怎么产生的？**
> 应收由发货产生：金额 = 出货数量 × 订单单价，到期日 = 发货日 + 客户账期。应付由采购产生：小额确认即付款、大额审批通过后付款，收货时若已有应付就不重复挂账。收款/付款核销后余额递减。

**43. 账龄怎么算的？**
> 按到期日与今天的天差分档：未到期、1-30、31-60、61-90、90 以上。接口 `/erp/finance/aging-summary` 一次返回应收和应付两组。

**44. 为什么用视图？**
> 净缺料、准时率、款式成本这类口径复杂且要复算，做成视图保证"看板和列表用同一套口径"，不会出现两个页面两个数。

## F. 权限与安全（8 题）

**45. 权限模型是什么？**
> RuoYi 的 RBAC：用户 → 角色 → 菜单（M 目录 / C 页面 / F 按钮），菜单的 `perms` 一列就是权限串。后端 `@PreAuthorize("@ss.hasPermi('...')")`，前端 `can()`。一共 186 项菜单，其中 ERP 业务 132 项（1 目录 + 32 页面 + 99 按钮）。

**46. 前端藏了按钮就安全了吗？**
> 不安全，前端只是体验。所以每个接口都有注解兜底，绕过页面直接打接口会被 403。

**47. 管理员为什么能看全部？**
> 管理员的权限集合是 `*:*:*`，`hasPermi` 和前端 `can()` 都支持通配匹配，所以一条就通吃。

**48. 有没有越权漏洞？**
> 228 处生效注解覆盖了业务接口；系统管理那一批还有一条反射扫描的测试兜底 —— 它在 `web/controller/system` 目录下逐个类、逐个方法扫，谁没加注解就测试失败（登录/注册/个人中心/首页 4 个类按设计豁免）。注意这条测试只管系统管理控制器，ERP 业务控制器是靠约定和 code review。
> 但要诚实说：`CacheController`、`ServerController`、`UserOnlineController`、`BillFrozenController` 里还有 21 处注解被 `//` 注释掉，等于登录即可访问。这是已知缺口，补法是把这批权限码写进 `sys_menu` 再放开注解。

**49. 你们发现并修过什么真实缺陷？**
> 三个比较典型的：① 34 个按钮权限没分给任何非 admin 角色，财务角色连财务页都打不开；② 出货单状态是"已签收"但没有任何出库流水（幽灵出货单）；③ 应收单硬编码了出货单主键，指到了别人的单子上。三个都写成了自检项，防止再犯。

**50. 密码怎么存的？**
> RuoYi 底座用 BCrypt 加盐哈希，数据库里看不到明文。演示账号密码只用于本机。

**51. 有没有 SQL 注入风险？**
> 所有查询用 MyBatis 的 `#{}` 参数绑定，不拼字符串。主数据因为表名/列名是动态的，走的是白名单 Spec（`ErpMasterSql.SPECS`），不是把用户输入直接拼进 SQL。

**52. 数据级权限做了吗？**
> 没做。现在只到功能级（能不能访问这个接口）。角色表里预留了 `data_scope` 字段，但业务查询还没按部门过滤 —— 这是明确的首期边界。

## G. AI（6 题）

**53. AI 在这套系统里干什么？**
> 只干一件事：把已经查出来的 20 条业务记录解释成人话。查什么由用户选（订单/库存/缺料/成本/准时率五档），查多少由代码定（LIMIT 20），SQL 是写死的，模型不碰数据库。

**54. 为什么不做自由问答 / NL2SQL？**
> 两个原因：幻觉和成本。让模型随便写 SQL，它可能编造不存在的订单，也可能写出全表扫描。所以我们把 AI 收窄成"解释工具"，输入输出都受控。

**55. 模型挂了怎么办？**
> 降级为规则摘要，返回里 `modelUsed=false`。不配密钥、没网、超时，页面照常能用，只是回答变成"已按范围查出 N 条记录，请核对下方数据"。

**56. 怎么防刷？**
> Redis 计数，每用户每分钟 10 次；问题长度限制 1~500 字；`max_tokens=800`、超时 10 秒。

**57. 用的什么模型？**
> DeepSeek HTTP 接口（`deepseek-v4-flash`），不是 Spring AI。配置在 `web/ai/DeepSeekConfig`，密钥走环境变量。

**58. AI 会不会改数据？**
> 不会。它只有一个出口：返回一段文字 + 原始记录。所有写操作都在别的接口里，且都有权限注解。

## H. 测试与质量（6 题）

**59. 怎么测的？**
> 三层：32 个单元测试（6 个类）、60 项 SQL 自检（4 个脚本）、8 个账号手工验收。前端有 `vue-tsc` 类型检查和 ESLint。

**60. 32 个单测都测什么？**
> 最有价值的是 `SystemPermissionGuardTest`：用反射扫描所有系统控制器方法，断言每个方法都有 `@PreAuthorize`，且权限串在种子 SQL 里存在 —— 这是防"改代码删注解"的护栏。其余是提示词护栏、DeepSeek 配置解析、草稿可编辑、AI 二次鉴权、看板毛利脱敏。

**61. 60 项自检查什么？**
> 库存双向对账、报工与工序进度一致、计件等于工资单、单据金额等于明细合计、已发货必须有出库流水、应收必须挂本订单出货单、生产中必须有工单、每个按钮至少一个岗位能用……

**62. 这些检查是自动跑的吗？**
> 不是，是本地手工执行 SQL 脚本。这是明确的不足 —— 没有 CI，应该在提交时自动跑。

**63. 有没有性能测试？**
> 没有。演示数据量很小（订单 38、工单 24、库存流水 197 条），没有意义。真要做，先定指标（P95 响应时间、并发数），再用 JMeter。

**64. 代码规范怎么保证？**
> 后端靠分层和命名约定（`Erp*`）、错误码集中；前端靠 ESLint + TS 严格模式。没有强制 code review 流程，这是团队规模决定的。

## I. 不足与改进（6 题，务必主动讲）

**65. 你们最大的不足是什么？**
> 三个：没有工作流引擎（审批只有通过/驳回，没有多级会签和条件分支）、报工没有复核（报工直接生成计件，缺少班长确认）、没有 CI（测试和自检都是手工跑）。

**66. 还有呢？**
> 数据级权限没做、没有冲销流程（单据只能作废不能红冲）、前端没有单测、单据页重复度高没抽通用组件。

**67. 如果再做一周，你先做什么？**
> 先补 CI（把 32 个单测和 60 项自检串起来，每次提交自动跑），因为这是所有后续改动的地基；然后补报工复核，因为它直接影响工资准确性。

**68. 为什么不做多组织 / 多仓库？**

## J. 送命题（8 题，怎么答不翻车）

**71. 「这段代码是你写的吗？」**
> 不要说"都是我写的"，也不要说"不是我写的"。答：**"这块是我负责的，具体在 X 文件，我给您翻。"** 然后立刻打开文件，讲一个具体判断（比如为什么这里用条件更新）。

**72. 「用 AI 写的吧？」**
> 「用了 AI 辅助，但有三件事 AI 替不了：一是权限串和菜单逐条对齐，要人判断哪条配哪个角色；二是缺陷定位，比如"已签收却没有出库流水"这种，得先想到去对账才发现；三是业务规则，比如报工不能超过前道工序合格数，这是服装厂的实际约束。」

**73. 「这个功能我点了一下报错，你怎么解释？」**
> 先看报错内容，不要慌。三层判断：① 400 类/业务码 → 参数或状态不对，看提示语；② 403 → 权限，换有权限的账号；③ 500 → 看后端日志。
> 现场话术：「这个提示是状态校验，说明这张单子当前状态不允许这个操作，我换一张能操作的单子演示。」

**74. 「你们的数据库设计有什么问题？」**
> 主动说两条：一是金额和数量用了 DECIMAL 但部分汇总字段没有加索引，数据量大了列表会慢；二是 `st_stock_txn` 是纯追加表，没有分区策略，长期会很大。

**75. 「并发你测了吗？」**
> 「没压测，只有机制保证。」然后讲条件更新 + 唯一键 + 幂等表，**不要吹"我们支持高并发"**。

**76. 「这个需求你怎么理解错了？」（老师指出一个缺陷）**
> 「您说得对，这块确实没考虑到。现在的实现是 X，问题在于 Y，正确做法应该是 Z。」**承认 + 定位 + 方案**，三步，不要辩解。

**77. 「你觉得你们组谁做得最多？」**
> 不要评价队友。答：「我们是按模块分的，我负责 X 和 Y，这块我能讲清楚；其他模块是队友做的，具体细节可以请他补充。」

**78. 「给你 5 分钟，你还能加什么功能？」**
> 挑一个你熟的、能落地的：「给采购单加金额分级审批 —— 现在只有一个固定阈值 10000，可以按金额段配不同审批人。这不用改表结构，`sys_config` 加几条配置 + 审批表加一个 `level` 字段就行。」

## M. 应急：一句话兜底

被问到完全不会的问题时，用这三句之一，不要沉默、不要编：

1. 「这块不是我最熟的，我讲一下我的理解，可能不完整——」
2. 「这个我们没做，原因是 X；如果要做，我会从 Y 开始。」
3. 「您问的是接口层还是数据层？我分开说。」

**绝对不要说的三句**：
- 「这个是我队友做的，我不知道。」（应该说"我负责的是 X，这块可以补充"）
- 「这个是 AI 写的。」（应该说"用了 AI 辅助，设计是我们做的"）
- 「应该没问题吧。」（没验证过就别说没问题，说"这个我没测到"）
