## 一、3 分钟版（时间被压到最短时用这个）

### 第 1 段｜定位（30 秒）

> 「我们做的是**服装制造企业的 ERP**，覆盖从客户报价、销售订单、采购原料、生产工单、领料报工、完工入库、出货签收，一直到应收收款、标准成本结算的整条链路。前端 Vue 3 + TypeScript，后端 Java 21 + Spring Boot 3.5，数据库 MySQL，缓存 Redis，权限底座是 RuoYi。」

### 第 2 段｜规模（40 秒，只报数字，不解释）

> 「先给一组实数：后端 6 个 Maven 模块、**325 个 Java 文件**；对外 **43 个 REST 控制器、260 个方法级接口**；**228 处生效的权限注解**；数据库 **66 张表**（其中 47 张业务表）加 **9 个视图**；还有 **60 项 SQL 自检**和 32 个单元测试，全部通过。」

（如果老师问「这些数字怎么来的」，答：`find backend -name "*.java" | wc -l`、`grep -rc "@PreAuthorize"`，当场可以敲。）

### 第 3 段｜一条业务主线（60 秒）

> 「主链路一共 19 步，我只讲关键的三段：
> 第一段是**接单**：报价单成交后转成订单，转单是一次性的 —— 同一张报价不能转两次，防止重复生产、重复记账。
> 第二段是**生产**：订单确认后按「订单 + 款式」建工单，建单那一刻就把色码计划量、BOM 用量、工序工价**冻结**到工单里，后面改主数据不影响在产工单；领料只认现存库存，在途的不算。
> 第三段是**出货与结算**：仓管员在「出货单 → 待出货订单」里就能看到所有已完工待发的订单（不用进销售订单），分批发货、签收，发货那一刻自动生成应收（金额 = 出货数量 × 订单单价，到期日 = 发货日 + 客户账期），收款核销后应收余额递减，最后做标准成本试算并确认，确认后的成本可以给下一轮报价当依据。」

### 第 4 段｜三个技术亮点（50 秒）

> 「三个我们花力气最多的地方：
> 一是**幂等**：所有会动库存、动钱的动作都带请求键，落在 `biz_action_request` 表里去重，用户狂点提交或者网络重试，只会入账一次。
> 二是**权限**：不是只有菜单藏起来，后端每个接口都有 `@PreAuthorize` 兜底；权限不足返回的是 HTTP 200 + 响应体 `code=403`，前端按码分流。
> 三是**数据能对账**：我们写了 60 项自检 SQL，其中一项是把「库存结存」和「库存流水」按物料+批次双向比对 —— 多一条、少一条都会 FAIL。」

### 第 5 段｜收尾（20 秒）

> 「不足也说三条：没有工作流引擎，审批只有通过/驳回两段式；报工没有复核环节，报工直接生成计件；没有接 CI，自检和单测都是本地手工跑的。谢谢老师。」

## 二、8 分钟版（推荐，覆盖前后端）

### 开场（20 秒）

> 「各位老师好，我讲我们这套服装 ERP。我按三条线讲：**业务怎么转、后端怎么接、前端怎么呈现**，最后讲验证和不足。」

### 线一｜业务怎么转（2 分钟）

投影打开「工作台」，指着待办中心说：

> 「我们的设计起点不是功能菜单，是**单据流转**。一张订单会依次产生：采购单 → 入库流水 → 生产工单 → 领料流水 → 报工记录与计件工资 → 完工入库 → 出货单 → 应收 → 收款。

> 每一步都有一个明确的前置条件，比如：
> · 领料必须先有工单、而且只认现存库存，采购在途的量不能拿来领；
> · 报工的合格数不能超过这道工序的计划量，也不能超过前一道工序的合格数；
> · 发货要校验订单未发数量，分批发完才算「发齐」，签收是另一个动作、另一个状态；
> · 成本是**标准成本**，用冻结的 BOM 和冻结的工价算，不是实际领料成本，退货也不冲回已确认成本。

> 这些规则不是写在文档里的，是写在服务层的校验里的，我一会儿可以翻代码。」

### 线二｜后端怎么接（3 分钟）

打开 `backend/` 目录，讲结构：

> 「后端 6 个模块：`ruoyi-common` 公共库、`ruoyi-framework` 安全与数据源、`ruoyi-quartz` 定时任务、`myfactoryai-system` 系统管理、`myfactoryai-manufacturing` 业务域、`myfactoryai-admin` 启动类和控制器。

> 业务代码集中在 manufacturing 的 `erp` 包里，55 个文件 5000 行左右，分四层：`service` 15 个（校验、状态机、事务）、`mapper` 19 个（SQL 全写在注解里，没有 XML）、`domain` 15 个（请求体）、`support` 3 个（错误码、单号、提示词）。

然后讲一次请求（用订单列表举例，见 `01-后端篇.md` 第 3 节）：

> 「一次请求的链路是：前端带 `Bearer` token → 过 Security 过滤器链 → 进 Controller，先过 `@PreAuthorize` 鉴权 → Controller 只做参数边界（页码、页大小）→ 交给 Service 做业务校验和事务 → Mapper 执行注解 SQL → 返回 `AjaxResult` 或 `TableDataInfo`。
> 分层的好处是**业务规则只有一处**：比如「仅草稿可编辑」，只在 Service 里判一次，Controller 不管，前端也不管（前端只是把按钮置灰，真正拦截在后端）。」

再讲三个硬点（每个 30 秒）：

1. **幂等**：`biz_action_request` + 请求键 + payload 的 SHA-256。同一个键、同样的参数 → 直接返回首次结果；同一个键、不同参数 → 报 2007。
2. **防负库存**：扣库存不是先查再改，而是一条带条件的更新 `UPDATE ... SET qty=qty-? WHERE ... AND qty>=?`，影响行数为 0 就抛「库存不足」。这条语句把并发下的超卖挡住了。
3. **权限两道**：`@PreAuthorize` 挡接口；AI 问答在方法里再按查询范围查一次权限（`sd:order:list` 这种），因为 AI 是"二次鉴权"的典型场景。

### 线三｜前端怎么呈现（2 分钟）

> 「前端 28 个页面，但真正手写的页面只有 10 个，其余是靠**配置驱动**：`api/catalog.ts` 里一张表描述每个列表页 —— 标题、接口路径、权限、列定义、枚举类型、是否要年月筛选，`CatalogView.vue` 一个组件根据配置渲染表格、分页、表单弹窗。
> 所以加一个列表页不用新建 Vue 文件，只加一段配置 + 一条菜单。」

> 「权限在前端有三处生效：路由守卫（`router.ts` 的 `beforeEach`，没权限直接跳 `/forbidden`）、侧边栏（`App.vue` 按 `can()` 过滤）、页面按钮（`v-if="user.can('...')"`）。三处都是"不渲染"，真正的拦截在后端。」

> 「页面里值得讲的是**财务页 8 个标签**：总览、账户、资金流水、月度现金流、应收、应付、账龄汇总、收付款。标签本身也按权限过滤 —— 财务能看到收付款，厂长只能看，同一个页面两种角色不同能力，这个现场可以演示。」

### 验证与不足（40 秒）

> 「验证分三层：32 个单元测试（含一条用反射扫描所有控制器方法必须有 `@PreAuthorize` 的护栏测试）、60 项 SQL 自检（库存双向对账、单据链路、权限完整度）、以及手动跑通的演示链路。前端 `npm run build` 含 `vue-tsc` 类型检查。
> 不足：没有工作流引擎、报工无复核、没有 CI。」
